# lania-g v3 技术方案

## 1. 文档目的

本文档用于说明 `lania-g v3` 的当前整体架构、分层职责、运行机制、扩展模型以及稳定性边界。本文档以当前仓库中的实际代码实现为准，不再描述历史演进阶段的中间方案。

本文档面向以下读者：

- 框架维护者
- 业务应用接入方
- 协议适配器与基础设施扩展开发者

## 2. 设计目标

`v3` 的核心设计目标如下：

1. 将应用装配、模块依赖管理、协议适配、参数绑定、运行时执行与基础设施集成进行职责分离。
2. 以统一运行时承接多协议请求执行，避免在各适配器中重复实现核心调用链。
3. 以声明式编译模型连接“协议 DSL”与“运行时执行器”，保证扩展协议时不必侵入核心执行层。
4. 对业务层暴露稳定且有限的使用面；对内部基础设施层保留演进空间。
5. 通过实例级 `Registry`、类型化取值能力以及模块化 integration 模式提升可维护性与可预测性。

## 3. 总体架构

### 3.1 分层结构

当前框架的核心分层如下：

- `application`
  - 负责应用实例创建、适配器挂载、协议插件收集、编译安装、生命周期管理与启动过程控制。
- `core/module`
  - 负责模块定义、模块加载、模块图构建、容器挂载以及模块引用暴露。
- `core/di`
  - 负责 provider 管理、实例构建、作用域处理、父子容器关系以及按 token 或按类型取值。
- `core/registry`
  - 负责保存协议声明、binding 解析器注册以及全局 AOP 声明。
- `core/compiler`
  - 负责将 `Registry` 中的声明交由协议插件扫描、编译并安装到运行时。
- `core/runtime`
  - 负责请求匹配、参数绑定、AOP pipeline、handler 调用与错误归一化。
- `adapter/*`
  - 负责协议 DSL、协议 transport、协议编译插件以及协议相关定义。
- `binding/*`
  - 负责协议参数绑定包装类型与默认 binding resolver。
- `integrations/*`
  - 负责将外部基础设施能力以模块方式接入框架，包括自动绑定、Factory、默认实例和命名实例等模式。

### 3.2 架构原则

该分层遵循以下原则：

- 业务使用面与内部实现面分离。
- 协议适配层与运行时执行层分离。
- 编译期声明与运行期执行分离。
- 默认实例与命名实例统一建模。
- 通过模块化与容器化处理大多数资源管理问题。

## 4. 核心执行链路

### 4.1 启动期链路

应用启动期的主要链路如下：

```text
root module
  -> module loader
  -> 构建 moduleRef 与容器树
  -> adapter mount
  -> 收集 protocol plugins
  -> compiler.Compile(moduleRef, registry, plugins...)
  -> compiled.Install(runtime)
  -> adapter.Start() / app.Listen(addr)
```

其含义如下：

1. 应用以一个根模块作为装配入口。
2. `ModuleLoader` 负责展开 imports、构建容器树并暴露 `ModuleRef`。
3. `Application` 在挂载 adapter 时同时收集各 adapter 暴露的 `ProtocolPlugin`。
4. 编译阶段读取 `Registry` 中的声明，按协议插件进行扫描与编译。
5. 编译结果安装到统一 `Runtime` 中。
6. 各 adapter 进入监听或启动状态。

### 4.2 请求期链路

运行期统一执行链路如下：

```text
client request
  -> adapter transport
  -> HandlerContext
  -> runtime route match
  -> binding resolve args
  -> AOP pipeline
  -> invoke handler
  -> adapter write response
```

其含义如下：

1. 协议 adapter 负责解析原始请求并构造 `HandlerContext`。
2. `Runtime` 负责按协议匹配 handler。
3. `BindingRegistry` 负责解析 handler 参数。
4. `Pipeline` 负责执行 middleware、guard、interceptor、pipe、filter 等 AOP 逻辑。
5. 执行器最终调用业务 handler。
6. adapter 将运行结果转换为协议响应。

### 4.3 启动前诊断与可预测性

为了降低“声明写了但运行时不生效”的排查成本，v3 在应用层提供了显式诊断入口：

- `CompileDiagnostics()`
  - 触发编译并返回编译诊断快照（已注册插件、协议安装顺序、声明数量、路由数量、binding resolver 数量、全局 AOP 汇总、routeKey 冲突等）
  - 推荐作为启动前必选预检查
- `StartupReport()`
  - 从“应用视角”汇总模块、adapter、协议、路由与关键摘要信息
  - 可通过 `Options.StartupReporter` 在启动时自动输出

同时，编译阶段与安装阶段都具备 routeKey 冲突防御：

- 编译阶段对“跨协议/跨插件 routeKey 冲突”直接报错，避免静默覆盖
- 安装阶段对“安装时重复 routeKey”做防御性报错，避免非预期覆盖

## 5. Application 设计

包：`application`

### 5.1 职责

`Application` 是对外的应用装配入口，其职责包括：

- 接收根模块
- 创建并持有 `Runtime`
- 持有 `Registry`
- 挂载 adapter
- 收集协议插件
- 触发编译与安装
- 管理生命周期启动与停止

此外，`Application` 提供 adapter 专属 API 访问入口（用于“在应用实例上注册声明或调用 adapter 扩展能力”）：

- `API(adapterID string) (any, bool)`

### 5.2 Registry 注入与实例隔离

当前版本已经提供实例级 `Registry` 隔离入口：

```go
app, err := application.NewWithOptions(root, application.Options{
    Registry: reg,
}, adapters...)
```

这项能力的目的在于：

- 避免多个应用实例共享全局声明池
- 降低测试之间的状态污染
- 使 adapter DSL、binding 注册与生命周期挂载可绑定到某个 app 实例

兼容性策略如下：

- `registry.Global()` 仍保留，用于历史兼容与默认 DSL 行为。
- 新代码应优先采用实例级 `Registry`。

### 5.3 生命周期管理

`Application` 负责两类生命周期：

- 适配器生命周期：`Start()` / `Stop()`
- 模块实例生命周期：`OnApplicationBootstrap`、`OnApplicationShutdown` 等

当前实现中，应用在执行生命周期时还会向支持以下接口的 provider 实例注入应用上下文：

- `SetRegistry(*registry.Registry)`
- `SetModuleRef(*module.ModuleRef)`

这使得生命周期型桥接组件可感知当前应用实例，而不必退回到全局状态。

## 6. Module 与 DI 设计

包：

- `core/module`
- `core/di`

### 6.1 模块模型

模块是框架中的资源组织单位。模块元数据主要包括：

- `Imports`
- `Providers`
- `Controllers`
- `Resolvers`
- `Exports`

模块的主要职责包括：

- 定义资源边界
- 承载容器实例
- 决定可见性与导出关系

### 6.2 ModuleLoader

`ModuleLoader` 负责：

- 展开根模块及其 imports
- 构建模块树
- 构建并暴露 `ModuleRef`
- 维护 `loadedModules`
- 对支持 `RegistryAware` 的模块注入应用 registry

### 6.3 ModuleRef

`ModuleRef` 是运行期访问模块图与实例容器的统一引用。

当前版本提供两类实例解析方式：

- 按 token：`Get(token)` / `MustGet(token)`
- 按类型：`GetByType[T]` / `MustGetByType[T]`

按类型获取是当前推荐方式，适用于默认实例的解析。

### 6.4 Container

`Container` 是 provider 实例的承载者。当前版本提供：

- 原始 token 解析能力
- 父子容器关系
- 类型化 `GetByType[T]` / `MustGetByType[T]`

类型化取值能力的目标在于：

- 降低直接书写 `reflect.TypeOf((*X)(nil)).Elem()` 的成本
- 使默认实例获取方式更具可读性

## 7. Registry 设计

包：`core/registry`

### 7.1 职责

`Registry` 负责保存三类声明：

1. 协议 DSL 写入的声明，例如 HTTP route、gRPC method、WS gateway、MQ subscription、Scheduler job 等。
2. binding resolver 注册信息。
3. 全局 AOP 注册信息。

### 7.2 设计动机

协议 DSL 是编译期输入，而非运行期直接执行对象。因此，框架需要一个编译前的声明仓库，由协议插件读取并转换为运行时结构。

### 7.3 当前策略

- `Registry` 是编译期声明存储，不直接承担运行时匹配逻辑。
- `adapter/*` 的 DSL 默认写入 `registry.Global()`；在应用级注入 registry 的场景中，模块初始化与生命周期桥接优先使用实例级 registry。
- `binding/*` 的默认注册函数可以写入指定 registry，而非强依赖全局实例。

## 8. Compiler 与 Runtime 设计

### 8.1 Compiler

包：`core/compiler`

`Compiler` 的职责是：

- 接收 `moduleRef`
- 接收 `Registry`
- 接收所有已挂载协议 adapter 暴露的 `ProtocolPlugin`
- 对每个插件执行扫描与编译
- 产出统一 `CompiledApp`
- 将编译结果安装到 `Runtime`

编译过程同时承担“跨协议一致性”的关键职责：

- 固定化协议安装顺序以保证编译结果可复现
- 进行跨协议 routeKey 冲突检测，避免出现静默覆盖导致的不可预期行为
- 汇总诊断信息，为启动前检查与排障提供结构化输入

### 8.2 Runtime

包：`core/runtime`

`Runtime` 的职责是：

- 维护匹配结果
- 维护 `BindingRegistry`
- 维护执行器与 AOP pipeline
- 统一执行 handler
- 统一错误封装

从设计上看，`Runtime` 是协议无关的。协议差异由 adapter transport 和 plugin 编译过程负责吸收。

在安装语义上，v3 采用“编译产物安装到全新 Router”的方式减少状态污染：

- 每次 `CompiledApp.Install(runtime)` 都会创建新的 Router 并安装 matcher/routes
- 安装完成后以原子方式替换 runtime 内部 Router
- 同时向 Executor 注入 BindingRegistry 与 RouteContainers，确保参数绑定与路由容器归属可预测

### 8.3 稳定性边界

`Runtime` 和 `Compiler` 目前属于内部基础设施层，不建议业务代码直接依赖其细节 API。业务应通过：

- `application`
- `adapter/*`
- `binding/*`
- `integrations/*`

进行扩展与接入。

## 9. Adapter 设计

包：`adapter/*`

### 9.1 定位

adapter 层承担以下职责：

- 提供协议 DSL
- 提供 transport
- 提供协议编译插件
- 将协议请求映射为统一运行时调用

### 9.2 已支持适配器

当前版本已经提供以下适配器：

- `adapter/http`
- `adapter/ws`
- `adapter/graphql`
- `adapter/grpc`
- `adapter/mq`
- `adapter/scheduler`

### 9.3 DSL 设计原则

DSL 仅负责“声明”，不负责直接执行。

典型示例如下：

- HTTP：`Controller(...).Get(...).Build()`
- gRPC：`Service(...).Method(...).Build()`
- WS：`Gateway(...).On(...).Build()`
- MQ：`Consumer(...).On(...).Build()`
- Scheduler：`Job(...).Every(...).Build()`

这些声明最终进入 `Registry`，并在编译阶段由相应 plugin 处理。

### 9.4 DSL 错误处理策略

为了增强稳定性，当前版本对部分高风险 DSL 误用已从 panic 收敛为 error：

- HTTP `ControllerBuilder`
  - 提供 `Err()`
  - 提供 `BuildE()`
- gRPC `ServiceBuilder`
  - 提供 `Err()`
  - 提供 `BuildE()`

兼容性考虑：

- `Build()` 仍保留，以兼容现有代码。
- 推荐新代码优先使用 `BuildE()`，并显式处理错误。

## 10. Binding 设计

包：`binding/*`

### 10.1 定位

binding 层负责将协议输入映射到 handler 参数，其目标是为业务 handler 提供类型化参数接入方式。

### 10.2 设计原则

- wrapper 类型优先
- 组合 struct 支持 tag 定义 bindingName
- resolver 注册到 registry
- 解析逻辑统一通过 runtime 调用

### 10.3 已支持 binding

当前版本已提供：

- HTTP binding
- WS binding
- GraphQL binding
- gRPC binding
- MQ binding
- Scheduler binding

这些 binding 在使用层面表现为 handler 参数包装类型，例如：

- `Body[T]`
- `Query[T]`
- `Param[T]`
- `Header[T]`
- `Context`
- 其它协议的 request / metadata / event / message wrapper

## 11. Integrations 设计

包：`integrations/*`

### 11.1 统一模式

当前大多数 integration 遵循统一模式：

- 模块初始化：`ForRoot(...)`
- 多实例初始化：`ForRoots(...)` 或 `ForRootMulti(...)`
- 手动实例获取：`Factory`
- 默认实例自动绑定：`InjectXxx`
- 命名实例自动绑定：`XxxRef[NamedMarker]`

### 11.2 默认实例与命名实例

- 默认实例：该 integration 在一个应用中最常用的主实例。
- 命名实例：相同资源类型的多实例，通过 name 区分。

这一定义统一适用于：

- HTTP client
- gRPC client / conn
- logger
- cache
- ORM datasource / repository
- Kafka client
- 其它具备多实例语义的 integration

### 11.3 ORM 的当前定位

`integrations/orm` 当前定位为：

- 基于 GORM 的关系型数据库 integration
- 支持默认数据源与命名数据源
- 支持 repository 自动绑定
- 支持多数据源模块化接入

其边界明确如下：

- 它并非通用数据库抽象层。
- 它不承担 MongoDB 等 NoSQL 数据库的统一抽象。
- `Entity(...)` 当前仅承载表名与主键元数据。
- 字段类型、索引、注释、约束等仍由 GORM model tag 管理。

### 11.4 Events 的当前定位

`integrations/events` 当前定位为应用内事件总线与声明式事件挂载模块。

当前版本的关键增强在于：

- lifecycle hook 使用真实 `moduleRef`
- handler receiver 优先从容器解析
- 事件处理器与 DI 实例语义保持一致

## 12. Public / Internal 包边界

### 12.1 推荐直接依赖的公共包

推荐业务代码直接依赖以下包：

- `application`
- `adapter/*`
- `binding/*`
- `core/module`
- `core/di`
- `integrations/*`

### 12.2 不建议业务直接依赖的内部包

以下包属于内部基础设施层：

- `core/compiler`
- `core/runtime`
- `core/registry`
- `core/graph`
- `core/errors`
- `core/integration`

不建议业务代码直接依赖这些包，原因如下：

- 这些包更多服务于框架装配与内部协作。
- 小版本内可能优化实现细节，而不对外承诺细粒度兼容。
- 业务通过更高层公共包即可完成绝大多数接入需求。

## 13. 稳定性策略

若将当前版本作为第一版稳定基线，应采用以下稳定性策略：

1. 将公共包视为稳定使用面。
2. 将内部基础设施包视为框架实现面。
3. 保留显式 `Must...` API 的 panic 语义。
4. 非 `Must...` API 尽量通过 `error` 反馈失败。
5. 优先通过实例级 registry、模块化集成与类型化取值能力降低不可预测性。

## 14. 后续演进建议

当前版本已经具备作为第一版稳定基线的结构条件。后续演进建议如下：

- 优先补充文档、示例与回归测试，而非继续扩大设计面。
- 若需支持 MongoDB，应以新的 `integrations/mongodb` 独立设计，而非强行扩展当前 ORM。
- 若需增强调度能力，应在保持轻量模型的前提下明确 cron 语义边界，而不是直接扩大 public API 面。
- 若需继续增强稳定性，应继续减少全局状态依赖，并以 `error` 替代隐式 panic 路径。

## 15. 结论

`lania-g v3` 当前已经形成清晰的核心结构：

- `Application` 负责装配与生命周期
- `Module / DI` 负责实例与依赖管理
- `Registry` 负责声明存储
- `Compiler` 负责编译
- `Runtime` 负责执行
- `Adapter` 负责协议 DSL 与 transport
- `Binding` 负责参数注入
- `Integrations` 负责基础设施接入

在此基础上，当前版本已经可以被视为一套具备明确架构边界与稳定使用面的框架内核。后续工作的重点应当转向文档、示例、测试与兼容性管理，而不是继续大规模改变核心设计。

## 16. 目录结构与读码顺序

### 16.1 顶层结构

仓库根目录的 `go.work` 已挂载当前多 module 目录。常见目录如下：

```text
application/v3           应用装配入口
kernel/v3                内核基础设施
protocol/http/v3         HTTP 协议模块
protocol/grpc/v3         gRPC 协议模块
protocol/graphql/v3      GraphQL 协议模块
protocol/ws/v3           WebSocket 协议模块
protocol/mq/v3           MQ 协议模块
protocol/scheduler/v3    Scheduler 协议模块
integrations/*/v3        各类基础设施集成
docs                     当前文档目录
```

说明：

- `application/v3` 负责创建应用实例并持有 `Runtime`、`Registry`、`ModuleRef`
- `kernel/v3` 负责 `module`、`di`、`compiler`、`registry`、`runtime` 等基础设施
- `protocol/<proto>/v3` 负责 DSL、plugin、transport 与 `binding`
- `integrations/*/v3` 负责 logger、config、orm、otel、swagger、terminus 等外部能力接入

### 16.2 推荐读码顺序

如果你第一次接手仓库，建议按下面顺序阅读：

1. [application.go](../application/v3/application.go)
2. [compile.go](../kernel/v3/compiler/compile.go)
3. [context.go](../kernel/v3/runtime/context.go) 与 [router.go](../kernel/v3/runtime/router.go)
4. [plugin.go](../protocol/http/v3/plugin.go) 与 [dsl.go](../protocol/http/v3/dsl.go)
5. 你实际要使用的 integration，例如 [logger module](../integrations/logger/v3/module.go) 或 [otel module](../integrations/otel/v3/module.go)

### 16.3 排错入口

- 路由不生效：先看协议模块 DSL 是否 `BuildE()` 成功，再看 `CompileDiagnostics()`
- 启动缺能力：先看 `StartupReport()`，确认目标模块和协议模块是否挂载
- 绑定失败：先检查对应协议的 `binding` 子包与 handler 入参类型
- 生命周期未执行：先检查对象是否放在正确的 `imports/providers/controllers/resolvers` 槽位
