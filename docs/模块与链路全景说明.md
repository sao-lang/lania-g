# lania-g 模块与链路全景说明

## 1. 文档目标与架构总览

本文档系统说明 `lania-g` 仓库的工作区模块组成、职责分工、模块间联动方式，以及一条业务声明从"写入 DSL"到"运行期执行"的完整路径。

### 1.1 总体架构心智模型

当前项目最重要的设计思想有三点：

1. **声明与执行分离** — 协议层 DSL 先把路由、服务、事件、AOP 等声明写入 `registry`，编译阶段再把声明转成 runtime 可执行产物
2. **协议差异前移到编译与 transport** — HTTP、GraphQL、gRPC、WS、MQ、Scheduler 各自保留协议语义，但运行期统一复用 `runtime.HandlerContext + Router + BindingRegistry + Pipeline + Executor`
3. **外部能力走 integration** — 认证、日志、ORM、OTel 等能力不直接塞进内核，而是通过 `integrations/*/v3` 以模块化方式装配进应用

主分层如下：

```text
application/v3           应用装配与生命周期
kernel/v3                内核基础设施（模块、DI、编译、运行时、AOP）
protocol/*/v3            协议适配器、DSL、编译插件
integrations/*/v3        外部能力接入与桥接
cmd/                     示例与样板工程
docs/                    文档
```

项目主线链路：

```text
Module -> Application -> Protocol Module / Integrations
  -> Registry -> Compiler -> Runtime -> Adapter Transport -> Handler
```

它不是"按单体应用拆 service"的仓库，而是一个 **Go 多 module 工作区**。根目录主要负责组织工作区和文档；真正对外提供能力的模块分散在各子目录下。

## 2. 工作区模块总览

### 2.1 根目录与工作区

根目录的 [go.work](../go.work) 声明了当前工作区启用的所有模块，包括 `cmd`、`application/v3`、`kernel/v3`、六个协议模块（`protocol/*/v3`）以及全部 integration 模块（`integrations/*/v3`）。根目录不是唯一的发布模块，每个子目录都可以独立演进。

### 2.2 `application/v3`

应用装配入口，负责把"模块树 + registry + runtime + protocol adapter + 生命周期"组装成一个可启动的应用实例。主要职责：

- 创建应用实例，接收显式 `Registry`
- 调用 `ModuleLoader` 加载模块树，创建并持有 `runtime.Runtime`
- 挂载 adapter 与 protocol plugin
- 生成 `CompileDiagnostics()` 和 `StartupReport()`
- 在 `Run()` / `Listen()` 前触发编译与安装，协调生命周期回调

关键文件：`application.go`、`runtime.go`、`lifecycle.go`、`startup_report.go`、`http_mount.go`

一句话理解：不负责协议细节和业务逻辑，负责把所有零件装成一台能启动的机器。

### 2.3 `kernel/v3`

内核基础设施层，提供协议无关的底座能力。

| 子包 | 职责 |
| --- | --- |
| `module` | 定义模块模型（imports/providers/controllers/resolvers/exports），递归加载模块树，组织模块级生命周期 |
| `di` | 依赖注入容器，支持按类型/token 取值、父子容器、request-scope child container |
| `registry` | 存放协议声明、事件声明、AOP 声明等编译输入，区分实例级与全局 Registry |
| `compiler` | 调用各协议 plugin 注册/扫描/编译声明，推导 owner，生成 runtime 可安装产物 |
| `runtime` | 统一运行期上下文、路由匹配、参数绑定、AOP 执行链、handler 调用 |
| `aop` | middleware/guard/pipe/interceptor/filter 定义 |
| `graph` | 依赖图与归属分析；`errors` 内核错误模型；`scanner` 声明扫描辅助；`integration` 注入桥 |

一句话理解：`kernel` 是协议无关的基础设施层，是整套框架最核心的底盘。

### 2.4 `protocol/*/v3`

协议层负责三件事：提供 DSL 写声明、提供 plugin 编译声明、提供 adapter/transport 对外服务。

| 协议 | DSL 入口 | 核心职责 | 特殊点 |
| --- | --- | --- | --- |
| HTTP | `Controller(...).Get/Post/...` | 编译 HTTP 路由、owner、参数计划、AOP 计划；把 HTTP 请求转成统一 `HandlerContext` | 路由形态最复杂，binding 类型最多，生态桥接最多 |
| GraphQL | `Resolver(...).Query/Mutation` | 构建 schema，将 resolver 声明编译为 runtime handler | 按 schema/field/resolver 组织，不按 REST path |
| gRPC | `Service(...).Method/StreamMethod` | 编译 gRPC 方法声明，运行期动态注册 `grpc.ServiceDesc` | 支持 unary/server/client/bidi 四种 streaming 模式 |
| WS | `Gateway(...).On(...)` | 编译消息事件与 gateway 归属 | 长期连接上的事件驱动消息 |
| MQ | `Consumer(...).On(...)` | 统一抽象消费端口、驱动接入与编译安装 | 处理对象是消息而非同步请求 |
| Scheduler | `Job(...).Trigger(...)` | 将定时任务声明编译为调度任务 | 触发来源是时间事件而非网络请求 |

### 2.5 `integrations/*/v3`

integration 层用于接入外部基础设施与横切能力。大多数 integration 通过 `ForRoot(...)` 创建模块，将实例/配置/工厂注册到 DI 容器，并在初始化阶段注册对应 binding 以支持 handler 直接注入。

**基础接入类**：auth（认证/RBAC）、config（配置加载）、logger（日志）、cache（缓存）

**外部客户端与数据访问类**：http/gRPC 客户端、orm（关系型数据库）、mongodb（文档数据库）、es（检索）、minio（对象存储）、kafka（消息队列 + MQ 桥接）

**治理与可观测类**：events（事件总线）、outbox（事务事件发布）、otel（tracing/metrics）、resilience（超时/重试/限流/熔断）、swagger（OpenAPI 文档）、terminus（健康检查）

一句话理解：`integrations` 是把外部能力纳入框架主链路的标准接入面。

### 2.6 `cmd`

样板和演示层，分为 `*-app-demo`（面向业务接入的最小启动路径）和 `*-demo`（高级能力和机制演示）。

### 2.7 `docs`

API 使用说明、架构说明、运行时说明、演进计划与收敛文档、integration 专项接入文档。

## 3. 模块联动与完整主链路

### 3.1 模块间如何联动

#### application ↔ kernel

`application` 依赖 `kernel` 做五件事：用 `module.Loader` 加载模块树，用 `registry` 保存声明，用 `compiler` 编译声明，用 `runtime` 承接请求，用 `di` 提供实例。即 `application` 决定"何时装配、编译、启动"，`kernel` 决定"装配后如何组织、编译后如何执行"。

#### application ↔ protocol

通过 `UseAdapter(...)` 挂载协议 adapter。挂载后 adapter 暴露两类能力：
- **编译期**：提供 protocol plugin，让 compiler 能扫描和编译本协议声明
- **运行期**：提供 transport/server，把外部请求转成 `runtime.HandlerContext`

#### protocol ↔ kernel

连接点有四个：
1. **DSL → registry**：协议 DSL 把声明写入 registry
2. **plugin → compiler**：编译期由 plugin 扫描并编译声明
3. **binding → runtime.BindingRegistry**：协议自带 binding 类型与 resolver
4. **transport → runtime.Executor**：请求最终交给 runtime 统一执行

这也是"协议差异前移、运行期统一"的具体落点。

#### integrations ↔ kernel

连接点有三个：向 `module` 输出 provider 和导出项，向 `di` 注册实例和工厂，向 `registry/runtime binding` 注册注入包装类型。接入后 handler 可直接注入 `InjectLogger`、`InjectDatabase` 等，无需手工拼装。

有些 integration 会进一步桥接到应用或协议层，例如 `otel` 需要与启动和请求链路对接，`swagger` 需要读取 HTTP 路由声明，`terminus` 需要暴露健康检查端点，`auth` 需要与 binding 和 AOP 配合。

#### cmd ↔ 其他模块

`cmd` 的职责是消费不是定义。最小样板通常：创建业务对象 → 创建 root module → 创建 adapter → 创建 application → 写 DSL 声明 → 调用诊断或启动。

### 3.2 完整主链路（协议无关总链路）

所有协议复用同一套八步骨架。

**第一步：创建模块树**。用 `module.CreateModule(...)` 定义根模块，放入 imports/providers/controllers/resolvers/exports。这一步是"声明阶段"——只描述模块有哪些依赖、提供了哪些能力和入口，不实际创建任何实例。

```plaintext
LoadMultiple(roots...)
  │
  ├── 阶段一：声明收集（loadModule 递归）
  │     → 深度优先遍历 imports 链
  │     → 收集 providers（按 token 存到 l.providers）
  │     → 收集 controllers（存到 l.controllers）
  │     → 此时全是声明，没有实例
  │
  ├── 阶段二：全局模块注入（prepareGlobalModules）
  │     → IsGlobal=true 的模块自动追加到其他模块的 imports
  │
  ├── 阶段三：依赖图校验（validateGraphs）
  │     → 检测模块 imports 环 + provider 依赖环
  │
  └── 阶段四：模块初始化（rootModule.Init()）
        → 这才是真正干活的地方：
          1. imports 递归 Init
          2. exports 传播（从 import 模块 Get 实例 → RegisterValue 到本模块）
          3. 注册本模块 providers
          4. 注册 controllers/resolvers（按指针类型做 Value provider）
          5. 预实例化非 Request-scope provider + 触发 OnModuleInit
```

**第一步背后的实现——ModuleLoader.LoadMultiple 算法详解**：

当 `Application` 创建时，`newWithOptions()` 内部调用 `loader.LoadMultiple(root)`，这是模块树的第一次实质性构建。完整流程如下：

```text
LoadMultiple(roots...):
  ┌─────────────────────────────────────────────────────┐
  │ 阶段一：声明收集（loadModule 递归）                    │
  │                                                       │
  │  setRootModules(roots):                               │
  │    - 0 roots → 清空                                   │
  │    - 1 root  → rootModule = roots[0]                  │
  │    - >1 root → 创建聚合 root（CreateModule 纯 import）  │
  │                                                       │
  │  对每个 root 递归调用 loadModule(root):                │
  │    1. 检查 modules[mod] 是否已加载（防重复）            │
  │    2. 调用 propagateRegistry 注入 RegistryAware         │
  │    3. 递归加载每个 Import（深度优先，先加载依赖）         │
  │    4. 收集 providers → l.providers[provider.Token]     │
  │    5. 收集 controllers → append(l.controllers)         │
  │                                                       │
  │ 阶段二：全局模块注入（prepareGlobalModules）            │
  │                                                       │
  │  遍历所有已收集模块：                                   │
  │    找出 metadata.IsGlobal == true 的模块               │
  │    将其注入到每个非全局模块的 imports 中（若尚未存在）    │
  │  效果：全局模块 exports 被所有模块可见，无需显式 import  │
  │                                                       │
  │ 阶段三：依赖图校验（validateGraphs）                    │
  │                                                       │
  │  构建 graph.ModuleNodeInput 列表                       │
  │  调用 graph.BuildDiagnostics:                          │
  │    - 检测模块 imports 环（ModuleGraph.DetectCycles）   │
  │    - 检测 provider 依赖环（ProviderGraph.DetectCycles）│
  │  有环 → 返回 KernelError(KindDI)，应用启动失败          │
  │                                                       │
  │ 阶段四：模块初始化（rootModule.Init）                   │
  │                                                       │
  │  BaseModule.Init():                                    │
  │    1. 递归初始化所有 Import 模块                        │
  │    2. 将 imports 的 exports 解析为实例                  │
  │       并 RegisterValue 到当前模块容器（实例转抄）       │
  │    3. 注册本模块 providers                              │
  │    4. 注册 controllers/resolvers 到容器（按类型）       │
  │    5. 预实例化所有非 Request-scope provider             │
  │       对实现 OnModuleInit 的触发回调                    │
  │    6. 标记 initialized = true                          │
  └─────────────────────────────────────────────────────┘
```

其中关键的 import/export 传播机制在 `BaseModule.Init()` 中：

```text
对每个 Import 模块 imp:
  1. imp.Init() — 递归初始化（先初始化被依赖的模块）
  2. 对 imp 的 exports 列表中的每个 token：
     a. 从 imp.Container().Get(token) 获取实例
     b. 注册到本模块容器: m.container.RegisterValue(token, instance)
        （实现"导入可用"语义——当前模块的 provider 可直接注入这些实例）
```

这套机制保证了模块的初始化顺序严格按照依赖关系执行（被依赖的模块先初始化），且每个模块都能访问到其 import 模块导出的能力。

**第二步：创建 Application**。`application.NewWithOptions(root, opts, adapter)` 校验 registry、加载模块树、构建 runtime、挂载 adapter 和 plugin。

**第三步：DSL 写声明到 Registry**。此时还没启动服务。例如 HTTP 的 `Controller().Get()`、GraphQL 的 `Resolver().Query()`、gRPC 的 `Service().Method()` 等，本质都是把声明写入 registry，等待编译。

**第四步：编译**。触发于 `CompileDiagnostics()` / `Run()` / `Listen()`：

1. 各 protocol plugin 执行 `Register`（注册默认 binding）

2. 执行 `Scan`（扫描声明，推导 owner/模块归属）

```plaintext
Plugin.Compile() 内部
  │
  ├── 对每个 routeOwnership，调用 compile(owned)
  │     ├── 编译出 Handler、routeKey
  │     └── 保留 owned.moduleContainer  ← 来自 Scanner 阶段确定的 owner.Container
  │
  └── CompileRouteSet(ownerships, compile, conflict)
        ├── routes[routeKey] = compiled.Handler
        └── routeContainers[routeKey] = compiled.Container  ← 这里！
```

3. 执行 `Compile`（生成 routes/matchers/handler plans/route containers）

```plaintext
HTTP Plugin.Scan():
  ScanResolvedRegistryItems(..., func(def, own, token) *routeOwnership {
    return &routeOwnership{
      moduleContainer: own.Container,  ← 模块归属解析出来的 DI 容器
      ...
    }
  })

HTTP Plugin.Compile():
  compileRoute(owned, global) → *CompiledRoute{Container: owned.moduleContainer}

```

4. 聚合全局产物（BindingRegistry、RouteContainers、全局 AOP、fallback inventory）

5. 检查跨协议 `routeKey` 冲突

**第五步：安装到 Runtime**。`CompiledApp.Install(rt)` 创建新 Router，安装各协议 matcher 和 routes，注入 BindingRegistry 和 RouteContainers，同步全局 AOP。

**第六步：执行生命周期**。应用启动前后遍历模块和 provider，触发生命周期接口（integration 初始化、事件总线挂接、bridge 安装等）。

生命周期的执行分为两个阶段：

**阶段 A：模块级生命周期（运行于 Module.Init/ Destroy）**
- `OnModuleInit`：每个模块初始化时触发，按模块依赖拓扑顺序执行。在 `BaseModule.Init()` 的第 5 步中，遍历所有非 Request-scope 的已实例化 provider，若实现了 `OnModuleInit` 接口则调用。
- `OnModuleDestroy`：应用关闭或动态卸载模块时触发。执行时先遍历本模块的 provider，再**逆序**销毁 imports（后 import 的模块先销毁）。

**阶段 B：应用级生命周期（运行于 Application.bootstrapLifecycle/ shutdownLifecycle）**
- `OnApplicationBootstrap`：应用所有编译和适配器启动完成后触发，按模块拓扑排序**正序**执行。
- `OnApplicationShutdown`：应用关闭时触发，按模块拓扑排序**逆序**执行。

应用级生命周期的执行引擎是 `forEachModulesLifecycle()`，其完整算法为：

```text
forEachModulesLifecycle(modules, reverse, visit):
  1. 遍历所有模块，构建 graph.ModuleNodeInput 列表
     （每个模块的 Type 及其 Import 的 Types）
  2. 调用 graph.NewModuleGraph(nodes).TopologicalSort()
     → 得到稳定的模块拓扑顺序（依赖项先于依赖者）
  3. 若 reverse == true，反转 order（shutdown 时逆序）
  4. 按 order 遍历每个模块：
     a. 获取模块的 container
     b. 遍历 container.GetAll() 中所有 provider
     c. 跳过 Request-scope 的 provider
     d. 对每个非 Request-scope 实例：
        - 若实现了 SetRegistry → 注入应用的 registry
        - 若实现了 SetModuleRef → 注入 moduleRef
        - 调用 visit(instance)（检查是否实现生命周期接口并调用）
```

关键设计点：
- **拓扑排序保障顺序**：`OnApplicationBootstrap` 按正序执行，保证依赖模块先初始化；`OnApplicationShutdown` 逆序执行，保证依赖者先关闭
- **Request-scope 跳过**：请求级别的 provider 没有稳定的应用级生命周期，不参与 bootstrap/shutdown
- **registry/moduleRef 注入**：生命周期执行前补齐上下文，让感知型 integration（如 events、swagger）能拿到当前应用实例的 registry
- **HotLoad 原子性**：热加载新模块时，仅对新模块子树执行 `OnApplicationBootstrap`，保证不影响已运行模块的状态

**第七步：对外监听或运行**。`Listen(addr)` 用于 HTTP/GraphQL/WS 共享监听；`Run()` 用于 gRPC/MQ/Scheduler 等由 adapter 自己控制地址的场景。

**第八步：请求进入 runtime 统一执行**。请求期统一骨架为：

```text
client request
  -> adapter transport
  -> runtime.HandlerContext
  -> runtime.Router.Match
  -> runtime.Executor
  -> BindingRegistry / DI
  -> AOP Pipeline
  -> invoke handler
  -> adapter write response
```

这是整套框架实现"多协议统一执行"的核心。

## 4. 六协议与横切链路详解

### 4.1 六协议链路

#### HTTP 链路

1. 业务通过 `httpAdapter.API().Controller(...)` 声明 controller 和 routes，写入 Registry
2. HTTP plugin 在编译期扫描路由、controller owner、参数计划、AOP 计划
3. 编译得到 `routeKey → handler`、模板路由 matcher、route 对应 module container
4. `Listen(":8080")` 启动服务，`ServeHTTP` 收到请求后构造 `HandlerContext` 进入 runtime
5. runtime 执行 handler，结果由 adapter 写回响应

特点：路由匹配最典型，参数绑定种类最丰富，Swagger/Auth/OTel/Terminus 桥接最常见。

#### GraphQL 链路

1. 通过 `gqlAdapter.API().Resolver(...)` 声明 Query/Mutation/Resolver
2. GraphQL plugin 在编译期构建 schema 与 field handler 映射
3. adapter 解析 operation/field/args，进入 runtime 执行 field 对应 handler
4. 返回值序列化为 GraphQL response

特点：schema 是编译关键产物，请求按 operation/field 分发而非 REST path。

#### WebSocket 链路

1. 通过 `wsAdapter.API().Gateway(...)` 声明 gateway 和事件 handler
2. WS plugin 编译 gateway 归属和 event 映射
3. 连接建立后事件消息进入 adapter，组装 `HandlerContext` 进入 runtime
4. adapter 把结果回写给对应连接

特点：连接是长生命周期对象，一条连接上反复触发多次事件。

#### gRPC 链路

1. 通过 `grpcAdapter.API().Service(...)` 声明 service 和 method，声明期固定 RPCMode
2. gRPC plugin 扫描 service/method/owner，编译生成 runtime handler 与 `grpc.ServiceDesc`
3. adapter 启动 gRPC server，动态注册 service
4. 请求进入后：unary 把 request message 作为主请求对象，streaming 把 `grpc.ServerStream` 放入 `Request.Raw`
5. binding 层为 handler 注入 `Req[T]`、`ServerStream[T]`、`ClientStream[T]`、`BidiStream[Req, Resp]` 等
6. runtime 执行 handler，adapter 桥接回 gRPC 协议语义

特点：四种调用模式已纳入统一执行链，流语义由 binding 和 transport 吸收。

#### MQ 链路

1. 业务声明消息消费端口和 handler，写入 Registry
2. MQ plugin 编译消费 handler 和驱动映射
3. `integrations/kafka` 等桥接消息系统，消费端收到消息后构造 `HandlerContext`
4. runtime 执行 handler，驱动决定 ack/重试/后续处理

特点：触发源是消息中间件而非同步请求，无传统响应体。

#### Scheduler 链路

1. 业务声明 job 和调度规则，写入 Registry
2. Scheduler plugin 编译 job handler 和触发计划
3. 每次时间触发时构造 `HandlerContext`，runtime 执行
4. 执行结果用于记录状态/错误/后续调度决策

特点：触发条件是时间计划，无真实网络请求，无外部回包。

### 4.2 横切链路

#### Binding 与 DI

参数来源有两类：协议绑定值（HTTP query/path param/header/body、GraphQL args、gRPC request 等）和容器实例（logger/db/cache/client/service）。这是协议层和 integration 层发生实际汇合的地方。

执行时 `Executor` 解析参数的顺序：先问 `BindingRegistry` 有无对应 wrapper/resolver，没命中再回退到 DI 容器 `ctx.Container.Get(paramType)`。

#### AOP

统一由 pipeline 承载，语义顺序为 `middleware → guard → input pipe → interceptor → handler → output pipe → filter`。典型能力包括鉴权、参数校验、统一异常处理、tracing/logging、超时重试。

#### Events

事件总线桥。`events.ForRoot(...)` 注册 Bus/Emitter/Factory，通过 `RegisterOn/RegisterHandlers` 写入事件声明，启动阶段 `AttachRegisteredHandlers` 将声明挂到 Bus。业务通过 Emitter 发事件，总线分发给对应 handler。

#### Outbox

连接数据库事务和事件投递。业务在事务中写 outbox 记录，dispatcher 读取待投递事件通过 events 总线或外部系统投递，成功后更新状态，失败走重试或死信。

#### OTel

tracing/metrics/propagation/日志字段桥接。`otel.ForRoot(...)` 创建 telemetry 模块，在应用链路中安装 bridge，协议请求进入时创建或续接 trace context。

#### Auth

`auth.ForRoot(...)` 创建 auth service，注册 JWT/Session/API Key/RBAC 等能力。协议请求进入时由 guard 或 binding 解析认证信息，handler 直接获取认证相关参数。

#### Resilience

提供超时/重试/熔断/限流/幂等治理策略。典型落点：作为 AOP 或外围执行策略，或作为下游调用前的保护层。

#### Swagger

HTTP DSL 写路由声明后，编译或 bridge 阶段读取 HTTP registry 构建 OpenAPI 文档，通过 HTTP bridge 暴露 Swagger UI 或文档 JSON。

#### Terminus

`terminus.ForRoot(...)` 注册健康检查服务，聚合检查项，通过 HTTP bridge 暴露 `/health` 等端点。

#### Kafka 双重角色

Kafka 在当前仓库中既是 integration（提供 client/reader/writer factory），也是 MQ 桥接（连接 `protocol/mq` 的消费模型）。

#### 兼容与 fallback 链路

当前仍保留一部分显式 compat/fallback 路径（如 `application.NewCompat`、`compiler.CompileCompat`、`events.AttachRegisteredHandlersCompat` 等），用于兼容历史使用方式。当前设计倾向是普通入口要求显式传入实例级 Registry，只有 `Compat` helper 才继续使用全局 fallback。这些 fallback 已显式建账到 inventory 中。

## 5. DI 容器系统

### 5.1 容器的树状结构

当前项目的 DI 不是"只有一个全局大容器"，而是一棵树：

```text
Root Container（进程级，持有所有 Singleton 缓存）
  ├── Route Container A（模块 A 的 provider）
  │     └── Request Child（请求 A1，持有 Request-scope 缓存）
  │     └── Request Child（请求 A2）
  └── Route Container B（模块 B 的 provider）
        └── Request Child（请求 B1）
```

- **Root Container**：应用启动时由 ModuleLoader 构建，持有所有模块注册的 provider 定义，Singleton 实例缓存在此
- **Route Container**：每个模块拥有自己的容器，路由级独有 provider 注册在这里
- **Request Child Container**：每次请求从 route container（或 root）派生，Request-scope 实例缓存在此，请求结束后被 GC 回收

查找语义：Child 查找 token 时，如果自身没有 provider 定义，沿 parent 链向上回溯到父容器再到根容器。

### 5.2 三级 Scope

| Scope | 缓存位置 | 适用场景 |
| --- | --- | --- |
| Singleton | 定义该 provider 的容器 | 无状态服务（Logger、Config）、线程安全客户端（DB 连接池） |
| Request | 请求级 child container | 请求上下文（当前用户、请求 ID）、非线程安全对象 |
| Transient | 不缓存，每次重新创建 | 轻量 VO、DTO |

### 5.3 Provider 的四种类型

- **Value provider**：直接返回常量值，用于注册已创建好的实例
- **Factory provider**：通过工厂函数创建实例，可配合 Scope 做缓存
- **Class provider**：通过反射构造 struct，支持构造函数注入优先，否则走 `reflect.New + Injectable.Inject`
- **Existing provider**：别名转发，解析 token A 时实际解析 token B 的实例

```plaintext
providers map:
  │
  ├─ token = "*UserService"  →  Provider{
  │      Type:        Class,
  │      UseClass:    UserService,    // 要反射构造的 struct 类型
  │      Scope:       Singleton,
  │   }
  │
  ├─ token = "*sql.DB"  →  Provider{
  │      Type:        Value,
  │      UseValue:    &sql.DB{...},   // 已创建好的实例，直接返回
  │      Scope:       Singleton,
  │   }
  │
  ├─ token = "*redis.Client"  →  Provider{
  │      Type:        Factory,
  │      UseFactory:  func() (interface{}, error) { return NewClient(), nil },
  │      Scope:       Singleton,
  │   }
  │
  └─ token = "MyService"  →  Provider{
         Type:        Existing,
         UseExisting: "*UserService",  // 别名，实际解析 *UserService
         Scope:       Singleton,
      }
```

```plaintext
Get(token)
  │
  └─ get(token, resolving={}, requester=self)
       │
       │  ─── 阶段一：找 provider 定义 ───
       │
       ├─ c.providers[token] 存在吗？
       │   ├─ 存在 → 取 provider
       │   └─ 不存在 → c.parent.get(token) 向上回溯（直到 Root Container）
       │      仍不存在 → 返回 ErrProviderNotFound
       │
       │  ─── 阶段二：查缓存 ───
       │
       ├─ cacheContainer = cacheContainerFor(provider.Scope, requester)
       │     Singleton → 返回 "定义该 provider 的容器"（即当前 c）
       │     Request   → 返回 requester（请求级 child）
       │     Transient → 返回 nil（不缓存）
       │
       ├─ cacheContainer 非 nil，且 instances[token] 已缓存？
       │   └─ 是 → 直接返回缓存实例（O(1)）
       │
       │  ─── 阶段三：循环检测 ───
       │
       ├─ resolving[token] == true？
       │   └─ 是 → 返回 ErrCircularDependency
       ├─ resolving[token] = true
       │
       │  ─── 阶段四：按 Type 创建实例 ───
       │
       ├─ createInstance(provider, resolving, requester)
       │    │
       │    │  根据 provider.Type 分流：
       │    │
       │    ├── Type == Value ─────────────────────────────
       │    │     return provider.UseValue
       │    │     // ↑ 直接返回已创建好的实例，不反射、不构造
       │    │
       │    ├── Type == Factory ───────────────────────────
       │    │     return provider.UseFactory()
       │    │     // ↑ 调用注册时传入的工厂函数
       │    │     //   工厂内部可以是任何逻辑：NewClient()、连接池等
       │    │
       │    ├── Type == Existing ──────────────────────────
       │    │     // 别名转发：
       │    │     return c.get(provider.UseExisting, resolving, requester)
       │    │     // ↑ 递归 Get()，实际解析 UseExisting 指向的 token
       │    │     //   例如 Existing("MyService") → "*UserService"
       │    │
       │    └── Type == Class ─────────────────────────────
       │          return c.construct(provider.UseClass, resolving, requester)
       │          // ↑ 这是最复杂的路径：
       │          //
       │          //   construct(UseClass=UserService):
       │          //    1. 优先 ConstructorFinder？
       │          //       → 找到 NewUserService(db, cache, logger)
       │          //       → callConstructor(NewUserService)
       │          //           → 对每个参数递归 c.get(paramType)
       │          //           → reflect.Call([db, cache, logger])
       │          //           → 返回 *UserService
       │          //
       │          //    2. 没有 ConstructorFinder？
       │          //       → reflect.New(UserService) → *UserService
       │          //       → 检查是否实现 Injectable
       │          //         → 是：instance.Inject(container)
       │          //       → injectFields（当前为空钩子）
       │          //       → 返回 *UserService
       │
       │  ─── 阶段五：写缓存 ───
       │
       └─ cacheContainer 非 nil 且 Transient？
           └─ 是 → cacheContainer.instances[token] = instance
         （Transient 不写缓存，直接返回）
```

### 5.4 构造函数注入

当模块设置了 ConstructorFinder 后，框架优先使用构造函数创建实例。流程：框架收到创建 `*UserService` 的请求 → ConstructorFinder 找到 `NewUserService(db, cache, logger)` → 对每个参数递归 `Container.Get()` 解析依赖 → 用解析到的参数调用构造函数返回实例。

### 5.5 模块初始化时容器的装配顺序

`Module.Init()` 的顺序：

1. **递归初始化 imports**：先初始化被导入的模块
2. **提取 exports 并注册**：从 import 模块的 exports 取出实例，`RegisterValue` 到当前模块容器（实例转抄，非共享引用）
3. **注册本模块 providers**
4. **注册 controllers/resolvers** 作为 value
5. **预实例化非 Request-scope** provider（提前发现依赖缺失）
6. **触发生命周期**回调

### 5.6 `imports` / `exports` / `Reexport`

`exports` 支持直接导出指定 token 或 `ModuleReexport`。`Reexport(module, tokens...)` 只透出指定 token，`Reexport(module)` 递归展开对方全部 exports。本质是让模块对外暴露能力面可控。

### 5.7 全局模块

`IsGlobal` 模块的实现方式：`ModuleLoader` 在加载图时把全局模块追加到其他模块的 `imports`，仍遵守普通模块模型。

### 5.8 `ModuleRef` 的角色

`ModuleRef` 是"应用模块树的只读索引视图"，提供 root container、模块树访问、`reflect.Type → Module` 索引。注意 request-scope 解析不应直接用 `ModuleRef` 的 root container。

### 5.9 请求期的容器选择

`Executor.Execute()` 中容器选择优先级：
1. `ctx.Container` 已被外部设置（如测试 mock）→ 直接使用
2. 查 `routeContainers[handler.Meta.RouteKey]` → 存在则从此容器派生 child
3. 否则从 `rootContainer` 派生 child

### 5.9a 三层容器详解：以一次 HTTP 请求为例

以下用一次 HTTP `GET /users/42` 请求，完整展示 Root Container、Route Container、Request Child Container 三层的存放内容与协作过程。

#### 场景设定

假设应用有两个模块：

```text
RootModule（根模块）
  imports: [UserModule, CommonModule]

UserModule（用户模块）
  providers:
    - *UserService      (Singleton)  ← 共享实例
    - *UserController   (Singleton)  ← controller 实例
  controllers:
    - *UserController

CommonModule（公共模块，IsGlobal=true）
  providers:
    - *Logger           (Singleton)  ← 全局共享实例
    - *Config           (Singleton)  ← 全局配置
  exports:
    - *Logger
    - *Config
```

#### 启动期：三层的构建

```text
Application.NewWithOptions(rootModule, opts, httpAdapter)
  │
  ├── ModuleLoader.LoadMultiple(rootModule)
  │     │
  │     ├── loadModule(RootModule)
  │     │     ├── loadModule(CommonModule)  // 深度优先，先加载
  │     │     │     └── CommonModule.Init()
  │     │     │           → 创建 *Logger 实例 → 缓存到 CommonModule 的 container
  │     │     │           → 创建 *Config 实例 → 缓存到 CommonModule 的 container
  │     │     │           → CommonModule Container: {*Logger, *Config}
  │     │     │
  │     │     ├── loadModule(UserModule)
  │     │     │     └── UserModule.Init()
  │     │     │           → 从 CommonModule 的 exports 复制 *Logger、*Config
  │     │     │             RegisterValue(userContainer, *Logger)
  │     │     │             RegisterValue(userContainer, *Config)
  │     │     │           → 注册 *UserService provider（Singleton）
  │     │     │           → 预实例化 *UserService → 缓存到 userContainer
  │     │     │           → 注册 *UserController（Value provider）
  │     │     │           → UserModule Container（Route Container）:
  │     │     │               {*Logger, *Config, *UserService, *UserController}
  │     │     │
  │     │     └── RootModule.Init()
  │     │           → 从 UserModule exports 复制 *UserService、*UserController
  │     │           → 从 CommonModule exports 复制 *Logger、*Config
  │     │           → RootModule Container（Root Container）:
  │     │               {*Logger, *Config, *UserService, *UserController}
  │     │
  │     └── prepareGlobalModules()
  │           → CommonModule 是 IsGlobal，自动注入 UserModule 的 imports
  │
  ├── compiler.Compile(moduleRef, reg, plugins...)
  │     └── HTTP plugin Scan → routeOwnership
  │           → routeKey "GET /users/:id"
  │           → controllerToken = *UserController
  │           → moduleContainer = UserModule 的 container（Route Container）
  │
  ├── CompiledApp.Install(rt)
  │     ├── routeContainers["GET /users/:id"] = UserModule 的 container
  │     └── executor.SetRouteContainers(routeContainers)
  │           ↑ 这就是运行时用的 routeContainers 映射
  │
  └── adapter.Start()
        → http.Server.Serve(listener)
```

**此时三层容器已全部就绪：**

```text
Root Container（RootModule 的容器）
  持有 provider 定义:
    *Logger       → Singleton 实例 (logger)
    *Config       → Singleton 实例 (config)
    *UserService  → Singleton 实例 (userSvc)
    *UserController→ Singleton 实例 (ctrl)
  │
  ├── Route Container A（UserModule 的容器）
  │   持有 provider 定义:
  │     *Logger       → Singleton 实例 (logger)  ← 从 CommonModule exports 复制
  │     *Config       → Singleton 实例 (config)  ← 从 CommonModule exports 复制
  │     *UserService  → Singleton 实例 (userSvc) ← 本模块注册
  │     *UserController→ Singleton 实例 (ctrl)   ← 本模块注册
  │
  └── Route Container B（其他模块...）
```

**关键理解**：Root Container 和 Route Container 中的 Singleton 实例**是同一份**（通过 exports 复制的是实例指针，不是克隆）。`*UserService` 在 UserModule 中创建后，通过 `RegisterValue` 复制到 Root Container 和当前模块容器——但在 `cacheContainerFor(Singleton)` 逻辑中，Singleton 的缓存始终落在"定义该 provider 的容器"上，因此查找时 parent 链回溯最终会命中创建它的容器。

#### 如果 handler 使用了 Request-scope provider 会怎样？

假设 `UserController` 中需要注入请求级上下文 `CurrentUser`：

```go
type UserController struct {
    UserService  *UserService    // Singleton
    CurrentUser  *CurrentUser    // Request（请求级，每次请求不同）
}

// 或者作为 handler 方法参数：
func (c *UserController) GetByID(id Param[string], currentUser *CurrentUser) (*User, error) {
    // currentUser 是请求级注入的
}
```

```text
resolveArguments 时解析 *CurrentUser：
  → BindingRegistry.Find(*CurrentUser) → 命中（有 container binding）
  → Resolve: ctx.Container.Get(*CurrentUser)

Request Child Container.Get(*CurrentUser):
  1. child.providers["*CurrentUser"] → 不存在
  2. Route Ctnr A.providers["*CurrentUser"] → 存在！
     Scope = Request（注意不是 Singleton）
     cacheContainerFor(Request) = requester = Request Child Container
  3. Request Child Container.instances["*CurrentUser"] → 不存在（首次请求）
  4. 创建新实例 currentUserA
  5. 缓存到 Request Child Container.instances["*CurrentUser"] = currentUserA
  6. 返回 currentUserA

下一次请求 GET /users/43：
  → 创建新的 Request Child Container（与上次隔离）
  → 解析 *CurrentUser → 未缓存 → 创建 currentUserB
  → 两个请求的 Request-scope 实例互不干扰
  → 请求结束后 Request Child Container 被 GC 回收
```

#### 三个容器各自存放什么 —— 总结

| 容器层级 | 何时创建 | 存放内容 | 生命周期 |
| --- | --- | --- | --- |
| **Root Container** | 应用启动时 `ModuleLoader.LoadMultiple` | 所有模块的 provider 定义（按 token 索引）；Singleton 实例（实际缓存分布在"定义该 provider 的模块容器"上） | 进程级，应用关闭时释放 |
| **Route Container** | 模块初始化 `BaseModule.Init()` | 该模块的 provider 定义；从 imports 复制的 export 实例（`RegisterValue`）；该模块注册的 Singleton 实例缓存 | 进程级，模块卸载时销毁（HotLoad） |
| **Request Child Container** | 每次请求 `Executor.Execute()` | 空的 providers（继承 parent 的查找链）；Request-scope 实例缓存（如 `CurrentUser`、请求 ID） | 单次请求，请求结束后被 GC |

#### 容器查找路径的可视化

```text
Request Child Container.Get(token)
  │
  ├─ child.providers[token] 存在吗？
  │   ├─ 存在 → 按 scope 决定缓存位置，创建/返回实例
  │   └─ 不存在 → 向 parent 回溯
  │
  ├─ Route Container.providers[token] 存在吗？
  │   ├─ 存在 → 按 scope 决定缓存位置
  │   │     Singleton → 缓存在 Route Container
  │   │     Request   → 缓存在 Request Child Container
  │   │     Transient → 不缓存，每次新建
  │   └─ 不存在 → 继续向 parent 回溯
  │
  └─ Root Container.providers[token] 存在吗？
      ├─ 存在 → 同上
      └─ 不存在 → 返回 ErrProviderNotFound
```

注意：Root Container 没有 parent，查找链至此终止。

#### 容器选择策略的代码路径

```go
// Executor.Execute 中的容器选择逻辑（executor.go:68-73）
if ctx.Container == nil {
    if container, ok := e.routeContainers[handler.Meta.RouteKey]; ok && container != nil {
        // 情况 2：命中 routeContainers → 从 Route Container 派生 child

    } else if e.rootContainer != nil {
        // 情况 3：未命中 → 从 Root Container 派生 child

    }

```

### 5.10 循环依赖检测

容器使用 `resolving map[token]bool` 记录正在构造的 token。同一个 token 在构造链中再次进入解析即判定为循环依赖并报错。

### 5.11 模块与 DI 的当前取舍

这套实现的风格：不追求重容器特性，优先把模块边界和请求期隔离做清楚。模块显式声明、容器显式注册、生命周期显式触发。这也是框架可预测性较强的原因之一。

### 5.12 模块树的构建与加载算法详解

#### 5.12.1 ModuleLoader 的整体架构

`ModuleLoader`（`kernel/v3/module/loader.go`）是模块树构建的核心入口。它负责从 root module 出发，递归收集 modules/imports 关系、providers/controllers/resolvers 声明，并生成依赖图诊断信息。

核心数据结构：

```go
type ModuleLoader struct {
    modules       map[Module]bool               // 已加载的模块集合（防重复）
    providers     map[interface{}]*di.Provider   // 收集到的所有 provider
    controllers   []interface{}                  // 收集到的所有 controller
    rootModule    Module                         // 根模块
    loadedModules map[reflect.Type]Module         // reflect.Type → Module 索引
    moduleRef     *ModuleRef                     // 运行期只读索引视图
    diagnostics   *graph.Diagnostics             // 依赖图诊断结果
    registry      *registry.Registry             // 声明注册表
}
```

#### 5.12.2 LoadMultiple 四阶段详解

**阶段一：声明收集（`loadModule` 递归）**

```text
loadModule(mod):
  1. 幂等检查：若 modules[mod] 已存在 → 直接返回（避免重复加载同一模块）
  2. 调用 propagateRegistry(mod)：
     - 若 mod 实现了 RegistryAware 接口 → 注入当前应用的 registry
     - 这样模块内部的 DSL/API 可以感知 registry，无需层层手传
  3. 标记 modules[mod] = true
  4. 获取 metadata := mod.Metadata()
  5. 递归加载每个 Import：
     for _, imp := range metadata.Imports {
         loadModule(imp)  // 深度优先，先加载依赖
     }
  6. 收集 providers：
     for _, provider := range metadata.Providers {
         l.providers[provider.Token] = provider
     }
  7. 收集 controllers：
     l.controllers = append(l.controllers, metadata.Controllers...)
```

注意：`loadModule` 是"声明收集"阶段，只记录**声明了哪些** providers 和 controllers，不实际创建任何实例。真正的实例化发生在 `BaseModule.Init()` 阶段。

**阶段二：全局模块注入（`prepareGlobalModules`）**

全局模块（`metadata.IsGlobal == true`）的机制使某些模块的能力对所有模块可见，无需在每个业务模块中显式 import。

```text
prepareGlobalModules():
  遍历 modules 集合中所有模块：
    找出 metadata.IsGlobal == true 的模块列表 → globals
    对每个非全局模块 mod：
      对每个全局模块 global：
        若 mod.Metadata().Imports 中尚未包含 global（按 reflect.Type 比较）：
          mod.Metadata().Imports = append(mod.Metadata().Imports, global)
```

这意味着全局模块的 exports 会被注入到所有模块的 DI 容器中，业务代码无需显式 import 即可使用全局模块导出的能力。

**阶段三：依赖图校验（`validateGraphs`）**

```text
validateGraphs():
  1. 遍历所有已加载模块，构建 graph.ModuleNodeInput 列表
     - 每个输入包含模块的 reflect.Type 和其 imports 的 Types
  2. 调用 graph.BuildDiagnostics(nodes, l.providers)
     - 同时检测模块 imports 环和 provider 依赖环
  3. 若 diagnostics.HasIssues()：
     - 保存 diagnostics（可通过 GetDiagnostics() 查询）
     - 返回 KernelError(KindDI, "module cycle detected: ...")
```

**阶段四：模块初始化（`rootModule.Init()`）**

详见 5.12.3 节。

#### 5.12.3 BaseModule.Init() 的详细实现

```text
BaseModule.Init():
  1. 幂等检查：若 m.initialized == true → 直接返回
  
  2. 递归初始化所有 Import 模块：
     for _, imp := range m.metadata.Imports {
         imp.Init()  // 被依赖的模块先初始化
         
         // 将 import 模块的 exports 解析为实例，注册到当前模块容器
         for _, exportToken := range exportedTokens(imp) {
             impContainer := imp.Container()
             instance, err := impContainer.Get(exportToken)
             if err != nil { continue }  // 跳过无法获取的 export
             m.container.RegisterValue(exportToken, instance)
         }
     }
  
  3. 注册本模块的 providers（将 provider 定义注册到 DI 容器）：
     for _, provider := range m.metadata.Providers {
         m.container.Register(provider)
     }
  
  4. 将 controllers/resolvers 注册到容器（按指针类型注册 value）：
     - 对每个 controller：
       t := reflect.TypeOf(controller)
       if t.Kind() != reflect.Ptr { t = reflect.PointerTo(t) }
       m.container.RegisterValue(t, controller)
     - 对每个 resolver 同理
     - 作用：compiler/runtime 可按类型解析 receiver 的模块归属
  
  5. 预实例化非 Request-scope provider 并触发生命周期：
     providers := m.container.GetAll()
     for token := range providers {
         if provider.Scope == di.Request { continue }  // 跳过请求级
         instance, err := m.container.Get(token)  // 真正创建实例
         if err != nil { continue }
         if initable, ok := instance.(OnModuleInit); ok {
             initable.OnModuleInit()  // 触发生命周期回调
         }
     }
  
  6. 标记 m.initialized = true
```

#### 5.12.4 imports/exports/Reexport 的传播机制

`exports` 支持三种导出方式：

1. **直接导出 token**：`Exports: []interface{}{reflect.TypeOf((*Service)(nil))}`
2. **`Reexport(module, tokens...)`**：只透出指定模块的指定 token
3. **`Reexport(module)`**：递归展开对方全部 exports

`exportedTokens()` 辅助函数递归处理这三种情况：

```text
exportedTokens(mod):
  for _, export := range mod.Metadata().Exports {
    switch e := export.(type) {
    case *ModuleReexport:
      if len(e.Tokens) > 0:
        yield each token in e.Tokens  // 只导出指定 token
      else:
        yield all exportedTokens(e.Module)  // 递归展开全部 exports
    default:
      yield export  // 直接导出
    }
  }
```

#### 5.12.5 模块的 Init/Destroy 生命周期对比

| 操作 | 执行顺序 | 主要行为 |
| --- | --- | --- |
| `Init()` | 正序（imports 先） | 递归初始化 imports → 复制 exports → 注册 providers → 注册 controllers → 预实例化 + OnModuleInit |
| `Destroy()` | 逆序（imports 后） | 遍历 provider 触发 OnModuleDestroy → 逆序 Destroy imports |

#### 5.12.6 ModuleRef 与运行期索引

`ModuleRef`（`kernel/v3/module/moduleref.go`）提供模块树的只读索引视图：

```go
type ModuleRef struct {
    module    Module                    // root module
    container *di.Container             // root container（全局 DI 入口）
    modules   map[reflect.Type]Module   // Type → Module 索引
}
```

主要用途：
- `GetModule(moduleType)`：按类型查找模块实例（先按精确 Type，再退回到 AssignableTo）
- `Get(token)`：从 root container 解析依赖（注意：请求级依赖应由 Executor 创建 child 后解析）
- `GetContainer()`：返回 root container（给 Executor 作为 child 容器的 parent）

索引构建过程在 `NewModuleRef(rootModule)` 中完成，会递归 `collectModules` 遍历整棵模块树。

#### 5.12.7 模块树的构建时序视图

```text
时序关键点：
  Application.NewWithOptions()
    → module.NewModuleLoader()                    // 创建空 loader
    → loader.SetRegistry(reg)                     // 注入 registry
    → loader.LoadMultiple(root)                   // 启动加载
        → setRootModules(roots)                   // 设置根模块
        → loadModule(root)                        // 递归声明收集
            → loadModule(importA)                 // 深度优先
            → loadModule(importB)                 // ...
        → prepareGlobalModules()                  // 全局模块注入
        → validateGraphs()                        // 依赖图校验（含 cycle 检测）
        → rootModule.Init()                       // 真正实例化
            → importA.Init() → importB.Init() → ...  // imports 先初始化
            → 复制 exports → 注册 providers → 实例化 + OnModuleInit
    → runtime.NewRuntime()                        // 创建 runtime
    → app.UseAdapter(adapter)                     // 挂载 adapter
```

### 5.13 依赖图构建与循环检测实现

#### 5.13.1 整体设计

依赖图系统（`kernel/v3/graph/graph.go`）不参与真实的依赖解析，而是给 module loader 提供"启动前图校验"的结构化工具。它维护两张独立的图：

- **ModuleGraph**：模块 imports 之间的依赖图，检测模块循环依赖
- **ProviderGraph**：provider 之间的依赖图，检测 DI 循环依赖

#### 5.13.2 ModuleGraph 的构建

```go
type ModuleGraph struct {
    nodes map[reflect.Type]struct{}           // 所有模块节点
    edges map[reflect.Type][]reflect.Type     // 有向边：A → B 表示 A imports B
}

type ModuleNodeInput struct {
    Type    reflect.Type
    Imports []reflect.Type
}
```

构建过程（`NewModuleGraph`）：

```text
NewModuleGraph(mods []ModuleNodeInput):
  遍历每个输入 mod:
    将 mod.Type 加入 nodes
    遍历 mod.Imports 中的每个 imp:
      在 edges[mod.Type] 中加入 imp（去重后）
```

**注意**：ModuleGraph 的 edges 方向是"模块 → 它的 imports"，而不是"imports → 模块"。这是因为 graph 的内部统一将边视为"依赖方向"，DFS 遍历时沿 edges 走。

#### 5.13.3 ProviderGraph 的构建

```go
type ProviderGraph struct {
    nodes map[string]*di.Provider
    edges map[string][]string
}
```

依赖推导规则（`providerDependencies`）：

```text
providerDependencies(provider):
  情况 1：provider.Deps 不为空 → 使用显式声明的 Deps 作为依赖
  情况 2：provider.Type == Existing → 依赖 UseExisting（别名指向的 token）
  情况 3：provider.Type == Class → 把导出字段类型视为潜在依赖
    - 遍历 struct 的所有导出字段
    - 将每个字段的 Type 加入依赖列表（作为近似诊断，非精确模型）
  情况 4：其他 → 无已知依赖
```

**设计取舍**：Class provider 的依赖推导是"近似诊断模型"，不是运行时真实注入算法的镜像。运行时真实注入通过构造函数参数或字段反射完成，而这里的近似模型只用于检测明显的循环依赖，无法覆盖所有间接依赖路径。

#### 5.13.4 环检测算法（DFS + 三色标记）

两张图共用同一套环检测算法。以 ModuleGraph 为例：

```text
DetectCycles():
  初始化：
    visited = {}   // 已访问节点（灰/黑）
    stack = {}     // 当前递归栈中的节点（灰）
    path = []      // 当前 DFS 路径
    cycles = []    // 检测到的所有环

  对每个节点（按 Type.String() 排序后稳定遍历）：
    if !visited[node]:
      DFS(node)

  DFS(node):
    visited[node] = true          // 标记为灰
    stack[node] = true            // 加入递归栈
    path = append(path, node)

    for _, next := range edges[node]:
      if !visited[next]:
        DFS(next)                 // 未访问 → 递归
        continue
      if stack[next]:
        // 发现环！将当前路径中从 next 开始的部分截取出来
        cycles = append(cycles, extractTypeCycle(path, next))

    stack[node] = false           // 退栈，标记为黑
    path = path[:len(path)-1]     // 回溯

  返回去重后的 cycles
```

**三色标记含义**：
- **白色（不在 visited 中）**：尚未访问
- **灰色（visited 为 true 且 stack 为 true）**：在当前 DFS 路径中，遇到即表示有环
- **黑色（visited 为 true 且 stack 为 false）**：已完全遍历，其所有子节点都已处理

**环提取算法**（`extractTypeCycle`）：

```text
extractTypeCycle(path, start):
  从 path 中找到 start 的位置
  截取从 start 到 path 末尾的部分
  在末尾追加 start 形成闭环展示
  例：path = [A, B, C, D], start = C
    → 截取 [C, D] → 追加 C → [C, D, C]
```

#### 5.13.5 拓扑排序算法

```text
TopologicalSort():
  初始化 temp = {}, perm = {}  // 临时标记和永久标记
  order = []                   // 排序结果

  对每个节点：
    if node not in perm:
      visit(node)

  visit(node):
    if node in temp:
      return circular dependency error  // 有环无法拓扑排序
    if node not in perm:
      temp[node] = true
      for each next in edges[node]:
        visit(next)
      perm[node] = true
      order = append(order, node)  // post-order 追加

  返回 order
```

注意：拓扑排序和环检测都可以检测环，但环检测保留了**所有命中的环**（便于启动诊断输出全部问题），而拓扑排序检测到环就报错返回。

#### 5.13.6 BuildDiagnostics 统一入口

```go
func BuildDiagnostics(mods []ModuleNodeInput, providers map[interface{}]*di.Provider) *Diagnostics {
    d := &Diagnostics{}
    for _, cycle := range NewModuleGraph(mods).DetectCycles() {
        d.ModuleCycles = append(d.ModuleCycles, stringifyTypes(cycle))
    }
    d.ProviderCycles = append(d.ProviderCycles, NewProviderGraph(providers).DetectCycles()...)
    if !d.HasIssues() { return nil }
    return d
}
```

这个函数被 `ModuleLoader.validateGraphs()` 调用，输出结果可通过 `loader.GetDiagnostics()` 或 `app.GraphDiagnostics()` 查询。

### 5.14 生命周期执行链路

#### 5.14.1 生命周期接口体系

框架定义了四个生命周期接口，分布在模块级和应用级两个层面：

| 接口 | 定义位置 | 方法 | 触发时机 | 执行顺序 |
| --- | --- | --- | --- | --- |
| `OnModuleInit` | `kernel/v3/module/module.go` | `OnModuleInit() error` | 模块 `Init()` 时，非 Request-scope provider 实例化后立即触发 | 模块拓扑正序 |
| `OnModuleDestroy` | `kernel/v3/module/module.go` | `OnModuleDestroy() error` | 模块 `Destroy()` 时触发 | 模块内先销毁自身，再逆序销毁 imports |
| `OnApplicationBootstrap` | `kernel/v3/module/module.go` | `OnApplicationBootstrap() error` | 应用全部编译+适配器启动完成后触发 | 模块拓扑正序 |
| `OnApplicationShutdown` | `kernel/v3/module/module.go` | `OnApplicationShutdown() error` | 应用关闭时触发 | 模块拓扑逆序 |

#### 5.14.2 模块级生命周期执行

**OnModuleInit 的触发链路**：

```text
BaseModule.Init() 的第 5 步：
  providers := m.container.GetAll()
  for token := range providers {
      if provider.Scope == di.Request { continue }  // 跳过请求级
      instance, _ := m.container.Get(token)         // 获取或创建实例
      if initable, ok := instance.(OnModuleInit); ok {
          err := initable.OnModuleInit()            // 触发生命周期
          if err != nil { return err }              // 失败则中断初始化
      }
  }
```

关键点：
- 按模块拓扑正序触发（被依赖的模块的 provider 先收到 OnModuleInit）
- Request-scope 的 provider 不参与（没有稳定上下文）
- 错误传播：任一 OnModuleInit 返回 error 会中断整个模块初始化

**OnModuleDestroy 的触发链路**：

```text
BaseModule.Destroy():
  // 1. 先触发本模块的 provider
  for token := range providers {
      if provider.Scope == di.Request { continue }
      instance, _ := m.container.Get(token)
      if destroyable, ok := instance.(OnModuleDestroy); ok {
          destroyable.OnModuleDestroy()  // 尽力而为，不阻止后续销毁
      }
  }
  // 2. 再逆序销毁 imports
  for i := len(m.metadata.Imports) - 1; i >= 0; i-- {
      m.metadata.Imports[i].Destroy()
  }
```

关键点：
- 错误处理偏"尽力而为"：打印错误但不阻止后续销毁
- 逆序销毁：后 import 的模块先销毁（依赖者先关闭，再关依赖的基础设施）

#### 5.14.3 应用级生命周期执行

应用级生命周期由 `Application` 在启动/关闭时触发，定义在 `application/v3/lifecycle.go`。

**bootstrapLifecycle 触发时序**：

```text
Application.Run() / Listen():
  1. ensureCompiled()          → 编译 + 安装路由
  2. adapter.Start()           → 启动各协议服务
  3. bootstrapLifecycle()      → 触发 OnApplicationBootstrap
     ├─ 幂等检查（bootstrapped 标记）
     └─ forEachModuleLifecycle(false, visit)
         ├─ 构建模块拓扑排序
         ├─ 正序遍历（依赖模块先触发）
         └─ 对每个模块的所有非 Request-scope provider：
             ├─ SetRegistry(reg)        → 注入 registry
             ├─ SetModuleRef(moduleRef) → 注入 moduleRef
             └─ 若实现 OnApplicationBootstrap → 调用
```

**shutdownLifecycle 触发时序**：

```text
Application.Stop():
  1. 逆序停止 adapter（后挂载的先停止）
  2. shutdownLifecycle()
     ├─ 检查已 bootstrap
     └─ forEachModuleLifecycle(true, visit)
         ├─ 构建模块拓扑排序
         ├─ 逆序遍历（依赖模块先关闭）
         └─ 对每个模块的所有非 Request-scope provider：
             └─ 若实现 OnApplicationShutdown → 调用
```

**完整的 Application 启动链路**：

```text
NewWithOptions(root, opts, adapters...)
  ├─ NewModuleLoader()
  ├─ loader.LoadMultiple(root)      // 模块树声明收集 + Init
  │    ├─ loadModule(root)          // 递归声明收集
  │    ├─ prepareGlobalModules()    // 全局模块注入
  │    ├─ validateGraphs()          // 依赖图校验（含 cycle 检测）
  │    └─ rootModule.Init()         // 递归 Init + OnModuleInit
  ├─ runtime.NewRuntime()           // 创建运行期
  ├─ UseAdapter(adapter)            // 挂载 adapter（收集 plugins）
  │
  Run() / Listen(addr)
  ├─ ensureCompiled()               // Compile(moduleRef, reg, plugins) → Install
  │    ├─ 各 plugin.Register()      // 注册默认 binding
  │    ├─ 各 plugin.Scan()          // 扫描声明、owner 推导
  │    ├─ 各 plugin.Compile()       // 编译产物、AOP 合并
  │    ├─ 跨协议 routeKey 冲突检测
  │    └─ CompiledApp.Install(rt)   // 安装路由到 runtime
  ├─ adapter.Start()                // 启动各协议服务
  ├─ bootstrapLifecycle()           // 应用级 OnApplicationBootstrap
  │    └─ forEachModuleLifecycle(false) → 正序拓扑 → 触发 bootstrap
  └─ emitStartupReport()            // 输出启动报告
```

#### 5.14.4 HotLoad 时的生命周期处理

当 `Application.HotLoad(mod)` 动态加载新模块时，生命周期需做特殊处理：

```text
HotLoad(mod):
  1. loader.LoadModule(mod)          // 加载新模块（不 Init）
  2. buildCompiledRuntime()          // 重新编译
  3. if 应用已 bootstrap:
     forEachSubtreeLifecycle(mod, false, visit)
       → 仅对新模块子树触发 OnApplicationBootstrap
       → 不影响已运行模块的状态
  4. reloadHotAdapters()             // 通知 adapter 刷新
  5. 若编译或 bootstrap 失败 → 回滚到旧状态
     - unloadModule(mod)
     - restoreState(previous)
```

#### 5.14.5 生命周期接口的实现约定

integration 中实现生命周期接口的典型模式：

```go
type MyIntegration struct {
    client  *SomeClient
    started bool
}

func (m *MyIntegration) OnModuleInit() error {
    // 初始化连接池、创建客户端、注册 binding 等
    client, err := NewClient()
    m.client = client
    return err
}

func (m *MyIntegration) OnApplicationBootstrap() error {
    // 在应用完全启动后执行（此时所有模块已初始化、路由已安装）
    // 适合做：订阅消息、启动后台协程、注册健康检查、挂载 HTTP bridge
    m.started = true
    return m.client.Subscribe("topic")
}

func (m *MyIntegration) OnApplicationShutdown() error {
    // 应用关闭时清理资源
    m.started = false
    return m.client.Close()
}

func (m *MyIntegration) OnModuleDestroy() error {
    // 模块卸载时清理（比 OnApplicationShutdown 更早触发）
    return nil
}
```

#### 5.14.6 生命周期执行的关键设计原则

1. **拓扑排序保障顺序**：所有应用级生命周期执行都经过 `graph.ModuleGraph.TopologicalSort()` 排序，保证模块间依赖关系在任何生命周期阶段都得到尊重
2. **Request-scope 排除**：请求级别的 provider 没有稳定的生命周期，不参与任何生命周期回调
3. **上下文注入**：生命周期执行前通过 `SetRegistry`/`SetModuleRef` 补齐 integration 所需的依赖，让它们能感知当前应用
4. **HotLoad 原子性**：新模块的回调失败会导致完整回滚，不会让应用卡在中间态
5. **幂等性**：`bootstrapLifecycle()` 有 `bootstrapped` 标记防重复执行

## 6. 编译期扫描、Owner 推导与安装

### 6.1 Snapshot

编译器不会直接对运行中的模块树做随手读取，而是先构建只读视图 `snapshot`，收集 Modules/Providers/Controllers/Resolvers/ModuleOwners/ControllerOwners/ResolverOwners。作用是冻结当前模块树状态，避免编译期到处碰运行时对象结构。

### 6.2 Owner 索引与解析

在 snapshot 之上建立 `SnapshotOwnerIndex`，维护两类索引：
- `OwnerByType map[reflect.Type][]ModuleOwner` — 类型 → 候选 owner 列表
- `OwnerByPointer map[uintptr]ModuleOwner` — 实例指针 → 精确 owner

解析规则：
1. 先按类型查 `OwnerByType`
2. 无候选 → `Missing`；唯一候选 → `Resolved`
3. 多个候选时用实例指针去 `OwnerByPointer` 消歧
4. 仍无法唯一确定 → `Ambiguous`

### 6.3 编译期主流程

1. protocol plugins 稳定排序
2. 每个 plugin 执行 `Register(reg)`（补默认 binding 或声明）
3. 冻结 `BindingRegistry`
4. 汇总全局 AOP、声明数量等诊断输入
5. 每个 plugin 依次执行 `Scan` → `Compile`
6. 汇总成 `CompiledApp`
7. 检查跨协议 `routeKey` 冲突
8. 生成 diagnostics 与 fallback inventory

### 6.4 各协议 owner 扫描差异

| 协议 | owner 来源 |
| --- | --- |
| HTTP | 只认 controller |
| GraphQL | controller + resolver |
| WS | controller + resolver |
| gRPC | controller + resolver + provider |
| MQ | controller + resolver + provider |
| Scheduler | controller + resolver + provider |

### 6.5 编译产物

每个协议编译后得到 `CompiledProtocol`，核心产物：
- `Routes`：`routeKey → handler`
- `RouteContainers`：`routeKey → module container`

单个 handler 的元数据固化：RouteKey、Protocol、ModuleKey、ParamPlans、CompiledAOP 及协议专属元数据（如 HTTP 的状态码/header/render/redirect）。

### 6.6 `routeContainers` 的作用

路由级模块容器选择表。plugin 编译声明时记录 `owner.container`，编译器汇总为 `map[string]*di.Container`（routeKey → container）。

### 6.7 `CompiledApp.Install()` 安装步骤

1. 创建新 Router
2. 按协议顺序安装 matcher / routes
3. 把 `BindingRegistry` 注入 `Executor`
4. 把 `RouteContainers` 注入 `Executor`
5. 把全局 AOP 同步到 runtime

路由和 matcher 是编译期产物，不是运行时临时解释；runtime 安装用的是"新 Router"，不是边跑边拼接。

### 6.8 Fallback Inventory

编译器显式维护 fallback inventory 记录兼容路径：

**Runtime fallback**：`runtime_global_aop`、`binding_to_di`、`route_to_root_container`

**Registry/read fallback**：`application_global_compat`、`compile_registry_global_compat`、`graphql_schema_global_read`、`events_attach_global_read`、`swagger_http_registry_global_read`

这套 inventory 让 compat 行为显式可见，让后续收敛有明确治理对象。

### 6.9 编译器当前的设计取舍

用统一外壳收敛协议差异，把 owner/binding/route container/AOP 计划尽量前置到编译期，让 runtime 只消费产物不重复推导。仍保留少量 fallback 以兼容历史路径。

### 6.10 编译期详细链路

编译期的完整执行链路从 `compiler.Compile()` 入口开始，到 `CompiledApp.Install()` 安装到 Runtime 结束。整体分为 **七个子阶段**：

#### 6.10.1 Snapshot 构建详解

Snapshot 是 Scanner 构建的只读模块视图（`kernel/v3/scanner/scanner.go`）。它的核心数据结构和构建过程：

```text
Snapshot 的数据结构：
  Modules:          []module.Module          — 所有已加载模块
  Providers:        map[token]*di.Provider   — 所有 provider 定义
  Controllers:      []interface{}            — 所有 controller 实例
  Resolvers:        []interface{}            — 所有 resolver 实例
  ModuleOwners:     map[type]ModuleOwner     — 模块类型 → 模块 owner
  ControllerOwners: map[type][]ModuleOwner   — controller 类型 → 候选 owners
  ResolverOwners:   map[type][]ModuleOwner   — resolver 类型 → 候选 owners

构建过程（BuildSnapshot）：
  1. 遍历 moduleRef.GetAllModulesWithTypes()
     → 对每个模块 mod（类型为 moduleType）：
       a. 创建 ModuleOwner{ModuleKey, ModuleType, Container}
       b. 遍历 meta.Providers → 存入 s.Providers
       c. 遍历 meta.Controllers：
          → normalizeToken(controller) 转为指针类型 *T
          → 追加到 s.ControllerOwners[*T]
       d. 遍历 meta.Resolvers：
          → normalizeToken(resolver) 转为指针类型 *T
          → 追加到 s.ResolverOwners[*T]
       e. 存入 s.ModuleOwners[moduleType] = owner
```

关键设计点：
- **Token 统一为指针类型**：`normalizeToken()` 确保所有 token 都是 `*T` 形式，避免 `T` vs `*T` 的匹配不一致
- **ControllerOwners/ResolverOwners 是 `type → []ModuleOwner`**：同类型的 controller 可能出现在多个模块中，保持列表而非单值
- **Snapshot 不含 runtime 信息**：它只反映模块树的静态结构，不包含运行期状态

#### 6.10.2 Owner 索引构建与解析算法详解

编译期的 Owner 索引在 `BuildSnapshotOwnerIndex()` 中构建（`kernel/v3/compiler/plugin_helpers.go`）：

```text
BuildSnapshotOwnerIndex(snapshot, opts) 的完整流程：

  输入：scanner.Snapshot + SnapshotOwnerOptions{Controllers, Resolvers, Providers}

  输出：SnapshotOwnerIndex
          OwnerByType:    map[reflect.Type][]ModuleOwner  — 类型→候选列表
          OwnerByPointer: map[uintptr]ModuleOwner         — 指针→精确 owner

  步骤：
  1. 处理 ControllerOwners：
     if opts.Controllers:
       将 snapshot.ControllerOwners 复制到 OwnerByType
       （类型 → 该类型 controller 所在的模块列表）
       → 例如 *UserController → [ModuleA, ModuleB]

  2. 处理 ResolverOwners（同上，若 opts.Resolvers）

  3. 处理 Providers（若 opts.Providers）：
     遍历 snapshot.Modules 中每个模块的 metadata.Providers：
       → 对每个 provider，若其 Token 是 reflect.Type：
         → 确保为指针类型
         → 将 owner 追加到 OwnerByType[token]
       → 若 provider.UseValue 有实例指针：
         → 存入 OwnerByPointer[ptr] = owner

  4. 填充 OwnerByPointer：
     遍历 snapshot.Modules：
       → 若 opts.Controllers：对每个 controller 实例取指针
         → 存入 OwnerByPointer[ptr] = owner
       → 若 opts.Resolvers：对每个 resolver 实例取指针
         → 存入 OwnerByPointer[ptr] = owner

Owner 解析算法（idx.Resolve(instance)）：

  输入：任意实例（controller/resolver/provider 对象）
  输出：OwnerResolution{Token, Candidates, Owner, Status}

  算法：
    1. token = PointerToken(instance)  // 统一为 *T
    2. candidates = OwnerByType[token]
    3. switch len(candidates):
       case 0 → return {Status: Missing}
       case 1 → return {Owner: candidates[0], Status: Resolved}
       default:
         ptr = InstancePointer(instance)
         if owner, ok := OwnerByPointer[ptr]; ok:
           return {Owner: owner, Status: Resolved}  // 指针精确消歧
         else:
           return {Status: Ambiguous}  // 多个候选但无法消歧
```

#### 6.10.3 CompileRouteSet 汇总算法

`CompileRouteSet` 是各协议 Compile 阶段最后都会走的一步汇总逻辑（`kernel/v3/compiler/plugin_helpers.go`）：

```text
CompileRouteSet(items, compile, conflict) 的完整流程：

  输入：
    items:     []T          — 协议声明项列表
    compile:   T → CompiledRoute[T]  — 单品编译函数
    conflict:  (T, string) → error    — 冲突回调

  输出：
    routes:          map[string]*runtime.Handler       — routeKey → handler
    routeContainers: map[string]*di.Container           — routeKey → container

  算法：
    for each item in items:
      1. compiled = compile(item)
         → 必须返回非 nil 的 Handler 和非空的 RouteKey
      2. 检查 routes[compiled.RouteKey] 是否已存在
         → 若存在：调用 conflict(item, routeKey) 返回冲突错误
         → 若不存在：将 compiled.Handler 存入 routes
      3. 若 compiled.Container != nil：
         → 将 compiled.Container 存入 routeContainers[routeKey]
    return routes, routeContainers, nil
```

#### 6.10.4 CompileSimpleProtocol 通用外壳

对于 gRPC/GraphQL/WS/MQ/Scheduler 这类"不需要额外构建 matcher 树"的协议，统一走 `CompileSimpleProtocol` 外壳：

```text
CompileSimpleProtocol(scan, protocol, pluginID, ...) 的流程：

  1. 从 scan 结果中提取 ownership 列表
     → items(scan) → []T（各协议自己的 ownership 结构）

  2. 对每个 item 调用 compile(item, global)
     → 返回 CompiledRoute[T]{Item, Handler, RouteKey, Container}
     → 内部执行：NewHandlerByToken + CompileAOPPlan + BuildParamPlans

  3. CompileRouteSet 汇总 → routes + routeContainers

  4. 返回 CompiledProtocol{
       Protocol:        protocol,
       Routes:          routes,
       RouteContainers: routeContainers,
       Install:         ProtocolInstaller(protocol, nil, routes),
       //        ↑ matcher 传 nil
       //        因为这类协议不需要自定义 matcher
     }
```

HTTP 不走这个外壳，因为它的 `Install` 函数需要额外回放 Radix Tree：

```text
HTTP 的 Install 实现：
  return &compiler.CompiledProtocol{
    ...
    Install: func(router *runtime.Router) error {
      matcher := newRadixMatcher()
      // 回放编译期构建的 CompiledHTTPTree
      for method, root := range tree.Methods {
        replayCompiledTree(matcher, method, "", root, routes)
      }
      replayCompiledTree(matcher, AllMethod, "", tree.All, routes)
      // 安装时带了 matcher
      return compiler.ProtocolInstaller(http, matcher, routes)(router)
    },
  }
```

gRPC 更特殊：Install 函数只注册 routeKey→handler 映射到 Router，**真正的 `grpc.ServiceDesc` 注册延迟到 adapter.Start() 阶段**，原因是 `grpc.ServiceDesc` 的注册需要 `grpc.Server` 实例，而 `grpc.Server` 在编译期尚未创建。

#### 6.10.5 AOP 计划的编译期合并

AOP 的三级合并（全局 + Controller/Service 级 + Route 级）完全在编译期完成：

```text
CompileAOPPlan(global, local) → AOPPlan

合并规则：
  Middlewares  = global.Middlewares + local.Middlewares
  Guards      = global.Guards + local.Guards
  Interceptors = global.Interceptors + local.Interceptors
  Pipes       = global.Pipes + local.Pipes
  ParamPipes  = mergeParamPipes(global.ParamPipes, local.ParamPipes)
  Filters     = global.Filters + local.Filters

三种形态统一为函数切片（以 Guard 为例）：
  形态一（接口实现）：
    Guard{CanActivate} → aop.WrapGuard → func(execCtx) (bool, error)
  形态二（函数式）：
    GuardFunc(fn) → 直接作为 func(execCtx) (bool, error)
  形态三（延迟构造）：
    GuardConstructor{fn()} → 每次请求调用构造函数 → 调用 CanActivate
```

合并完成后，`CompiledAOP` 写入 `handler.Meta.CompiledAOP`，**运行期不再做任何合并**。

#### 6.10.6 编译期异常处理与错误模型

编译期的错误通过 `KernelError` 统一收口：

```text
错误类型                         触发条件
─────────────────────────────────────────────────────────────
moduleRef is nil                Compile 入口检查
no protocol plugins registered  Compile 入口检查
registry is nil                 未传 registry 且非 Compat 模式
OwnerResolutionMissing          Scan 时 receiver 不在任何模块中
OwnerResolutionAmbiguous        Scan 时 receiver 存在多个模块候选且无法消歧
OwnerTargetNil                  Scan 时 receiver 为 nil
routeKey 冲突                    CompileRouteSet 时发现重复 routeKey
跨协议 routeKey 冲突             不同协议产生了相同的 routeKey
```

所有错误发生时，当前的 `CompileDiagnostics` 会被 `Clone()` 冻结并附着到错误上，便于上层通过 `app.GraphDiagnostics()` 查询完整的编译诊断信息。

## 7. 协议对照与三段式总览

### 7.1 三段式模型

每个协议的完整链路固定为三个阶段，由 ProtocolPlugin 接口驱动：

```text
第一段：DSL 声明（业务代码编写时）
  adapter.API().Controller(...).Get(...).Build()
  → 写入 Registry.RegisterDecl(pluginID, kind, items...)

第二段：编译期（应用启动前/触发编译时）
  compiler.Compile(moduleRef, reg, plugins...)
    ├── [Plugin.Register] 补齐默认 binding
    ├── [BindingRegistry 冻结]
    ├── [Plugin.Scan] 扫描声明，解析 owner
    ├── [Plugin.Compile] → CompiledProtocol
    └── [CompiledApp.Install → Runtime]

第三段：运行期（请求进入时）
  Transport → HandlerContext → Runtime.Execute → Response
```

### 7.2 六协议五维度对照表

| 协议 | 声明粒度 | 扫描/编译特征 | transport/server | binding 重点 | 返回写回 |
| --- | --- | --- | --- | --- | --- |
| HTTP | Controller + Route(method/path) | owner 只看 controller；编译期额外构建 method/path 树 | `net/http` 入口，解析 body/form/files/middleware | body/query/param/header/form/cookie/file/auth/session/auto struct | 统一 HTTP 响应，支持状态码/header/redirect/render/json/string/bytes |
| GraphQL | Resolver + Field(Query/Mutation/Object) | 按 resolver 找 owner，拍平成 field；routeKey 不是 path | transport 解析 GraphQL request，逐字段进入 runtime | args/parent/variables/selection-set/info | 固定写回 `data/errors/extensions` |
| gRPC | Service + Method，声明期确定 RPCMode | owner 可来自 controller/resolver/provider；编译前签名校验 | `grpc.Server` 动态注册 ServiceDesc；unary/stream 分两条桥接链 | proto message、metadata、RawServerStream、ServerStream、ClientStream、BidiStream | unary 直接 return；stream 通过 wrapper 发消息 |
| WS | Gateway(namespace) + On(event) | 按 gateway owner 解析；routeKey = event + namespace | socket 回调里组装 HandlerContext | message/header/socket/context/room/event | 成功 emit response event，失败 emit error event |
| MQ | Consumer + On(topic) | owner 可来自 controller/resolver/provider；simple protocol 编译 | driver 轮询消息，投影为 HandlerContext | message/header/topic/key/retry/ack/nack | 成功 ack，失败 nack |
| Scheduler | Job(name) + Trigger | owner 可来自 controller/resolver/provider；simple protocol 编译 | cron/ticker/timer 触发后构造 HandlerContext | job metadata、run id、scheduled at、context | 无外部回包；结果影响 retry/history/metrics |

### 7.3 六协议三段式一览表

| 协议 | DSL 入口 | Register（binding） | Scan（owner 来源） | Compile 产物 | 运行期触发 | 响应方式 |
| --- | --- | --- | --- | --- | --- | --- |
| HTTP | Controller.Get/Post/... | ~30 种 wrapper | controller | Radix Tree | 网络请求 | HTTP Response |
| gRPC | Service.Method/StreamMethod | Req/Stream wrapper | controller/resolver/provider | ServiceDesc | gRPC Request | return / stream msg |
| GraphQL | Resolver.Query/Mutation | GraphQL wrapper | controller/resolver | Schema + field map | GraphQL Request | data/errors |
| WS | Gateway.On | WS wrapper | controller/resolver | event map | Socket 事件 | emit event |
| MQ | Consumer.On | ack/nack wrapper | controller/resolver/provider | topic map | 消息到达 | ack/nack |
| Scheduler | Job.Trigger | metadata wrapper | controller/resolver/provider | trigger map | 时间事件 | metrics/retry |

### 7.4 各协议关键差异说明

**HTTP** 是当前最"全量"的协议：路由形态最复杂、binding 类型最多、生态桥接最多。编译期额外构建模板路由 matcher tree（非 simple protocol），响应期有独立 `writeHTTPResponse` 逻辑。

**GraphQL** 的关键不是 URL 路径而是 schema/resolver/field。transport 只负责入口，真正的业务执行按 field 多次进入 runtime。

**gRPC** 同时支持四种调用模式（unary/server/client/bidi streaming），声明期固定 RPCMode，编译前做签名校验。streaming 把原生 `grpc.ServerStream` 放入 `Request.Raw`，binding 负责包装成强类型参数。

**WebSocket** 是长连接上的事件协议。每次消息事件重新组装 HandlerContext，返回值是二次 emit 的事件消息。

**MQ** 是消费模型非请求响应模型。没有常规 server，driver 轮询消息并投影进 binding。业务 handler 更像"消息处理器"。

**Scheduler** 是时间驱动任务执行器。transport 是调度器触发器，binding 很克制，返回值不写回外部协议。

## 8. AOP 系统详解

### 8.1 四级作用域

AOP 组件按声明作用域从宽到窄分为四个级别，与 NestJS 的 AOP 分级模型一致：

| 级别 | 作用范围 | 典型场景 |
| --- | --- | --- |
| **全局级（Global）** | 所有协议、所有路由 | CORS、请求日志、全局鉴权、统一异常过滤 |
| **Controller 级** | 某个 Controller 下的所有路由 | 模块级 AuthGuard、模块级日志拦截器 |
| **Service/Route 级** | 单个方法或路由 | 接口级 RateLimitGuard、参数校验 Pipe |
| **Param 级** | 单一参数 | `ParseIntPipe`、`DefaultValuePipe`、`TrimPipe` |

这四级声明的合并完全在编译期 `Plugin.Compile()` 阶段完成，按"全局 → Controller → Route → Param"的顺序叠加为 `CompiledAOP` 写入 `handler.Meta.CompiledAOP`，运行期不再重新合并。

在运行期执行链中，AOP 组件按类型而非作用域执行固定顺序：**Middleware → Guard → Interceptor（包裹 Pipe + Handler）→ ExceptionFilter**。每种类型的内部，四级声明按"全局 → Controller → Route → Param"的顺序执行。

### 8.2 三层使用形态

每一层都提供了三种使用方式，业务可以根据复杂度选择：

**形态一：接口实现**——适合复杂业务逻辑。业务定义一个结构体，实现对应接口（如 `Guard` 的 `CanActivate` 方法）。框架在编译期或运行期通过类型断言识别。

**形态二：函数式**——适合简单逻辑。直接传一个闭包函数（如 `GuardFunc`），框架通过函数类型适配接口。轻量，不需要定义结构体。

**形态三：延迟构造**——适合需要从 DI 容器解析的场景。传一个构造函数，框架在每次请求执行时调用构造函数产生新的实例。适合需要请求级上下文的场景。

这三种形态的统一方式是：框架内部通过 `WrapGuard`、`WrapInterceptor`、`WrapPipe` 等辅助函数，将接口形态统一转换为函数切片。这样一来，运行期的 Pipeline 只处理函数切片，不处理接口——减少了接口调用的类型断言开销，也让执行路径更可预测。

### 8.3 ExecutionContext

AOP 各层不能直接依赖 `runtime.HandlerContext`（否则会造成循环依赖——AOP 在 runtime 之下），因此框架定义了一个"投影"结构 `ExecutionContext`。

这个结构把 runtime 层的信息（协议、路由、请求、响应、容器等）投影到 AOP 层可见的视图中。各层 AOP 组件只通过 `ExecutionContext` 读取上下文，不关心底层是 HTTP 还是 gRPC 还是 MQ。

创建时机在 `Pipeline.Run()` 执行前：用 `HandlerContext` 中的信息填充 `ExecutionContext`，然后传递给所有 AOP 组件。

### 8.4 编译期组装（四阶段）

AOP 的所有组装工作在编译期完成，运行期只做执行。完整组装分四个阶段：

**阶段一：DSL 声明**——业务在 Builder 上声明 AOP

业务通过链式调用声明 AOP，分为两级：
- **Controller/Service 级**：作用于该 controller 下所有路由，作为"基座"
- **Route/Method 级**：仅作用于当前路由，在 Controller 级基础上"追加"

为什么要分两级？因为一个 controller 内的路由通常共享大部分治理逻辑（都需要鉴权、都需要日志），但可能有少数路由需要额外的处理（某个接口需要额外的参数校验）。两级设计避免了在每个路由上重复声明公共 AOP。

**阶段二：Build() 写入 Registry**

当业务调用 `Build()` 时，Builder 将"Controller 级 AOP + Route 级 AOP"合并且写入 `Registry`。合并规则很简单：Controller 级的 AOP 列表在前，Route 级的追加在后。ParamPipes 需要按参数索引分别合并。

**阶段三：Plugin 编译——三级 AOP 合并**

这是最关键的一步。编译期 `Plugin.Compile()` 阶段会做三级合并：

```text
全局 AOP（来自 registry.GlobalAOPRegistration）
  + Controller/Service 级 AOP（来自 RouteDefinition 的基座）
  + Route/Method 级 AOP（来自 RouteDefinition 的追加项）
  = CompiledAOP（写入 handler.Meta.CompiledAOP）
```

全局 AOP 是 application 层面注册的、对所有协议所有路由生效的 AOP；Controller 级只对该 controller 下的路由生效；Route 级只对该路由生效。

**一旦合并完成，CompiledAOP 就成为"最终权威结果"**，运行期不再做任何合并。这保证了执行顺序的可预测性，也消除了运行期合并带来的性能开销。

**阶段四：安装到 Runtime**

`CompiledApp.Install(rt)` 将编译期产出的 AOP 计划、BindingRegistry、RouteContainers 等一次性安装到 Runtime 中。至此运行期准备就绪。

### 8.5 运行期执行链

运行期执行入口在 `Executor.Execute()`（`kernel/v3/runtime/executor.go`），它先完成路由匹配和参数解析，再进入 `Pipeline.Run()` 执行 AOP 管道。以下是基于实际代码的完整链路：

```text
Executor.Execute(ctx, handler)
  │
  ├─ router.Match(ctx)                         → 路由匹配，回填 Params/RouteKey
  │
  ├─ resolveArguments(ctx, handler)            → 参数解析（含 ParamPipes）
  │   └─ 对每个参数按索引依次：
  │       BindingRegistry.Resolve() → DI fallback
  │       → applyParamPipes()                  ← 参数级 Pipe 在此执行
  │         （与 Pipeline 中的 Pipes(input) 不同，ParamPipes 每个参数独立注册，
  │           在 binding/DI 解析完成后立即执行，不经过 Interceptor 包裹）
  │
  └─ pipeline.Run(ctx, handler, args)          → 进入 AOP 管道
      │
      ├─ [Panic 恢复 defer]
      │
      ├─ 选择 AOP 来源
      │   CompiledAOP != nil → 直接使用编译期产物（五类列表均已合并）
      │   否则 → 合并全局 + handler 局部列表
      │
      ├─ 构建 ExecutionContext（HandlerContext 的 AOP 投影）
      │
      ├─ buildMiddlewareChain(middlewares, finalHandler)
      │   │
      │   │  middleware 构成"洋葱最外层"：
      │   │  middleware[0](execCtx, next)
      │   │    → 前置逻辑
      │   │    → next() → middleware[1](execCtx, next)
      │   │      → ... → 最终到达 finalHandler()
      │   │                │
      │   │                ├─ [Guards 逐个执行]
      │   │                │   guard[0](execCtx) → guard[1] → ...
      │   │                │   任一返回 false → ErrGuardRejected
      │   │                │   任一返回 error  → 中断，返回 error
      │   │                │
      │   │                ├─ buildInterceptorChain(interceptors, interceptorFinalHandler)
      │   │                │   │
      │   │                │   │  interceptor 用状态机维护索引，通过 next.Handle() 驱动：
      │   │                │   │  interceptor[0](execCtx, next)
      │   │                │   │    → 前置逻辑（tracing start、缓存检查等）
      │   │                │   │    → next.Handle() → interceptor[1](execCtx, next)
      │   │                │   │      → ... → 最终到达 interceptorFinalHandler()
      │   │                │   │                │
      │   │                │   │                ├─ [Pipes(input)]
      │   │                │   │                │   → 遍历所有 pipes，对每个入参执行 pipe.Transform(arg, "input")
      │   │                │   │                │   → 转换后的值替换原始参数
      │   │                │   │                │
      │   │                │   │                ├─ [Handler.Invoke]
      │   │                │   │                │   → Instance 模式：直接 method.Call(args)
      │   │                │   │                │   → Token 模式：从容器取 receiver → method.Call(args)
      │   │                │   │                │   → 约定：最后一个返回值如果是 error，视为错误
      │   │                │   │                │
      │   │                │   │                ├─ [Pipes(output)]
      │   │                │   │                │   → 对第一个返回值执行 pipe.Transform(result, "output")
      │   │                │   │                │
      │   │                │   │                └─ 返回 (result, nil)
      │   │                │   │
      │   │                │   │    → 后置逻辑（tracing end、缓存回填、异常捕获等）
      │   │                │   │    → 返回 (result, error)
      │   │                │   │
      │   │                │   └─ 若所有 interceptor 都调用了 next.Handle()，则进入 pipes+handler
      │   │                │      若有 interceptor 未调用 next.Handle()（如缓存命中），则跳过剩余链路
      │   │                │
      │   │                └─ 返回 err
      │   │
      │   │  → 后置逻辑
      │   │  → 返回 error
      │   │
      │   └─ middlewareHandler = 上述整条链
      │
      ├─ middlewareHandler()                   ← 执行整条 Middleware + Guard + Interceptor + Pipes + Handler 链
      │
      ├─ [ExceptionFilters]（仅当 middlewareHandler() 返回 error 时执行）
      │   → filter[0](err, execCtx) → filter[1] → ...
      │   → filter 返回 nil：已消费错误，返回 (nil, nil)
      │   → filter 返回 error：继续传播
      │
      └─ 返回 (result, err)
```

#### 关键设计点说明

**1. ParamPipes 为什么在 Pipeline 外面？**

参数级 Pipe（如 `ParseIntPipe`、`DefaultValuePipe`）在 `resolveArguments` 阶段、每个参数 binding/DI 解析完成后**立即执行**（`executor.go` `applyParamPipes`）。这是因为 ParamPipes 是针对**单个参数**的转换器，每个参数可以注册不同的 Pipe，它们在参数值拿到后、handler 被调用前执行。这与 `CompiledAOP.Pipes`（作用于所有入参的全局/路由级 Pipe）不同——后者在 Interceptor 内部的 `interceptorFinalHandler()` 中执行。

**2. Guards 在 Middleware final handler 内部、Interceptor 之前**

从代码结构看，Guards 位于 `buildMiddlewareChain` 的 `finalHandler` 内部、`buildInterceptorChain` 之前。这意味着 Guards 的执行时机是在所有 Middleware 的 `next()` 调用完成后、Interceptor 的 `next.Handle()` 调用之前。效果上：Middleware 可以决定是否让请求到达 Guards（通过不调用 `next()`），Guards 可以决定是否让请求到达 Interceptor（通过返回 false/error）。

**3. Interceptor 包裹 Pipes + Handler**

`buildInterceptorChain` 的 `interceptorFinalHandler` 内部依次执行 Pipes(input) → Handler.Invoke → Pipes(output)。这样设计的三个原因：

- **缓存拦截器**需要在 handler 前检查缓存、后回填缓存，要求包裹整个过程
- **Tracing 拦截器**需要记录 handler 执行的完整耗时
- **未调用 `next.Handle()` 可以跳过整个执行链**——缓存命中时直接返回结果，不走 Pipes + Handler

**4. ExceptionFilters 在整个 middlewareHandler 之后执行**

ExceptionFilters 不在 middleware/guard/interceptor 的链路内部，而是在 `middlewareHandler()` 调用**返回之后**，仅当返回 error 时才逐个执行。这与 NestJS 的 `@Catch()` 异常过滤器位置一致——所有 AOP 组件和 handler 都执行完毕后，如果有未被捕获的错误，才进入过滤器链。

### 8.6 ExceptionFilter 的错消费机制

ExceptionFilter 的设计有一个关键语义：**返回 nil 表示"已消费该错误"**。

```text
handler 返回 error → filter[0].Catch(err)
  → filter[0] 识别为 HttpException(400, "参数错误")
  → 写入 Response 对象，返回 nil（已消费）
  → Pipeline 收到 nil → 不再传播错误
  → 上层 adapter 读取 Response 写回客户端
```

如果 filter 返回非 nil，则错误继续传播。多个 filter 可以形成链——前一个没消费的，后一个接着处理。

框架内置了 `HttpException` 类型，携带 HTTP 状态码和错误消息，专门供 HTTP adapter 读取并映射到响应。

### 8.7 AOP 的 fallback 路径

当 `handler.Meta.CompiledAOP == nil`（没有编译期产物时），Pipeline 会从全局列表和 handler 局部列表中实时收集 AOP 项并合并。这条路径记录在 `runtime_global_aop` fallback inventory 中，供启动报告和诊断输出。

## 9. 优化体系

### 9.1 优化策略的三层模型

框架没有追求"彻底消灭反射"，而是采用三层递进策略：

**第一层：能前置到编译期的，绝不留到运行期**
- AOP 计划编译期合并为 `CompiledAOP`，运行期直接读取，不再实时拼装
- HTTP 路由编译期构建为 Radix Tree，运行期直接树匹配，不做模板解析
- 参数的 BindingName 编译期钉死到 ParamPlans，运行期直接覆盖 matcher 默认值
- BindingRegistry 编译期冻结，运行期不再增删 resolver（`Register()` 仍可用但会清空缓存）

**第二层：必须在运行期做的反射，加缓存**
- BindingRegistry.Find() 有正缓存（类型 → resolver）和负缓存（类型 → 无匹配），热路径 O(1)
- Handler 使用 MethodIndex（int 索引）代替 MethodByName（字符串查找），避免 O(n) 反射查找
- WrapperDescriptor 缓存，同一参数类型不重复匹配

**第三层：通过类型约定减少反射不确定性**
- 泛型 wrapper（`Body[T]`、`Param[T]`）匹配路径固定：包路径 + 泛型名裁剪，无需深度类型遍历
- 精确类型匹配（`*swagger.Builder`）直接用 `==` 比较，走模糊匹配
- 后注册优先策略减少"猜"的成本——越具体的 resolver 越靠后注册，优先命中

### 9.2 编译排序稳定化

**问题**：protocol plugins 的编译顺序影响最终产物的确定性。如果每次启动时 plugins 的顺序不同，遇到跨协议 routeKey 冲突时报错顺序会不稳定。

**实现**：在 `compiler/compile.go` 的 `Compile()` 入口处，先对所有 plugins 做稳定排序：

```go
func stableProtocolPlugins(plugins []ProtocolPlugin) []ProtocolPlugin {
    sorted := make([]ProtocolPlugin, len(plugins))
    copy(sorted, plugins)
    slices.SortStableFunc(sorted, func(a, b ProtocolPlugin) int {
        return strings.Compare(a.ID(), b.ID())
    })
    return sorted
}
```

排序后，每个 plugin 依次执行 `Register → Scan → Compile`。排序保证了：
- 跨协议 routeKey 冲突的报错顺序可预测
- 多 adapter 场景的注册顺序稳定
- 启动报告和诊断输出与启动次数无关

### 9.3 BindingRegistry 编译期冻结与缓存机制

#### 冻结语义

BindingRegistry 在编译器 `Compile()` 阶段通过 `reg.GetBindings()` 收集所有 resolver，然后将其注入到新创建的 `BindingRegistry` 实例中。此后这个实例被注入 `runtime.Executor`，运行期不再修改。虽然 `Register()` 方法仍然可用，但在正常启动链路中不会在运行期调用。

#### 正缓存实现

`BindingRegistry.Find()` 的核心实现在 `binding.go`：

```go
func (br *BindingRegistry) Find(paramType reflect.Type) (BindingResolver, WrapperDescriptor, bool) {
    // 先查缓存
    if br.cache != nil {
        if cached, ok := br.cache[paramType]; ok {
            return cached.resolver, cached.desc, cached.ok
        }
    }
    // 后注册优先：从尾到头遍历
    for i := len(br.resolvers) - 1; i >= 0; i-- {
        desc, ok := br.resolvers[i].Match(paramType)
        if ok {
            // 命中 → 回填正缓存
            br.cache[paramType] = bindingCacheEntry{resolver: res, desc: desc, ok: true}
            return res, desc, true
        }
    }
    // 未命中 → 回填负缓存
    br.cache[paramType] = bindingCacheEntry{resolver: nil, desc: WrapperDescriptor{}, ok: false}
    return nil, WrapperDescriptor{}, false
}
```

**假设 5 个参数、30 个 resolver 的缓存效果**：

| 场景 | 操作 | 复杂度 |
| --- | --- | --- |
| 无缓存（每次请求） | 5 × 30 = 150 次 Match | O(n×m) |
| 首请求 | 5 次 miss + 缓存回填 ≈ 150 次 Match | O(n×m) |
| 后续请求（正缓存命中） | 5 次 map 查找 | O(1) |
| 后续请求（负缓存命中） | 5 次 map 查找，跳过全部遍历 | O(1) |

**负缓存的关键性**：大量 handler 参数是业务 struct（如 `*UserService`），没有对应 binding resolver。无负缓存时每次请求都要遍历全部 30 个 resolver 来确定"没有匹配"——这是 O(n) 的不可缓存成本。负缓存将这个降为 O(1)。

**缓存清空时机**：`Register()` 被调用时清空整个缓存。因为新 resolver 可能覆盖旧匹配结果，缓存指向旧 resolver 会导致语义错误。

### 9.4 AOP 计划前置编译

#### 三级合并算法

AOP 的组装完全在编译期 `Plugin.Compile()` 阶段完成，运行期只做执行不重新合并。

合并发生在 `compiler.CompileAOPPlan()` 函数中：

```text
输入：
  全局 AOP（来自 registry.GlobalAOPRegistration，对所有协议所有路由生效）
  + Controller/Service 级 AOP（来自 RouteDefinition，作用于该 controller 下所有路由）
  + Route/Method 级 AOP（来自 RouteDefinition 的追加项，只作用于当前路由）

合并规则：
  Middlewares  = 全局.Middlewares + Controller.Middlewares + Route.Middlewares
  Guards      = 全局.Guards + Controller.Guards + Route.Guards
  Interceptors = 全局.Interceptors + Controller.Interceptors + Route.Interceptors
  Pipes       = 全局.Pipes + Controller.Pipes + Route.Pipes
  ParamPipes  = 按参数索引合并（全局[paramIdx] + Controller[paramIdx] + Route[paramIdx]）
  Filters     = 全局.Filters + Controller.Filters + Route.Filters

输出：CompiledAOP（写入 handler.Meta.CompiledAOP）
```

**为什么分为两级（Controller 级 + Route 级）？** 因为一个 controller 内的路由通常共享大部分治理逻辑（都需要鉴权、都需要日志），但可能有少数路由需要额外的处理（某个接口需要额外的参数校验）。两级设计避免了在每个路由上重复声明公共 AOP。

**合并后不可变性**：一旦合并完成，`CompiledAOP` 就成为"最终权威结果"。运行期 `Pipeline.Run()` 直接读取 `handler.Meta.CompiledAOP`，不再做任何合并。这保证了：
- 执行顺序的可预测性
- 消除运行期合并的性能开销
- 各层 AOP 的叠加关系在启动期就已固化

#### AOP 的三层使用形态统一

三种形态（接口实现、函数式、延迟构造）通过 `WrapGuard`、`WrapInterceptor`、`WrapPipe` 等辅助函数统一转换为函数切片：

```text
形态一（接口实现）：Guard{CanActivate()} → WrapGuard → func(execCtx) (bool, error)
形态二（函数式）：GuardFunc(fn) → 直接作为 func(execCtx) (bool, error)
形态三（延迟构造）：func() Guard → 每次请求调用构造函数 → 调用 CanActivate
```

运行期 Pipeline 只处理函数切片，不处理接口，减少了接口调用的类型断言开销。

### 9.5 HTTP Radix Tree 编译期构建

#### 设计动机

HTTP 路由匹配是请求执行的最热路径。传统框架通常在运行期逐个匹配路由模板（"遍历所有路由的 method+path，用正则或字符串比较判断是否匹配"），复杂度为 O(n)。编译期构建 Radix Tree 可将匹配复杂度降为 O(path_segments)。

#### 编译期中转结构

在 `plugin.go` 的 `Compile()` 阶段，先构建一株轻量中间树：

```go
// 编译期中转结构（在 runtime 包中定义）
type CompiledHTTPNode struct {
    Static    map[string]*CompiledHTTPNode  // 静态段子树
    Param     *CompiledHTTPNode             // 参数段子树（:id）
    ParamName string                        // 参数名
    RouteKey  string                        // 叶子节点持有路由 key
}

type CompiledHTTPTree struct {
    Methods map[string]*CompiledHTTPNode    // GET/POST 等方法
    All     *CompiledHTTPNode               // ALL method 树
}
```

#### 插入算法

```text
insertCompiledRoute(tree, method, path, routeKey):
  1. 选择根节点：
     - 若 method == "ALL" → tree.All
     - 其他 → tree.Methods[method]（不存在则创建空根节点）
  2. 分割路径：strings.Split(strings.Trim(path, "/"), "/")
  3. 遍历每个 segment：
     - 若 segment 以 ":" 开头（如 ":id"）：
       → node.Param 不存在则创建，记录 ParamName = 去掉 ":" 后的部分
       → node = node.Param
     - 否则（静态段）：
       → node.Static[segment] 不存在则创建
       → node = node.Static[segment]
  4. 叶子节点的 RouteKey 设为当前路由的 routeKey

示例：插入三条路由
  GET /users/:id           →  tree.Methods["GET"] → Static["users"] → Param["id"] → routeKey
  GET /users/me            →  tree.Methods["GET"] → Static["users"] → Static["me"] → routeKey
  POST /users             →  tree.Methods["POST"] → Static["user"] → routeKey

得到的树结构：
  Methods["GET"] → static["users"] → static["me"]    → routeKey("GET /users/me")
                                   → param("id")     → routeKey("GET /users/:id")
  Methods["POST"] → static["users"] → routeKey("POST /users")
```

注意：目前是"node-per-segment"的结构，不是严格的 Radix Tree（压缩前缀树）。每个 URL 段是一个节点，不压缩公共前缀。这是出于代码简洁和 seg 数量通常很小的考虑。如果路由数量极大（万级），可升级为压缩前缀树，目前的设计保留了未来升级的接口。

#### 安装（回放）过程

`Compile()` 产出的中间树通过 `replayCompiledTree()` 回放到运行期 matcher：

```go
func replayCompiledTree(matcher routeMatcher, method, prefix string,
    node *runtime.CompiledHTTPNode, routes map[string]*runtime.Handler) {
    if node == nil { return }
    // 叶子节点：注册路由
    if node.RouteKey != "" {
        matcher.Add(method, prefix, routes[node.RouteKey])
    }
    // 先递归静态段
    for seg, child := range node.Static {
        nextPrefix := prefix + "/" + seg
        replayCompiledTree(matcher, method, nextPrefix, child, routes)
    }
    // 再递归参数段
    if node.Param != nil {
        nextPrefix := prefix + "/:" + node.Param.ParamName
        replayCompiledTree(matcher, method, nextPrefix, node.Param, routes)
    }
}
```

这种"编译期建中间树 + 安装期回放"的两阶段设计，把路由树的构建约束在编译期，运行期的 matcher 只负责匹配。

#### 运行期匹配器

```go
type radixNode struct {
    static   map[string]*radixNode     // 静态段：key=精确字符串
    param    *radixNode                 // 参数段（:id）
    paramKey string                     // 参数名
    handler  *runtime.Handler
}

type radixMatcher struct {
    trees map[string]*radixNode         // method → 根节点
    all   *radixNode                    // ALL method 树
}
```

**匹配算法**（`Match()` 方法）：

```text
Match(ctx):
  1. 对请求路径 splitPath("/users/42") → ["users", "42"]
  2. 先匹配 ctx.Request.Method 对应的树（如 "GET"）
     → matchNode(root, segments, 0, params)
  3. 若未命中，回退到 all 树
     → matchNode(r.all, segments, 0, params)

matchNode(node, segments, idx, params):
  1. 若 node == nil → 返回 nil
  2. 若 idx == len(segments) → 返回 node.handler（到达叶子）
  3. 取当前段 seg = segments[idx]
  4. 尝试静态匹配：node.static[seg] 存在
     → 递归 matchNode(staticNode, segments, idx+1, params)
     → 命中则返回
  5. 尝试参数匹配：node.param 存在
     → params[node.param.paramKey] = seg（记录路径参数）
     → 递归 matchNode(node.param, segments, idx+1, params)
     → 命中则返回；失败则回滚 params 中的记录
  6. 都未命中 → 返回 nil
```

**静态段优先于参数段**：这一顺序保证了 `/users/me` 不会被 `/:id` 抢走。因为匹配时先尝试 static["me"]，命中即返回，不会走到 param 分支。

#### 节点类型

| 节点类型 | 示例 | 匹配规则 | 优先级 |
| --- | --- | --- | --- |
| **Static**（静态节点） | `/users` | 精确字符串匹配 | 最高 |
| **Param**（参数节点） | `/:id` | 匹配任意非空段，记录为路径参数 | 次高 |
| *Wildcard（通配符）* | `/*path` | 当前尚未实现，保留扩展空间 | — |

### 9.6 Owner 指针消歧

**问题**：当多个模块包含同一类型的 controller 时（例如两个模块都有 `*UserController`），编译器需要确定每个路由属于哪个模块。

**实现**：两层消歧策略。

**第一层：类型缩小候选**。`SnapshotOwnerIndex` 维护 `OwnerByType map[reflect.Type][]ModuleOwner`。给定一个 controller 类型，先按类型查出所有候选 owner。

**第二层：实例指针精确消歧**。当类型命中的候选数 > 1 时，用 `OwnerByPointer map[uintptr]ModuleOwner` 按实例指针定位唯一 owner。

```text
例：两个模块都有 *UserController
  ModuleA 的 controller: &UserController{addr: 0x1234}
  ModuleB 的 controller: &UserController{addr: 0x5678}

  扫描发现 route 的 controller 指针是 0x1234
  → OwnerByType[*UserController] = [ModuleA, ModuleB]（2 个候选）
  → OwnerByPointer[0x1234] = ModuleA（精确消歧）
  → 确定 owner = ModuleA
```

如果指针消歧后仍无法唯一确定，标记为 `Ambiguous` 并报错，防止运行时出现"不知道该用哪个模块的容器"的问题。

### 9.7 routeContainers 映射

**目的**：让运行期 `Executor` 能按 `routeKey` 找到对应的模块容器，从而为每个请求创建正确的 DI 子容器。

**编译期构建**：每个 route 编译时，plugin 记录 `owner.container`（该路由所属模块的 DI 容器）。编译器汇总为 `map[string]*di.Container`（routeKey → container）。

**安装**：`CompiledApp.Install()` 将这个映射注入 `runtime.Executor`。

**运行期使用**：`Executor.Execute()` 的容器选择优先级：
1. `ctx.Container` 已被外部设置（如测试 mock）→ 直接使用
2. 查 `routeContainers[handler.Meta.RouteKey]` → 存在则从此容器派生 child
3. 否则从 `rootContainer` 派生 child

没有这个映射，只能退回 root container，模块边界会被冲淡，不同模块的 provider 隔离将失效。

### 9.8 Handler 的 Instance vs Token 模式

两种模式的本质差异在于 receiver 的解析时机和方式：

```text
Instance 模式（运行期注册）：
  DSL 写声明时传入 controller 实例（如 Controller("/users", ctrl)）
  → handler 持有 ctrl 的 reflect.Value
  → 运行期直接 method.Call(args)
  → 优点：实现简单
  → 缺点：无法做 AOP 优化，不支持模块隔离

Token 模式（编译期产物）：
  DSL 写声明时传入 controller 实例
  → plugin 在 Compile 阶段解析 controller 的类型 token
  → handler 保存 token 和 MethodIndex（int 索引）
  → 运行期从 ctx.Container.Get(token) 解析 receiver
  → 再用 rv.Method(MethodIndex) 调用
  → 优点：O(1) 方法定位、支持模块容器隔离和热更新
  → 缺点：需要容器支持按类型解析
```

**MethodIndex 的实现方式**：Go 的 `reflect.Type.Method(i)` 按索引返回 `reflect.Method`，且索引在编译期即固定。框架在编译期通过 `runtime.NewHandlerByToken(controllerType, methodName)` 找出方法名对应的 MethodIndex，运行期用 `receiverValue.Method(MethodIndex)` 直接调用，避免了 `MethodByName` 的 O(n) 字符串查找。

### 9.9 BindingName 编译期钉死

**问题**：HTTP 路由 `GET /users/:id` 中的参数名 `id` 需要在运行时从 path 中提取。如果运行时再解析路由模板来提取参数名，每次请求都要做字符串解析。

**实现**：编译期在 `buildParamPlan()` 函数中将模板参数名钉死到 `ParamPlans`：

```go
func buildParamPlan(handler *runtime.Handler, path string) []runtime.ParamPlan {
    paramNames := extractHTTPParamNames(path)  // "/users/:id" → ["id"]
    for i, typ := range handler.Meta.ParamTypes {
        plan := runtime.ParamPlan{Index: i, Type: typ}
        if isParamWrapper(typ) && paramNameIndex < len(paramNames) {
            plan.BindingName = paramNames[paramNameIndex]  // 钉死 BindingName
            paramNameIndex++
        }
        out = append(out, plan)
    }
    return out
}
```

运行期 `Executor.resolveArgument()` 中，如果 `ParamPlans[paramIndex].BindingName != ""`，直接用它覆盖 `WrapperDescriptor.BindingName`。这样 `resolver.Resolve()` 不需要再解析路由模板，直接从 `ctx.Request.Params["id"]` 取值即可。

### 9.10 Request-scope 启动期跳过

**问题**：模块初始化时如果预实例化所有 provider，Request-scope 的 provider（如当前用户、请求 ID）在启动期没有请求上下文，实例化了也无法使用，白白浪费资源。

**实现**：`BaseModule.Init()` 中遍历 provider 时跳过 Request-scope：

```go
for token := range providers {
    if provider := providers[token]; provider != nil && provider.Scope == di.Request {
        continue  // Request scope 实例不应在模块初始化阶段提前创建
    }
    instance, err := m.container.Get(token)
    // ...触发生命周期回调
}
```

这样每个 Request-scope provider 的实例化推迟到第一次请求进来时，由 `request child container` 按需创建。

### 9.11 Compat 显式建账

**目的**：让所有兼容/fallback 路径显式化，避免"默默回退"导致难以调试的问题。

**实现**：编译器在 `Compile()` 阶段生成两份 fallback inventory：

**Runtime fallback**（运行时可能触发的 fallback）：
- `runtime_global_aop`：handler.Meta.CompiledAOP 为空时，从全局和 handler 局部列表实时合并
- `binding_to_di`：BindingRegistry.Find() 未命中时，回退到 DI 容器取值
- `route_to_root_container`：routeContainers 中没有对应 routeKey 时，从 root container 派生 child

**Registry/read fallback**（编译期从 registry 读取时的 fallback）：
- `application_global_compat`：未传入显式 registry 时使用 `registry.Global()`
- `compile_registry_global_compat`：编译时从全局 registry 读取声明
- `graphql_schema_global_read`：GraphQL schema 读取全局 registry
- `events_attach_global_read`：事件注册从全局 registry 读取
- `swagger_http_registry_global_read`：Swagger 从全局 registry 读取 HTTP 路由声明

这些 fallback 会被写入 `CompileDiagnostics` 和 `StartupReport`，让开发者知道哪些路径走了兼容模式，后续收敛有明确的治理对象。

### 9.12 仍然存在的反射成本

1. **HTTP `Bind[T]` struct tag 解析**：当 handler 使用 `Bind[T]` 时，运行期需要遍历 struct 字段读取 `json`、`form`、`query` 等 tag 来确定绑定来源。这是当前最重的反射操作之一，暂未做缓存优化。

2. **`Handler.Invoke()` 的 `method.Call(args)`**：Go 反射调用的固有成本。Token 模式虽然做了 MethodIndex 优化，但 `reflect.Value.Call()` 本身仍比直接函数调用慢一个数量级。对于性能敏感的高频接口，建议 handler 内部自己组装参数。

3. **gRPC stream wrapper 类型检查**：gRPC 的四种流模式（ServerStream、ClientStream、BidiStream）在运行期需要反射检查泛型参数合法性，以确定 wrapper 与 handler 签名的匹配。

**优化哲学**：不在热路径上做不可缓存的重复反射，但不能消除的反射不强行消除。

### 9.13 剩余复杂度成本

1. **binding 层仍大量依赖反射**：HTTP 绑定 struct（`Bind[T]` 的 struct tag 解析）、GraphQL args 转换（从 AST 到 Go 类型）、gRPC stream wrapper 匹配等
2. **owner 规则未完全统一**：各协议 owner 来源仍分裂——HTTP 只认 controller，gRPC/MQ/Scheduler 还认 resolver 和 provider。这导致 `SnapshotOwnerIndex` 的构建逻辑需要为每个协议做差异化处理
3. **imports/exports 是实例转抄非容器共享**：`BaseModule.Init()` 从 import 模块获取实例后用 `RegisterValue()` 转抄到当前模块容器。边界清楚但初始化有成本（每个导出 token 都要做一次 Get + RegisterValue）
4. **仍保留一部分 fallback**：`binding_to_di`（10.7 节详述）、`route_to_root_container`（9.7 节详述）等

## 10. Binding 与自动绑定系统

### 10.1 设计动机

Binding 系统通过"类型即语义"解决传统 Go web 框架中 handler 需要手动提取参数的问题。例如 `id Param[string]` 表示从 path param 取，`body Body[CreateUserReq]` 表示从请求体反序列化，`svc *UserService` 表示从 DI 容器注入。

### 10.2 三层架构

```text
第一层：BindingRegistry（kernel/v3/runtime/binding.go）
  管理所有 BindingResolver 的注册、查找、缓存
  关键设计：后注册优先、正/负缓存

第二层：BindingResolver（接口契约）
  Name()、AllowedProtocols()、Match()、Resolve()

第三层：具体实现
  协议侧：HTTP 的 Body[T]/Query[T]/Param[T] 等 30+ 种
  Integration 侧：containerBindingResolver（从 DI 容器取值）
  自定义：用户通过 BindingRegistration 注册自己的 resolver
```

### 10.3 BindingRegistry 工作机制

**注册与查找**：后注册优先。基础注册 `matchGenericWrapper("Param")` 匹配所有 `Param[T]`，业务自定义 `matchCustomParam()` 只匹配 `Param[UserId]`。查找 `Param[UserId]` 时先检查自定义匹配 → 命中返回。

**正缓存**：类型命中 resolver 后缓存，后续 O(1) 返回。
**负缓存**：类型无任何 resolver 匹配后缓存，后续直接 DI fallback。

缓存清空时机：`Register()` 被调用时，因新 resolver 可能覆盖旧匹配结果。

### 10.4 BindingResolver 的四个方法

每个 resolver 需要实现四个方法：

**Name**：返回名称用于诊断，让人知道谁处理了这个参数（如 "Body"、"Query"）。

**AllowedProtocols**：协议白名单。HTTP 的 `Body[T]` 只应给 HTTP 协议用，gRPC 的 `Req[T]` 只应给 gRPC 用，而 Integration 的服务如 `*swagger.Builder` 对所有协议可用。这解决了"跨协议参数冲突"问题。

**Match**：给定参数类型，判断是否归这个 resolver 管。返回 WrapperDescriptor 说明匹配细节。

**Resolve**：运行期取值。从 HandlerContext 中提取实际值返回。

`AllowedProtocols` 解决了"跨协议参数冲突"的问题。例如：

```text
HTTP 协议有 Param[string]（从 path 取）
gRPC 协议也有 Param[string]（从 metadata 取）

如果没有协议限制：
  gRPC 请求进来，参数 Param[string] 被 HTTP 的 resolver 拦截
  → HTTP resolver 从 ctx.Request.Params 取值
  → 但 gRPC 的 path params 是空的
  → 返回空字符串，悄无声息地错了

有协议限制：
  gRPC 请求进来：
    → HTTP 的 Param resolver: AllowedProtocols = {http: true}
    → 当前协议是 "grpc"，不在白名单
    → 返回 ErrBindingNotSupported
    → 框架继续尝试下一个 resolver
```

### 10.5 两种匹配模式

#### 模式一：泛型 Wrapper 匹配（协议侧）

这种模式用于 `Body[T]`、`Query[T]`、`Param[T]` 这类泛型包装类型。

匹配的核心思路是"剥洋葱"：

```text
步骤 1：检查参数类型是不是 struct
步骤 2：检查这个 struct 是否在对应 binding 包下
步骤 3：去掉泛型后缀 [T]（Go 的泛型在反射中名为 "Body[string]"）
步骤 4：与基础名比较（"Body"）
步骤 5：取第一个字段（Value）的类型作为 InnerType

例子：Param[string]
  → 类型名 "Param[string]"
  → 去掉泛型后缀 → "Param"
  → 匹配 baseName "Param" → 命中
  → 第一个字段 Value 的类型是 string
  → 返回 {Kind: "Param", WrapperType: Param[string], InnerType: string}
```

为什么取第一个字段？因为所有 HTTP wrapper 的约定是 `Value` 字段在第一位，`Body[T]` 和 `Param[T]` 都是如此。

#### 模式二：精确类型匹配（Integration 侧）

这种模式用于 `*swagger.Builder`、`*kafka.Client` 这类集成服务。

匹配规则极其简单：**参数类型完全相等才命中**。

```text
handler 参数: client *kafka.Client
  → reflect.TypeOf(*kafka.Client)
  → 遍历 resolvers
  → containerBindingResolver.target 也是 *kafka.Client
  → t == r.target → 命中
  → 从 ctx.Container.Get(*kafka.Client) 取值
```

这里的关键设计是"精确匹配"而不是"接口匹配"。为什么不匹配接口？因为如果两个不同的集成都注入了 `interface{}`，系统就无法区分谁是谁了。精确类型匹配牺牲了一点灵活性，但换来了确定性。

### 10.6 完整参数解析流程

```text
Executor.resolveArgument(ctx, handler, paramType, paramIndex)

阶段 1：找 resolver
  → BindingRegistry.Find(paramType)
     → 有正缓存 → 直接返回
     → 有负缓存 → ErrBindingNotFound → DI fallback
     → 无缓存 → 遍历 resolvers 后注册优先
        → 找到 → 回填正缓存
        → 未找到 → 回填负缓存 → DI fallback

阶段 2：协议校验 → resolver.AllowedProtocols 检查

阶段 3：BindingName 覆盖 → ParamPlans[paramIndex].BindingName 覆盖默认值

阶段 4：取值 → resolver.Resolve(ctx, desc)

阶段 5：类型校验 → AssignableTo / ConvertibleTo

阶段 6：参数级 Pipe → 执行 pipe.Transform()

阶段 7：返回 resolved reflect.Value
```

### 10.7 Binding 与 DI 协作

**Binding 优先，DI 兜底。** Binding 一旦命中，无论成功失败，都不会回退到 DI。这能避免错误 binding 配置被 DI 悄悄掩盖。

| 场景 | Binding | DI |
| --- | --- | --- |
| `Param[string]` | 命中，从 path params 取值 | 不参与 |
| `*UserService` | 未命中（ErrBindingNotFound） | fallback 从容器取 |
| 错误注册 `*UserService` binding | 命中但取不到值 | **不参与**（binding 覆盖了） |

### 10.8 Integration 自动绑定（Swagger + Kafka）

所有 integration 的自动绑定通过 `kernel/v3/integration/binding.go` 中的 `RegisterContainerBindings` 完成。这个函数接收一组 `BindingEntry`（每个 entry 包含一个名字和一个 reflect.Type token），为每个 entry 创建一个 `containerBindingResolver`。

`containerBindingResolver` 的工作逻辑极其简单：
- **Match**：参数类型与 target 完全相等（`==` 比较）才命中。不做任何泛型推导或包路径检查。
- **Resolve**：从 `ctx.Container.Get(token)` 取值——直接从请求级 DI 容器获取之前由 ForRoot 注册的实例。

这种"精确类型匹配"的设计哲学和协议 binding 的"泛型 wrapper 推导"截然不同。原因很简单：Integration 侧没有"从请求中提取数据"的需求，只有"从容器中查找服务"的需求。精确匹配最安全——不会误拦截其他类型的参数。

#### Swagger 自动绑定完整链路

**第一步：ForRoot 创建实例**。用户在 `swagger.ForRoot(cfg)` 时，框架创建 `*Builder`、`Config`、`*UIConfig`、`Factory` 五个实例，并包装为 `di.Provider`（token = reflect.Type）注册到模块的 providers 和 exports。

**第二步：Init 注册 binding**。`Module.Init()` 调用 `RegisterContainerBindings`，向 registry 注册 5 个 `containerBindingResolver`。每个 resolver 知道"当 handler 参数类型是 X 时，从容器取 X 的实例"。

**第三步：编译期聚合**。compiler 从 registry 读取所有 binding resolver，组装到 BindingRegistry。

**第四步：运行期注入**。handler 参数中有 `*swagger.Builder` → BindingRegistry.Find 命中 → containerBindingResolver.Resolve 从 ctx.Container.Get(*swagger.Builder) → 返回 ForRoot 时注册的实例。

关键理解：**ForRoot 创建实例并放入容器，RegisterContainerBindings 告诉 binding 系统"这个类型可以从容器取"，两者缺一不可**。

#### Kafka 的两种绑定（精确匹配 + 命名引用）

Kafka 比 Swagger 多了一种绑定能力——命名引用绑定。它解决的是"多个同类型实例如何区分"的问题。

**精确类型绑定**：和 Swagger 一样，注册 `*kafka.Client`、`ReaderFactory`、`WriterFactory`、`Config`、`*Config`、`Factory` 等 6 个 containerBindingResolver。当 handler 参数类型精确匹配时，从容器取对应的单例。

**命名引用绑定**：当应用中有多个 Kafka 客户端（如一个处理订单消息、一个处理通知消息）时，通过 `Ref[T, Marker]` 模式区分。`Marker` 是一个标记类型（如 `OrderTopic`、`NotificationTopic`），运行时通过 Marker 的类型名推导出命名空间的名称，从容器中按名称查找对应的实例。

这和协议 binding 的泛型 wrapper 有本质区别：协议 wrapper 的泛型参数 T 是值的类型（如 `Param[string]` 中的 string），而 Ref 的泛型参数 T 是服务类型、Marker 是区分标记。

### 10.9 协议绑定 vs Integration 绑定的本质差异

| 维度 | 协议绑定 | Integration 绑定 |
| --- | --- | --- |
| **匹配哲学** | 泛型类型推导（"你说 Body[T] 我就从 body 取"） | 精确类型匹配（"你说 *Client 我就从容器拿"） |
| **值从哪里来** | 从当前请求数据中提取 | 从 DI 容器中获取 |
| **有没有协议限制** | 通常有（只服务自己的协议） | 通常没有（所有协议都可注入） |
| **注册时机** | 编译期 Plugin.Register() | 模块初始化 Init() |
| **依赖什么** | 不依赖模块（框架内置） | 依赖 ForRoot() 先创建 provider |
| **典型例子** | HTTP 的 `Param[string]` | Swagger 的 `*swagger.Builder` |
| **能否自定义** | 可以，注册新的 BindingRegistration | 可以，RegisterContainerBindings |

### 10.10 链式调用的实现

框架 DSL 使用 **Builder 模式**。核心设计理念是：声明与执行分离——链式调用的每一环都在收集声明，不执行业务逻辑，只在最终的 `Build()` 时一次性写入 Registry。

#### 10.10.1 三阶段 Builder 状态机

HTTP 协议的 DSL 定义了三种 Builder，构成一个严格的状态转换机：

```text
┌──────────────────┐      Get/Post/Put/...      ┌──────────────────┐
│ ControllerBuilder │ ──────────────────────────→ │   RouteBuilder   │
│ （配置阶段）       │                              │  （路由配置阶段）  │
│                    │ ←────────────────────────── │                   │
│   UseGuards()     │     Get/Post/...（继续下一条） │  UseGuards()     │
│   UsePipes()      │                              │  UsePipes()      │
│   UseMiddlewares()│                              │  Header()        │
│   UseInterceptors()│                             │  Summary()       │
│   UseFilters()    │                              │  ...             │
│   UseParamPipes() │                              │                   │
└──────────────────┘                              └────────┬──────────┘
         ▲                                                   │
         │                StatusCode(200)/Redirect/Render     │
         │                                                   ▼
         │                              ┌──────────────────────────┐
         │                              │  RouteTerminalBuilder     │
         └───────────────────────────── │  （终结态，sealed）        │
              Get/Post/.../Build()      │  → 继续下一条 Get/Post    │
                                        │  → 或 Build() 结束        │
                                        └──────────────────────────┘
```

**ControllerBuilder**：Controller 级配置阶段。在此阶段可以配置作用于该 Controller 下**所有路由**的共享 AOP（UseGuards、UsePipes、UseMiddlewares 等）。这些方法返回 `*ControllerBuilder` 自身，支持继续链式调用。

**RouteBuilder**：单条路由配置阶段。通过 `ControllerBuilder.Get/Post(...)` 进入。在此阶段可以追加仅**作用于当前路由**的 AOP 和文档元信息。路由级配置与 Controller 级配置在最终 `build()` 时合并。

**RouteTerminalBuilder**：路由终结态。通过 `RouteBuilder.StatusCode()/Redirect()/Render()` 进入。设置了 `sealed=true` 标记，防止继续对当前路由追加配置。该 Builder 上只能做两件事：开始下一条路由（Get/Post...），或调用 Build() 结束整个 Controller 的声明。

#### 10.10.2 状态守卫机制

DSL 通过 `sealed` 字段和 `assertCanConfigureControllerScope()` 保证调用的合法性：

**RouteBuilder.sealed 守卫**：所有路由级配置方法（UseGuards、UsePipes 等）开头都检查 `if rb.sealed { return rb }`。一旦调用了 StatusCode/Redirect/Render 进入终结态，任何对当前路由的配置都会被静默忽略。

**Controller 级守卫**：`assertCanConfigureControllerScope()` 确保在第一条路由声明之后，不能再修改 controller 级别的共享配置：

```go
func (b *ControllerBuilder) assertCanConfigureControllerScope() {
    if len(b.routes) > 0 && b.err == nil {
        b.err = fmt.Errorf("http.ControllerBuilder: controller-level Use* APIs " +
            "must be called before declaring the first route")
    }
}
```

这意味着以下用法会报错：

```go
adp.API().Controller("/users", ctrl).
    Get("/:id", ctrl.GetByID).        // 第一条路由 → routes 不为空
    UseGuards(AuthGuard{}).           // 错误！Controller 级配置必须在路由之前
    Post("/", ctrl.Create).
    Build()
```

正确的做法是：

```go
adp.API().Controller("/users", ctrl).
    UseGuards(AuthGuard{}).           // 先配置 controller 级共享守卫
    Get("/:id", ctrl.GetByID).        // 再声明路由
    Post("/", ctrl.Create).
    Build()
```

#### 10.10.3 AOP 继承与合并算法

核心合并逻辑在 `RouteBuilder.build()` 中：

```go
func (rb *RouteBuilder) build(cb *ControllerBuilder) *RouteDefinition {
    return &RouteDefinition{
        Method:     rb.method,
        Path:       cb.prefix + rb.path,
        Controller: cb.controller,
        MethodName: rb.methodName,
        // Controller 级（cb.*）在前，Route 级（rb.*）在后
        Guards:       append(append([]any{}, cb.guards...), rb.guards...),
        Interceptors: append(append([]any{}, cb.interceptors...), rb.interceptors...),
        Middlewares:  append(append([]any{}, cb.middlewares...), rb.middlewares...),
        Pipes:        append(append([]any{}, cb.pipes...), rb.pipes...),
        ParamPipes:   MergeParamPipes(cb.paramPipes, rb.paramPipes),
        Filters:      append(append([]any{}, cb.filters...), rb.filters...),
        StatusCode:   rb.statusCode,
        // ...
    }
}
```

**合并规则**：Controller 级的 AOP 列表在前，Route 级的追加在后。以 Guards 为例：

```text
Controller 级 Guards：      [AuthGuard, LoggerGuard]
Route 级 Guards：           [RateLimitGuard]
合并后：                    [AuthGuard, LoggerGuard, RateLimitGuard]

执行顺序：AuthGuard → LoggerGuard → RateLimitGuard
```

ParamPipes 的合并需要按参数索引分别合并：

```text
Controller 级 ParamPipes：  {0: [ParseIntPipe], 1: [TrimPipe]}
Route 级 ParamPipes：       {0: [ValidatePositivePipe], 2: [RequiredPipe]}
合并后：                    {0: [ParseIntPipe, ValidatePositivePipe],
                             1: [TrimPipe],
                             2: [RequiredPipe]}
```

#### 10.10.4 链式调用的完整代码示例

```go
// 最小示例
adp.API().Controller("/users", &UserController{}).
    UseGuards(AuthGuard{}).                  // controller 级守卫
    UsePipes(ValidationPipe{}).              // controller 级 pipe
    Get("/:id", (*UserController).GetByID).  // GET /users/:id
        UsePipes(ParseIntPipe{}).            // route 级 pipe（追加）
        Summary("根据 ID 获取用户").           // 文档摘要
        Header("X-Cache", "true").           // 响应头
        ErrorResponse(404, "用户不存在").      // 文档
        StatusCode(200).                     // 终结态（200）
    Post("/", (*UserController).Create).     // POST /users
        StatusCode(201).                     // 终结态（201）
    Build()                                  // 写入 Registry
```

#### 10.10.5 链式调用的本质

**链式调用的本质是声明收集器**，与常规 Builder 模式的区别：

| 维度 | 常规 Builder | 框架 DSL |
| --- | --- | --- |
| 调用时机 | 创建对象时 | 应用启动前，编译阶段之前 |
| 产出 | 直接返回构建好的对象 | 写入 Registry，等待编译期读取 |
| 执行 | 方法调用时可能执行业务逻辑 | **只收集声明，不执行业务逻辑** |
| 终点 | 调用 Build() 返回目标对象 | 调用 Build() 写入 Registry |

`Build()` 调用时，将所有已收集的 `RouteDefinition` 通过 `registry.RegisterDecl(AdapterID, "routes", items...)` 一次性地写入 Registry。编译期 `Plugin.Scan()` 再从 Registry 读取这些声明，做 owner 推导和编译。

```text
时序：
  ControllerBuilder.UseGuards()     → 写入 cb.guards 列表
  ControllerBuilder.Get()           → 创建 RouteBuilder，记录 method/path/handler
  RouteBuilder.UsePipes()           → 写入 rb.pipes 列表
  RouteBuilder.StatusCode(201)      → 设置 rb.statusCode，标记 sealed
  RouteTerminalBuilder.Build()      → 遍历所有 RouteBuilder
                                       → 每个 RouteBuilder.build(cb) 合并 AOP
                                       → 生成 RouteDefinition 列表
                                       → registry.RegisterDecl("http", "routes", defs...)
```

所有声明写完 Registry 后，编译阶段才开始读取并处理它们。这就是"声明与执行分离"在 DSL 层的具体落地。

## 11. 请求执行完整链路

以一个 HTTP 请求为例，完整走通从"声明"到"响应"的所有阶段。

### 11.1 完整链路总图

```text
【阶段一：模块与启动装配】
Application.NewWithOptions(rootModule, opts, httpAdapter)
  -> ModuleLoader.LoadMultiple(rootModule)
  -> Module.Init()：初始化各模块，注册 provider
  -> adapter.Mount(host)：挂载 HTTP adapter
  -> adapter.Plugins()：注册 HTTP Plugin

【阶段二：DSL 声明】
adapter.API().Controller("/users", ctrl).
    UseGuards(AuthGuard{}).
    Get("/:id", ctrl.GetByID).UsePipes(ParseIntPipe{}).
    Post("/", ctrl.Create).StatusCode(201).
    Build()
  -> registry.RegisterDecl("http", "routes", defs...)

【阶段三：编译】
compiler.Compile(moduleRef, reg, plugins...)
  -> [Register] HTTP Plugin 注册 Body[T]/Query[T]/... 等 binding
  -> [BindingRegistry 冻结]
  -> [Scan] 扫描 routes 声明，解析 controller owner
  -> [Compile]
    -> 合并 AOP（全局 + Controller + Route → CompiledAOP）
    -> 构建 CompiledHTTPTree（Radix Tree）
    -> 编译 ParamPlans（记录每个参数的 BindingName）
    -> 生成 routeKey → handler 映射
    -> 生成 routeContainers（routeKey → module container）
  -> [跨协议冲突检测] → [CompiledApp]
  -> CompiledApp.Install(rt)
    -> 创建新 Router，安装 matcher
    -> 注入 BindingRegistry → Executor
    -> 注入 RouteContainers → Executor
    -> 同步全局 AOP → Pipeline

【阶段四：服务启动】
app.Listen(":8080") → adapter.Start() → http.Server 启动 → ServeHTTP 循环

【阶段五：请求处理】
HTTP Request → ServeHTTP(w, r)
  |
  +-- adapter 层
  |   → CORS/Helmet 处理
  |   → 解析 body/query/form/file
  |   → 构造 HandlerContext { Protocol, Request, Response }
  |   → 构造 HttpContext（放入 Metadata）
  |   → 提取 auth/session（若有）
  |
  +-- Runtime.Execute(ctx)
  |     → Router.Match(ctx)
  |     |   → Radix Tree 按 method + path 匹配
  |     |   → 返回 Handler + path params
  |     |   → ctx.Request.Params 回填
  |     |
  |     → 容器选择（routeContainers[routeKey] ? NewChild : root.NewChild）
  |     |   → ctx.Container = child container
  |     |
  |     → resolveArguments(ctx, handler)
  |     |   → 遍历 ParamTypes，对每个参数：
  |     |     → BindingRegistry.Find(paramType) [正/负缓存]
  |     |     → 命中 → AllowedProtocols 校验 → resolver.Resolve()
  |     |     → 未命中 → ctx.Container.Get(paramType) [DI fallback]
  |     |     → 类型校验 → ParamPipes Transform
  |     |
  |     → Pipeline.Run(ctx, handler, args)
  |     |   → 选择 AOP 来源（CompiledAOP 优先）
  |     |   → 构建 ExecutionContext
  |     |   → [Middleware Chain] → [Guard Chain]
  |     |   → [Interceptor Chain] → [Pipe(input)]
  |     |   → [Handler.Invoke]（Instance/Token 模式）
  |     |   → [Pipe(output)] → [ExceptionFilter]
  |     |   → 返回 (result, error)
  |     |
  |     → normalizeError（若有 error）
  |
  +-- adapter 写回响应
        → 有 error → 映射为 HTTP 状态码 + 错误体
        → 无 error → 按 StatusCode/Headers/Redirect/Render 写回
```

#### GraphQL 请求执行完整流程

以 GraphQL Query `{ user(id: 1) { name } }` 为例：

```text
GraphQL 请求 POST /graphql
  |
  +-- Adapter.ServeHTTP(w, r)
  |     |
  |     +-- 解析 HTTP 请求（支持 GET/POST, JSON/application-graphql/batch）
  |     |     → gqlparser.Parse 解析 Query AST
  |     |     → findOperationAndFragments 提取 operation
  |     |     → coerceVariables 合并变量
  |     |
  |     +-- 构造 OperationContext
  |     |     → 包含 Schema、Fragments、Variables、HTTP Request 等
  |     |
  |     +-- 执行 Schema Extensions.BeforeOperation（如果有）
  |     |
  |     +-- rootTypeNameForOperation → 确定根类型（"Query"）
  |     |
  |     +-- validateSelectionSet → 校验字段选择集合法性
  |     |
  |     +-- executeSelectionSet(opCtx, "Query", selectionSet, nil, nil)
  |           |
  |           +-- collectFields：按 parentType 收集需要解析的字段
  |           |     → 对每个选中字段，查找 schema 中的 compiledField
  |           |
  |           +-- 遍历字段，逐个 executeField()
  |                 |
  |                 +-- 内置字段（__typename / __schema / __type）
  |                 |     → 直接返回元信息，不进入 runtime
  |                 |
  |                 +-- 业务字段（如 user）
  |                       |
  |                       +-- coerceFieldArguments → 参数校验与类型强制转换
  |                       |
  |                       +-- executeRuntimeField(opCtx, parentType, field, root, args, info)
  |                             |
  |                             +-- 构造 runtime.HandlerContext
  |                             |     Protocol: "graphql"
  |                             |     RouteKey: "gql:Query:user"
  |                             |     Request: {
  |                             |       Method: "Query",
  |                             |       Path: "user",
  |                             |       Body: nil,
  |                             |       Raw: &http.Request{...}  // 原始 HTTP 请求
  |                             |       Headers: {"content-type": "application/json", ...}
  |                             |     },
  |                             |
  |                             +-- 构造 GraphQLContext → 注入 Metadata
  |                             |     → MetadataKeyContext / Headers / Vars / Root
  |                             |     → MetadataKeyInfo / Field / FieldTyp / FieldName
  |                             |     → MetadataKeySelectionSet / OperationName / RawQuery
  |                             |
  |                             +-- Runtime.Execute(ctx)
  |                                   |
  |                                   +-- Router.Match(ctx)
  |                                   |     → GraphQL 不经过自定义 matcher
  |                                   |     → routeKey 由 executeRuntimeField 直接设置
  |                                   |     → ctx.RouteKey = "gql:Query:user"
  |                                   |
  |                                   +-- 容器选择（同 HTTP，按 routeKey 取 module container）
  |                                   |
  |                                   +-- resolveArguments(ctx, handler)
  |                                   |     → 参数[0]: Arg[Int]（对应 args.id）
  |                                   |       → BindingRegistry.Find(Arg[Int]) 命中
  |                                   |       → resolver.Resolve: 从 ctx.Metadata 的 field args 中取值
  |                                   |       → 返回 Arg[Int]{Value: 1}
  |                                   |     → 参数[1]: *UserService
  |                                   |       → BindingRegistry 未命中 → DI fallback
  |                                   |
  |                                   +-- Pipeline.Run → Handler.Invoke
  |                                   |     → 返回 (*User{ID: 1, Name: "Alice"}, nil)
  |                                   |
  |                                   +-- 返回 (result, nil)
  |
  +-- completeFieldValue(opCtx, "Query", schemaField, field, value, path)
  |     → user 是非标量类型且有子选择集 { name }
  |     → 递归 executeSelectionSet(opCtx, "User", selectionSet, user, path)
  |     |     → 解析 name 字段：直接取 reflect.ValueOf(user).Field("Name")
  |     |     → 返回 {"name": "Alice"}
  |     → 合并结果为 {"user": {"name": "Alice"}}
  |
  +-- Schema Extensions.AfterOperation（如果有）
  |
  +-- 返回 GraphQLResponse{Data: {"user": {"name": "Alice"}}}
  |     → 序列化为 JSON
  |     → HTTP 200, Content-Type: application/json
```

**GraphQL 的关键差异**：
- 一条请求可能**多次进入 `runtime.Execute()`**（每个有 handler 的 field 各一次），而非一次
- 路由不按 URL path 分发，而是按 **schema + AST 解析结果**逐字段执行
- `executeRuntimeField()` 每次调用都构造新的 `HandlerContext`，但复用同一个 HTTP 请求上下文

#### WebSocket 请求执行完整流程

以 WS 事件 `chat.message` 为例（namespace=`/chat`）：

```text
WebSocket 客户端连接 ws://host:port/socket.io/
  |
  +-- socket.io Server 建立连接
  |     → server.OnConnect(ns, callback) 被触发
  |     → callOnConnect(ns, conn) → 调用 gateway 的 OnWebSocketConnect
  |
  +-- 客户端 emit "message" 事件到 namespace "/chat"
  |
  +-- socket.io 框架按 namespace + event 匹配
  |     → 命中编译期注册的 OnEvent("/chat", "message", callback)
  |
  +-- callback(conn, msg) 被调用
  |     |
  |     +-- 构造 runtime.HandlerContext
  |     |     Protocol: "ws"
  |     |     RouteKey: "ws:message:/chat"
  |     |     Request: {
  |     |       Method: "message",          // 事件名
  |     |       Path: "/chat",              // namespace
  |     |       Body: msg,                  // 事件消息原始对象
  |     |       BodyBytes: jsonBytes(msg),  // JSON 序列化后的字节
  |     |       Raw: nil,
  |     |       Headers: conn.RemoteHeader()  // 连接建立时的 HTTP 头
  |     |     },
  |     |     Response: { Status: 200, Headers: {} }
  |     |
  |     +-- 注入 Metadata
  |     |     → MetadataKeySocket: conn（socket.io 连接对象）
  |     |     → MetadataKeyServer: a.server（socket.io server）
  |     |     → MetadataKeyEvent: "message"（事件名）
  |     |     → MetadataKeyHeaders: conn.RemoteHeader()
  |     |
  |     +-- Runtime.Execute(ctx)
  |           |
  |           +-- Router.Match(ctx)
  |           |     → WS 不经过自定义 matcher
  |           |     → routeKey 已由 callback 直接设置
  |           |     → ctx.RouteKey = "ws:message:/chat"
  |           |
  |           +-- 容器选择（同 HTTP）
  |           |
  |           +-- resolveArguments(ctx, handler)
  |           |     → 参数[0]: WSMessageBody[ChatMessage]
  |           |       → BindingRegistry 命中 → 从 BodyBytes JSON 反序列化
  |           |       → 返回 WSMessageBody[ChatMessage]{Value: &ChatMessage{...}}
  |           |     → 参数[1]: Socket（socket.io 连接）
  |           |       → BindingRegistry 命中 → 从 Metadata 取 conn
  |           |       → 返回 Socket 包装
  |           |     → 参数[2]: Event（事件名）
  |           |       → BindingRegistry 命中 → 从 Metadata 取 event
  |           |
  |           +-- Pipeline.Run → Handler.Invoke
  |           |     → handler 执行业务逻辑
  |           |     → 返回 (result, nil) 或 (nil, error)
  |           |
  |           +-- 返回 (result/nil, error/nil)
  |
  +-- 响应写回（由 callback 完成）
        → 成功：conn.Emit("messageResponse", result)
        → 失败：conn.Emit("messageError", err.Error())
```

**WS 的关键差异**：
- 连接是长生命周期对象，一条连接上反复触发多个事件
- 每次事件都重新构造 HandlerContext，但 socket.io 连接对象（`conn`）跨越多个请求
- 响应不是 HTTP 回包，而是 emit 到客户端的事件
- namespace 的 connect/disconnect/error hooks 只注册一次，由 `ensureNamespaceHooks` 去重

#### MQ 请求执行完整流程

以 Kafka 消息 `order.created` 为例（consumer=`order-service`）：

```text
Kafka Broker 上有消息到达 topic "order.created"
  |
  +-- Adapter.Start()
  |     → driver.Open(ctx, consumerConfig) 打开 Session
  |     → 启动 consumeLoop 后台 goroutine
  |
  +-- consumeLoop(ctx, cfg, session)
  |     → 循环调用 session.Poll(ctx) 拉取消息
  |     → 拿到消息 msg → dispatchMessage(ctx, cfg, msg)
  |
  +-- dispatchMessage(ctx, cfg, msg)
  |     |
  |     +-- 构造 runtime.HandlerContext
  |     |     Protocol: "mq"
  |     |     RouteKey: "mq:order.created:order-service"
  |     |     Request: {
  |     |       Method: "order.created",         // topic
  |     |       Path: "order-service",            // consumer
  |     |       Body: msg.Raw,                    // 原始消息对象
  |     |       BodyBytes: msg.Body,              // 消息体字节
  |     |       Raw: msg.Raw,
  |     |       Headers: normalizeHeaders(msg.Headers)
  |     |     },
  |     |     Response: { Status: 200, Headers: {} }
  |     |
  |     +-- 注入 Metadata
  |     |     → MetadataKeyHeaders: msg.Headers
  |     |     → MetadataKeyTopic: "order.created"
  |     |     → MetadataKeyConsumer: "order-service"
  |     |     → MetadataKeyKey: msg.Key
  |     |     → MetadataKeyRetryCount: msg.RetryCount
  |     |     → MetadataKeyAck: onceAck(msg.Ack)    // ack 函数（仅调用一次）
  |     |     → MetadataKeyNack: onceNack(msg.Nack)  // nack 函数（仅调用一次）
  |     |
  |     +-- Runtime.Execute(ctx)
  |           |
  |           +-- Router.Match(ctx)
  |           |     → MQ 不经过自定义 matcher
  |           |     → routeKey 已由 dispatchMessage 直接设置
  |           |     → ctx.RouteKey = "mq:order.created:order-service"
  |           |
  |           +-- 容器选择（同 HTTP）
  |           |
  |           +-- resolveArguments(ctx, handler)
  |           |     → 参数[0]: Message[OrderCreated]
  |           |       → BindingRegistry 命中 → 从 BodyBytes JSON 反序列化
  |           |       → 返回 Message[OrderCreated]{Value: &OrderCreated{...}}
  |           |     → 参数[1]: Headers（消息头）
  |           |       → BindingRegistry 命中 → 从 Metadata 取 Headers
  |           |     → 参数[2]: Ack
  |           |       → BindingRegistry 命中 → 从 Metadata 取 ack 函数
  |           |     → 参数[3]: Nack
  |           |       → BindingRegistry 命中 → 从 Metadata 取 nack 函数
  |           |
  |           +-- Pipeline.Run → Handler.Invoke
  |           |     → handler 执行业务逻辑（处理订单创建事件）
  |           |     → 返回 (result, nil) 或 (nil, error)
  |           |
  |           +-- 返回 (result/nil, error/nil)
  |
  +-- 响应（由 dispatchMessage 根据 error 决定）
        → error == nil → ack() 确认消息（消息出队，不会重投）
        → error != nil → nack() 拒绝消息（由 driver 决定重投/死信）
```

**MQ 的关键差异**：
- 没有网络 server，触发源是消息队列轮询（`session.Poll()`）
- 没有"请求-响应"模型，ack/nack 代替了回包
- `Message[T]` binding 从 `BodyBytes` JSON 反序列化，而非从请求体解析
- Ack/Nack 作为 binding wrapper 注入 handler，而非通过返回值控制

以定时任务 `daily-report`（Cron 表达式 `0 8 * * *`）为例：

```text
  |     → time.NewTicker(1s)  // 每秒轮询
  |     → 匹配 cron 表达式 "0 8 * * *"
  |     → 每天 08:00:00 触发（cronSlot 去重防止同一秒重复触发）
  |
  |     OR
  |
  +-- runTicker(ctx, def)    // TriggerKind = TriggerEvery
  |     → time.NewTicker(def.Duration)
  |     → 固定间隔触发（如每 30 秒）
  |
  |     OR
  |
  +-- runTimer(ctx, def)     // TriggerKind = TriggerAfter
  |     → time.NewTimer(def.Duration)
  |     → 一次性延迟触发（如启动后 5 分钟）
  |
  +-- dispatchJob(ctx, def, scheduledAt)
  |     → acquireSlot(def)：检查限流槽（并发限制）
  |     → 获取不到 slot → 丢弃此次触发（不阻塞）
  |     → 获取成功 → go runJob(ctx, def, scheduledAt)
  |
  +-- runJob(ctx, def, scheduledAt)
  |     |
  |     +-- 若 def.Timeout > 0 → ctx = WithTimeout(ctx, def.Timeout)
  |     |
  |     +-- 构造 runtime.HandlerContext
  |     |     Protocol: "scheduler"
  |     |     RouteKey: "scheduler:cron:daily-report"
  |     |     Request: {
  |     |       Method: "cron",              // TriggerKind
  |     |       Path: "daily-report",        // job name
  |     |       Body: nil,
  |     |       BodyBytes: nil,
  |     |       Raw: nil,
  |     |       Headers: {}
  |     |     },
  |     |     Response: { Status: 200, Headers: {} }
  |     |
  |     +-- 注入 Metadata
  |     |     → MetadataKeyJobName: "daily-report"
  |     |     → MetadataKeyTriggerType: "cron"
  |     |     → MetadataKeyScheduledAt: scheduledAt
  |     |     → MetadataKeyRunID: "daily-report-<unix-nano>"
  |     |
  |     +-- 重试循环（若 def.RetryAttempts > 0）
  |           |
  |           +-- Runtime.Execute(ctx)
  |           |     |
  |           |     +-- Router.Match(ctx)
  |           |     |     → routeKey 已由 runJob 直接设置
  |           |     |     → ctx.RouteKey = "scheduler:cron:daily-report"
  |           |     |
  |           |     +-- 容器选择（同 HTTP）
  |           |     |
  |           |     +-- resolveArguments(ctx, handler)
  |           |     |     → 参数[0]: JobMeta（任务元信息）
  |           |     |       → BindingRegistry 命中 → 从 Metadata 提取
  |           |     |       → 返回 JobMeta{Name: "daily-report", RunID: "...", ...}
  |           |     |     → 参数[1]: *ReportService
  |           |     |       → BindingRegistry 未命中 → DI fallback
  |           |     |
  |           |     +-- Pipeline.Run → Handler.Invoke
  |           |           → 生成每日报告、发送邮件等业务逻辑
  |           |           → 返回 (result, nil) 或 (nil, error)
  |           |
  |           +-- 根据执行结果处理
  |                 → 成功：recordRun(def, Success=true) → 结束
  |                 → 失败 + 还有重试次数：
  |                   → def.RetryBackoff > 0 → time.After(backoff)
  |                   → 进入下一次重试循环
  |                 → 失败 + 无重试次数：
  |                   → recordRun(def, Success=false, Error=err) → 结束
  |
  +-- 最终结果
        → 记录到 history（JobRunRecord）
        → 更新 metrics（成功/失败计数、执行耗时）
        → 无外部回包（不涉及网络响应）
```

**Scheduler 的关键差异**：
- 触发源是**时间事件**（cron/ticker/timer），而非网络请求
- **无外部回包**：执行结果影响 history/metrics/retry 决策
- 内置**重试+backoff 机制**，由 adapter 层处理而非业务 handler
- 支持**限流**（`acquireSlot`/`releaseSlot`）和**唯一执行锁**（`UniqueLocker`）
- 有完整的**运行历史**和**指标收集**体系

### 11.2 六协议在统一执行链中的差异点

上述链路中，`Runtime.Execute` 完全一致，差异只出现在三处：

1. **Router.Match 的 matcher 不同**
   - HTTP：Radix Tree（method + path）
   - gRPC：service/method 字符串匹配
   - GraphQL：field name 匹配
   - WS：event name 匹配
   - MQ：topic 匹配
   - Scheduler：trigger kind 匹配

2. **HandlerContext 构建方式不同**（数据来源不同，但最终投影为统一结构）

3. **响应写回方式不同**
   - HTTP：`writeHTTPResponse`（状态码 + header + body）
   - gRPC unary：直接 return；stream：通过 wrapper 发送
   - GraphQL：`data/errors/extensions`
   - WS：emit response/error event
   - MQ：ack/nack
   - Scheduler：记录状态/metrics

#### 12.1.1 DSL 声明层

定义 Builder 模式的结构体，提供链式调用的声明 API：

```go
// ===== amqp/dsl.go =====
package amqp

import (
    "github.com/sao-lang/lania-g/kernel/v3/registry"
)

// 消费定义：描述一个 AMQP 队列消费者的声明
type ConsumerDefinition struct {
    Queue       string
    Exchange    string
    RoutingKey  string
    Handler     any
    MethodName  string
    Middlewares []any
    // ...
}

// ConsumerBuilder 用于声明一个 AMQP 消费者
type ConsumerBuilder struct {
    queue      string
    exchange   string
    handler    any
    methodName string
    middlewares []any
    registry   *registry.Registry
}

// On 声明消费者监听的路由键，返回 HandlerBuilder
func (cb *ConsumerBuilder) On(routingKey string, handler any) *HandlerBuilder {
    return &HandlerBuilder{
        consumerBuilder: cb,
        routingKey:      routingKey,
        handler:         handler,
        // 通过 adapter.FindMethodName 从方法表达式提取方法名
        methodName:      FindMethodName(cb.handler, handler),
        middlewares:     make([]any, 0),
    }
}

// HandlerBuilder 用于配置单条消费路由的详细信息
type HandlerBuilder struct {
    consumerBuilder *ConsumerBuilder
    routingKey      string
    handler         any
    methodName      string
    middlewares     []any
    sealed          bool
}

// UseMiddlewares 为当前消费追加中间件
func (hb *HandlerBuilder) UseMiddlewares(items ...any) *HandlerBuilder {
    if hb.sealed { return hb }
    hb.middlewares = append(hb.middlewares, items...)
    return hb
}

// AutoAck 标记当前消费者为自动确认模式（终结方法）
func (hb *HandlerBuilder) AutoAck() *ConsumerBuilder {
    hb.sealed = true
    // 设置 ack 模式...
    return hb.consumerBuilder
}

// ConsumerBuilder.Build 将所有声明写入 Registry
func (cb *ConsumerBuilder) Build() {
    items := cb.collectDefinitions()
    cb.registry.RegisterDecl("amqp", "consumers", items...)
}
```

#### 12.1.2 ProtocolPlugin

实现 `compiler.ProtocolPlugin` 接口的三个方法：

```go
// ===== amqp/plugin.go =====
package amqp

import (
    "github.com/sao-lang/lania-g/kernel/v3/compiler"
    "github.com/sao-lang/lania-g/kernel/v3/module"
    "github.com/sao-lang/lania-g/kernel/v3/registry"
    "github.com/sao-lang/lania-g/kernel/v3/runtime"
)

const PluginID = "amqp"
var Protocol runtime.Protocol = "amqp"

type Plugin struct{}

func (p *Plugin) ID() string                          { return PluginID }
func (p *Plugin) Protocol() runtime.Protocol           { return Protocol }

// Register：向 registry 注册 AMQP 默认的 binding resolver
func (p *Plugin) Register(reg *registry.Registry) {
    // 例如注册一个从消息体反序列化的 binding：
    // reg.RegisterBindings(NewMessageBindingResolver())
}

// Scan：从 registry 读取声明，解析 module owner
func (p *Plugin) Scan(moduleRef *module.ModuleRef, reg *registry.Registry) (any, error) {
    // 使用编译器提供的 ScanResolvedRegistryItems 辅助函数，
    // 自动完成 owner 推导：
    return compiler.ScanResolvedRegistryItems(
        PluginID, moduleRef, reg,
        "amqp plugin scan requires an explicit registry",
        compiler.SnapshotOwnerOptions{
            Controllers: true,
            Resolvers:   true,
            Providers:   true,
        },
        "consumers",                    // registry 中的 kind
        func(raw any) (*ConsumerDefinition, bool) {
            def, ok := raw.(*ConsumerDefinition)
            return def, ok && def != nil
        },
        func(def *ConsumerDefinition) any    { return def.Handler },
        func(def *ConsumerDefinition) string { return def.Queue },
        nil,  // 额外信息
        func(def *ConsumerDefinition, owner compiler.ModuleOwner, token reflect.Type) *consumerOwnership {
            return &consumerOwnership{
                definition:      def,
                moduleKey:       owner.ModuleKey,
                moduleContainer: owner.Container,
                handlerToken:    token,
            }
        },
    )
}

type consumerOwnership struct {
    definition      *ConsumerDefinition
    moduleKey       string
    moduleContainer *di.Container
    handlerToken    reflect.Type
}

// Compile：将扫描结果编译为 runtime 可安装的产物
func (p *Plugin) Compile(scan any, reg *registry.Registry,
    global registry.GlobalAOPRegistration) (*compiler.CompiledProtocol, error) {

    result := scan.(*scanResult) // 上一步 Scan 的返回值
    routes := make(map[string]*runtime.Handler)
    routeContainers := make(map[string]*di.Container)

    for _, owned := range result.consumers {
        // 编译 handler：通过 runtime.NewHandlerByToken 创建 Token 模式 handler
        handler, err := runtime.NewHandlerByToken(owned.handlerToken, owned.definition.MethodName)
        if err != nil { return nil, err }

        // 合并 AOP 计划
        plan := compiler.CompileAOPPlan(global, compiler.AOPSources{
            Middlewares: owned.definition.Middlewares,
        })
        handler.Meta.CompiledAOP = &plan
        handler.Meta.RouteKey = "amqp:" + owned.definition.Queue + ":" + owned.definition.RoutingKey
        handler.Meta.Protocol = Protocol

        routes[handler.Meta.RouteKey] = handler
        routeContainers[handler.Meta.RouteKey] = owned.moduleContainer
    }

    return &compiler.CompiledProtocol{
        Protocol:        Protocol,
        Routes:          routes,
        RouteContainers: routeContainers,
        Install: func(router *runtime.Router) error {
            // 将路由安装到 router 的 matcher 中
            matcher := newAMQPMatcher()
            for key, handler := range routes {
                matcher.Add(key, handler)
            }
            return compiler.ProtocolInstaller(Protocol, matcher, routes)(router)
        },
    }, nil
}
```

#### 12.1.3 Adapter

实现 `adapter.Adapter` 接口：

```go
// ===== amqp/adapter.go =====
package amqp

import (
    "github.com/sao-lang/lania-g/kernel/v3/adapter"
    "github.com/sao-lang/lania-g/kernel/v3/compiler"
    "github.com/sao-lang/lania-g/kernel/v3/runtime"
)

type AMQPAdapter struct {
    host    adapter.Host
    runtime *runtime.Runtime
    api     *API
    conn    *AMQPConnection // 真实的 AMQP 连接
}

func NewAdapter() *AMQPAdapter {
    return &AMQPAdapter{api: &API{}}
}

func (a *AMQPAdapter) ID() string   { return PluginID }
func (a *AMQPAdapter) API() any     { return a.api }

func (a *AMQPAdapter) Mount(host adapter.Host) error {
    a.host = host
    a.runtime = host.Runtime()
    a.api.reg = host.Registry() // DSL 写入目标 registry
    return nil
}

// Plugins 暴露协议插件，让 Application 自动收集
func (a *AMQPAdapter) Plugins() []compiler.ProtocolPlugin {
    return []compiler.ProtocolPlugin{&Plugin{}}
}

func (a *AMQPAdapter) Start() error {
    // 启动 AMQP 连接，开始消费消息
    conn, err := Dial(a.config)
    if err != nil { return err }
    a.conn = conn
    // 启动消费循环...
    go a.consumeLoop()
    return nil
}

func (a *AMQPAdapter) Stop() error {
    if a.conn != nil {
        return a.conn.Close()
    }
    return nil
}

// consumeLoop 是 AMQP 的消息消费循环（简化）
func (a *AMQPAdapter) consumeLoop() {
    for msg := range a.conn.Deliveries() {
        // 构造 HandlerContext
        ctx := &runtime.HandlerContext{
            Protocol: Protocol,
            Request: &runtime.Request{
                Raw: msg,
            },
            Container: a.runtime.GetExecutor().NewChildContainer(),
        }
        // 匹配路由并执行
        a.runtime.Execute(ctx)
    }
}
```

### 12.2 封装一个新的 Integration（以 Redis 为例）

封装一个新的 Integration 需要三步：定义 `ForRoot` 创建模块、实现 Module 的 Init 注册 binding、在 handler 中自动注入。下面以 Redis 客户端为例。

#### 12.2.1 完整代码

```go
// ===== integrations/redis/v3/module.go =====
package redis

import (
    "context"
    "reflect"

    "github.com/redis/go-redis/v9"
    "github.com/sao-lang/lania-g/kernel/v3/di"
    coreintegration "github.com/sao-lang/lania-g/kernel/v3/integration"
    "github.com/sao-lang/lania-g/kernel/v3/module"
    "github.com/sao-lang/lania-g/kernel/v3/registry"
)

// RedisConfig 是 Redis 集成模块的配置项
type RedisConfig struct {
    Addr     string
    Password string
    DB       int
}

// Module 是 Redis 集成模块的结构体
type Module struct {
    *module.BaseModule
    client *redis.Client
    config RedisConfig
    reg    *registry.Registry
}

// ForRoot 创建 Redis 集成模块，注册 client、config 到 DI 容器
func ForRoot(cfg RedisConfig) (module.Module, error) {
    // 1. 创建 Redis 客户端实例
    client := redis.NewClient(&redis.Options{
        Addr:     cfg.Addr,
        Password: cfg.Password,
        DB:       cfg.DB,
    })

    // 2. 准备 DI token
    clientToken  := reflect.TypeFor[*redis.Client]()
    configToken  := reflect.TypeFor[*RedisConfig]()
    factoryToken := reflect.TypeFor[Factory]()

    // 3. 创建 di.Provider：将实例包装为 provider，scope 为 Singleton
    pClient,  _ := di.ProviderFromInstanceWithToken(clientToken, client, di.Singleton)
    pConfig,  _ := di.ProviderFromInstanceWithToken(configToken, &cfg, di.Singleton)
    pFactory, _ := di.ProviderFromInstanceWithToken(factoryToken, Factory(func() *redis.Client {
        return redis.NewClient(&redis.Options{Addr: cfg.Addr})
    }), di.Singleton)

    // 4. 创建 BaseModule，providers 和 exports 同时注册
    base := module.NewBaseModule(&module.ModuleMetadata{
        Providers: []*di.Provider{pClient, pConfig, pFactory},
        Exports:   []interface{}{clientToken, configToken, factoryToken},
    })

    return &Module{
        BaseModule: base,
        client:     client,
        config:     cfg,
    }, nil
}

// SetRegistry 注入 registry（由 ModuleLoader 在加载时自动调用）
func (m *Module) SetRegistry(reg *registry.Registry) {
    m.reg = reg
}

// Init 初始化模块，先调用 BaseModule.Init() 将 provider 注册到 DI 容器，
// 再调用 RegisterContainerBindings 注册自动注入 binding
func (m *Module) Init() error {
    // 5. 先调用基类 Init，将 provider 实例化并注册到容器
    if err := m.BaseModule.Init(); err != nil {
        return err
    }

    // 6. 注册 container binding：当 handler 参数类型为 *redis.Client 时，
    //    自动从请求级 DI 容器注入
    coreintegration.RegisterContainerBindings(m.reg,
        coreintegration.NewBindingEntryFor[*redis.Client]("RedisClient"),
        coreintegration.NewBindingEntryFor[*RedisConfig]("RedisConfig"),
        coreintegration.NewBindingEntryFor[Factory]("RedisFactory"),
    )

    return nil
}

// OnModuleDestroy 关闭 Redis 连接（模块级生命周期）
func (m *Module) OnModuleDestroy() error {
    if m.client != nil {
        return m.client.Close()
    }
    return nil
}

// Factory 是 Redis 客户端工厂类型，方便按需创建新连接
type Factory func() *redis.Client

// OnApplicationBootstrap 在应用启动后检查 Redis 连接（应用级生命周期）
func (m *Module) OnApplicationBootstrap() error {
    return m.client.Ping(context.Background()).Err()
}
```

### 12.3 注册一个新的自动绑定类型

有三种方式，分别适用于不同场景。下面各举一个完整示例。

#### 12.3.1 方式一：协议侧（编译期注册）

适合需要从请求数据中提取值的新参数类型。例如为 AMQP 协议添加一个 `Message[T]` 绑定类型，自动从消息体反序列化：

```go
// ===== amqp/binding.go =====
package amqp

import (
    "reflect"
    "github.com/sao-lang/lania-g/kernel/v3/runtime"
    "github.com/sao-lang/lania-g/kernel/v3/registry"
)

// Message 是一个泛型包装类型，业务 handler 用它声明"从消息体反序列化"
type Message[T any] struct {
    Value T
}

// messageBindingResolver 匹配 Message[T] 类型，从消息体反序列化
type messageBindingResolver struct{}

func (r *messageBindingResolver) Name() string { return "Message" }

func (r *messageBindingResolver) AllowedProtocols() map[runtime.Protocol]bool {
    return map[runtime.Protocol]bool{"amqp": true} // 仅限 AMQP 协议
}

func (r *messageBindingResolver) Match(t reflect.Type) (runtime.WrapperDescriptor, bool) {
    // 匹配逻辑：检查类型名是否为 Message[...]，且包路径匹配
    if t.Kind() == reflect.Struct {
        name := t.Name()
        if pkg := t.PkgPath(); pkg == PackagePath() && strings.HasPrefix(name, "Message[") {
            inner := t.Field(0).Type // 取第一个字段 Value 的类型
            return runtime.WrapperDescriptor{
                Kind: "Message", WrapperType: t, InnerType: inner,
            }, true
        }
    }
    return runtime.WrapperDescriptor{}, false
}

func (r *messageBindingResolver) Resolve(ctx *runtime.HandlerContext, desc runtime.WrapperDescriptor) (interface{}, error) {
    // 从 ctx.Request.Raw 取出原始 AMQP 消息
    msg := ctx.Request.Raw.(*AMQPMessage)
    // 反序列化 JSON body 为 InnerType
    result := reflect.New(desc.InnerType).Interface()
    if err := json.Unmarshal(msg.Body, result); err != nil {
        return nil, err
    }
    // 包装回 Message[T]
    wrapper := reflect.New(desc.WrapperType).Elem()
    wrapper.Field(0).Set(reflect.ValueOf(result).Elem())
    return wrapper.Interface(), nil
}

// 在 Plugin.Register() 中注册
func (p *Plugin) Register(reg *registry.Registry) {
    reg.RegisterBindings(&messageBindingResolver{})
}
```

#### 12.3.4 三种方式的本质对比

```text
方式一（协议侧）：
    Plugin.Register(reg) → reg.RegisterBindings(resolver)
    → resolver 实现完整的 Match/Resolve 逻辑
    → 适合：需要从请求数据中按协议规则提取值的场景（如 HTTP 的 Body[T]、AMQP 的 Message[T]）

方式二（Integration 侧）：
    Module.Init() → RegisterContainerBindings(reg, entries...)
    → 自动创建 containerBindingResolver（精确类型匹配 + 从容器取值）
    → 适合：服务/配置实例的自动注入（如 *redis.Client、*swagger.Builder）

方式三（运行期）：
    executor.RegisterBindingFunc(matcher, resolver)
    → 直接在运行期实例注册
    → 适合：测试 mock、临时扩展、热修复
```

### 12.4 自动绑定类型的注册时机总结

| 注册方式 | 时机 | 作用域 | 适用场景 |
| --- | --- | --- | --- |
| `Plugin.Register()` | 编译期 | 全局（registry） | 协议侧内置绑定类型 |
| `Module.Init()` 中 `RegisterContainerBindings` | 模块初始化 | 全局（registry） | Integration 的服务/配置注入 |
| `Executor.RegisterBindingFunc()` | 运行期 | 运行时实例 | 单测覆盖、临时扩展 |

## 13. 推荐阅读与速查

### 13.1 最值得先理解的几条关键链路

1. **业务启动链路**：`cmd/*-app-demo → application/v3 → kernel/v3/module`
2. **协议编译链路**：`protocol/*/v3 DSL → registry → compiler → runtime`
3. **请求执行链路**：`adapter transport → HandlerContext → Router → Executor → Binding/DI → AOP → handler`
4. **Integration 注入链路**：`ForRoot(...) → module exports/providers → binding 注册 → handler 自动注入`

### 13.2 一句话总结

- `application` 负责装配和启动
- `kernel` 负责模块、编译、运行时、DI 和 AOP
- `protocol` 负责声明、编译协议产物和对外 transport
- `integrations` 负责把外部能力标准化接入
- `cmd` 负责给出最小样板和能力演示
- 所有协议最终在运行期汇合到统一的 `runtime` 执行模型

因此这个仓库的核心不是"每个协议各跑一套"，而是"多协议共享一套编译与执行骨架，再用 integration 把外部能力挂进来"。
