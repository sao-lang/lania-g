# lania-g 模块与链路全景说明

## 1. 文档目标

本文档用于系统说明当前 `lania-g` 仓库的：

- 工作区由哪些模块组成
- 每个模块分别负责什么
- 模块之间如何联动、通信和传递上下文
- 一条业务声明从“写入 DSL”到“运行期执行”的完整路径
- 每种协议与横切能力在链路中的位置

如果只记一句话，可以先记住当前项目的主线：

```text
Module
  -> Application
  -> Protocol Module / Integrations
  -> Registry
  -> Compiler
  -> Runtime
  -> Adapter Transport
  -> Handler
```

它不是一个“按单体应用拆 service”的仓库，而是一个 **Go 多 module 工作区**。根目录主要负责组织工作区和文档；真正对外提供能力的模块分散在 `application`、`kernel`、`protocol`、`integrations`、`cmd` 这些目录下。

## 2. 总体架构心智模型

当前项目最重要的设计思想有三点：

1. **声明与执行分离**
   - 协议层 DSL 先把路由、服务、事件、AOP 等声明写入 `registry`
   - 编译阶段再把声明转成 runtime 可执行产物
2. **协议差异前移到编译与 transport**
   - HTTP、GraphQL、gRPC、WS、MQ、Scheduler 各自保留协议语义
   - 但运行期统一复用 `runtime.HandlerContext + Router + BindingRegistry + Pipeline + Executor`
3. **外部能力走 integration**
   - 认证、日志、ORM、OTel、事件总线、健康检查等能力不直接塞进内核
   - 而是通过 `integrations/*/v3` 以模块化方式装配进应用

对应到代码，主分层如下：

```text
application/v3           应用装配与生命周期
kernel/v3                内核基础设施
protocol/*/v3            协议适配器、DSL、编译插件
integrations/*/v3        外部能力接入与桥接
cmd/                     示例与样板工程
docs/                    文档
```

## 3. 工作区模块总览

- `protocol/graphql/v3`
- `protocol/grpc/v3`
- `protocol/http/v3`
- `protocol/mq/v3`
- `protocol/scheduler/v3`
- `protocol/ws/v3`
- `integrations/auth/v3`
- `integrations/cache/v3`
- `integrations/config/v3`
- `integrations/es/v3`
- `integrations/events/v3`
- `integrations/grpc/v3`
- `integrations/http/v3`
- `integrations/kafka/v3`
- `integrations/logger/v3`
- `integrations/minio/v3`
- `integrations/mongodb/v3`
- `integrations/otel/v3`

这意味着：

- 根目录不是唯一的发布模块
- 每个子目录都可以独立演进
- `cmd` 只负责消费这些模块，不是框架底座本身

### 3.2 `application/v3`

`application/v3` 是应用装配入口，负责把“模块树 + registry + runtime + protocol adapter + 生命周期”组装成一个可以启动的应用实例。

它的职责主要有：

- 创建应用实例
- 接收显式 `Registry`
- 调用 `ModuleLoader` 加载模块树
- 创建并持有 `runtime.Runtime`
- 挂载 adapter 与 protocol plugin
- 生成 `CompileDiagnostics()` 和 `StartupReport()`
- 在 `Run()` / `Listen()` 前触发编译与安装
- 协调生命周期回调

关键文件：

- [application/v3/application.go](../application/v3/application.go)
- [application/v3/runtime.go](../application/v3/runtime.go)
- [application/v3/lifecycle.go](../application/v3/lifecycle.go)
- [application/v3/startup_report.go](../application/v3/startup_report.go)
- [application/v3/http_mount.go](../application/v3/http_mount.go)

一句话理解：`application` 不负责协议细节，也不负责具体业务逻辑，它负责把所有零件装成一台能启动的机器。

### 3.3 `kernel/v3`

`kernel/v3` 是内核基础设施层。它不关心你使用 HTTP 还是 gRPC，也不关心你接的是 ORM 还是 MongoDB。它负责提供协议无关的底座能力。

#### `kernel/v3/module`

职责：

- 定义模块模型
- 表达 `imports/providers/controllers/resolvers/exports`
- 递归加载模块树
- 组织模块级生命周期
- 构造 `ModuleRef`

它解决的是“一个应用由哪些模块组成、这些模块如何导入和导出依赖”。

#### `kernel/v3/di`

职责：

- 提供依赖注入容器
- 支持按类型和 token 取值
- 支持父子容器
- 支持 request-scope child container

它解决的是“handler 执行时，参数或 provider 从哪里取实例”。

#### `kernel/v3/registry`

职责：

- 存放协议声明、事件声明、AOP 声明和各类编译输入
- 为编译阶段提供统一读取入口
- 区分实例级 `Registry` 与兼容性的 `registry.Global()`

它解决的是“声明写到哪里、编译从哪里读”。

#### `kernel/v3/compiler`

职责：

- 调用各协议 plugin 注册默认声明
- 扫描 registry 中的声明
- 推导声明归属模块和 owner
- 生成 runtime 可安装产物
- 汇总路由、绑定、AOP、fallback inventory

它解决的是“如何把静态声明变成运行期可执行结构”。

#### `kernel/v3/runtime`

职责：

- 统一协议无关的运行期上下文
- 路由匹配
- 参数绑定
- AOP 执行链
- handler 调用
- 错误和返回值归一化

它解决的是“请求真正进来之后如何执行”。

#### `kernel/v3/aop`

职责：

- middleware
- guard
- pipe
- interceptor
- filter

它解决的是“横切逻辑如何按统一方式附着到 handler 执行链上”。

#### 其他子包

- `graph`：依赖图与归属分析
- `errors`：内核错误模型
- `scanner`：声明扫描辅助
- `integration`：integration 注入桥与公共 helper
- `metadata`：元数据读写
- `adapter`：application 与 adapter 之间的最小契约

一句话理解：`kernel` 是协议无关的基础设施层，是整套框架最核心的底盘。

### 3.4 `protocol/*/v3`

协议层负责三件事：

1. 提供 DSL，写声明
2. 提供 plugin，编译声明
3. 提供 adapter/transport，对外提供协议服务

#### HTTP：`protocol/http/v3`

职责：

- 提供 `Controller(...).Get/Post/...` 这类 DSL
- 编译 HTTP 路由、owner、参数计划、AOP 计划
- 把 HTTP 请求转换成统一 `HandlerContext`
- 负责共享监听或挂载到宿主 HTTP 服务

典型使用入口是 `httpadapter.New()` 和 `httpAdapter.API().Controller(...)`。

#### GraphQL：`protocol/graphql/v3`

职责：

- 提供 Query/Mutation/Resolver 声明入口
- 构建 schema
- 将 resolver 声明编译为 runtime handler
- 提供 GraphQL transport 和 playground 支持

它的特殊点在于：GraphQL 不按传统 REST route 组织，而是按 schema、field、resolver 组织。

#### gRPC：`protocol/grpc/v3`

职责：

- 提供 service/method DSL
- 编译 gRPC 方法声明
- 运行期动态注册 `grpc.ServiceDesc`
- 把请求桥接到统一 runtime 执行链
- 支持 unary、server streaming、client streaming、bidi streaming 四种模式

它的特殊点在于：既要保留 gRPC 协议语义，又要复用 runtime、binding、AOP、DI。

#### WebSocket：`protocol/ws/v3`

职责：

- 提供 gateway / event handler DSL
- 编译消息事件与 gateway 归属
- 在运行期把 socket 事件转到统一执行链

它的特殊点在于：请求不是标准 HTTP request/response，而是长期连接上的事件驱动消息。

#### MQ：`protocol/mq/v3`

职责：

- 提供消息消费声明 DSL
- 统一抽象消费端口、驱动接入与编译安装流程
- 让 Kafka 等驱动复用统一消费执行模型

它的特殊点在于：处理对象是消息而不是同步请求。

#### Scheduler：`protocol/scheduler/v3`

职责：

- 提供定时任务声明 DSL
- 将任务声明编译为调度任务
- 把每次定时触发转入统一 runtime 执行

它的特殊点在于：触发来源不是网络请求，而是时间事件。

### 3.5 `integrations/*/v3`

integration 层用于接入外部基础设施与横切能力。大多数 integration 都会做三件事：

1. 通过 `ForRoot(...)` 创建模块
2. 将默认实例、命名实例、配置、工厂注册到 DI 容器
3. 在初始化阶段注册对应 binding，支持 handler 直接注入

下面按功能分组说明。

#### 基础接入类

| 模块 | 主要功能 | 对外导出 | 在链路中的作用 |
| --- | --- | --- | --- |
| `auth` | 认证、授权、RBAC、tenant context | auth service、config、factory、binding | 在 HTTP/gRPC 等链路中提供用户、token、角色、权限注入 |
| `config` | 配置加载与注入 | loader、config、factory | 为其他模块提供统一配置来源 |
| `logger` | 默认 logger、命名 logger、工厂 | logger、config、factory | 为业务与框架提供统一日志能力 |
| `cache` | 默认缓存、命名缓存、工厂 | cache、config、factory | 作为服务层缓存能力输入 |

#### 外部客户端与数据访问类

| 模块 | 主要功能 | 对外导出 | 在链路中的作用 |
| --- | --- | --- | --- |
| `http` | HTTP 客户端集成 | client、config、factory | 供业务发起下游 HTTP 调用 |
| `grpc` | gRPC 客户端集成 | client conn、client、factory | 供业务发起下游 gRPC 调用与流式调用 |
| `orm` | ORM 数据源、多数据源、repository 相关能力 | datasource、config、factory | 作为关系型数据库接入层 |
| `mongodb` | MongoDB 客户端与 database 注入 | client、database、factory | 作为文档数据库接入层 |
| `es` | Elasticsearch 客户端与查询接入 | client、config、factory | 提供检索与索引能力 |
| `minio` | MinIO 对象存储客户端 | client、config、factory | 提供对象存储访问 |
| `kafka` | Kafka 客户端、reader/writer factory、MQ 桥接 | client、factory、mq bridge | 既是 Kafka 集成，也是 MQ 驱动桥接的一部分 |

#### 治理、可观测与桥接类

| 模块 | 主要功能 | 对外导出 | 在链路中的作用 |
| --- | --- | --- | --- |
| `events` | 事件总线、发射器、事件 handler 声明桥接 | bus、emitter、factory | 连接事件声明与事件执行 |
| `outbox` | 事务事件发布、outbox/inbox、重试与死信桥接 | service、store、dispatcher、factory | 连接数据库事务与事件投递 |
| `otel` | tracing、metrics、propagation、logger bridge | telemetry、provider、factory | 提供跨链路追踪与指标 |
| `resilience` | 超时、重试、限流、熔断、幂等 | resilience service、factory | 为 handler 或下游调用提供治理策略 |
| `swagger` | HTTP 路由到 OpenAPI 文档构建与 UI | builder、doc config、ui config | 读取 HTTP 声明生成文档 |
| `terminus` | 健康检查服务与 HTTP bridge | health service、factory | 暴露 `/health` 等健康检查入口 |

一句话理解：`integrations` 不是协议层，也不是业务层；它是把外部能力纳入框架主链路的标准接入面。

## 4. 模块之间如何联动

### 4.1 `application` 与 `kernel`

这是最核心的一组联动。

`application` 依赖 `kernel` 做几件事：

- 用 `module.Loader` 加载模块树
- 用 `registry` 保存协议与横切声明
- 用 `compiler` 把声明编译成安装产物
- 用 `runtime` 承接所有请求
- 用 `di` 为 handler 和 provider 提供实例

换句话说：

- `application` 决定“何时装配、何时编译、何时启动”
- `kernel` 决定“装配后内部如何组织、编译后如何执行”

### 4.2 `application` 与 `protocol`

`application` 通过 `UseAdapter(...)` 挂载协议 adapter。

挂载后，adapter 会向应用暴露两类能力：

1. 编译期能力
   - 提供 protocol plugin
   - 让 compiler 能扫描和编译本协议的声明
2. 运行期能力
   - 提供 transport/server
   - 把外部请求转成 `runtime.HandlerContext`

因此协议模块既参与编译，也参与运行。

### 4.3 `protocol` 与 `kernel`

协议模块与内核的连接点主要有四个：

1. **DSL -> registry**
   - 协议 DSL 把声明写入 registry
2. **plugin -> compiler**
   - 编译期由 protocol plugin 扫描并编译声明
3. **binding -> runtime.BindingRegistry**
   - 协议自带 binding 类型与 resolver
4. **transport -> runtime.Executor**
   - 请求进入 transport 后，最终交给 runtime 统一执行

这也是“协议差异前移、运行期统一”的具体落点。

### 4.4 `integrations` 与 `kernel`

integration 与内核的连接点主要有三个：

1. 向 `module` 输出 provider 和导出项
2. 向 `di` 注册默认实例、命名实例和工厂
3. 向 `registry/runtime binding` 注册对应注入包装类型

因此 integration 接入后，业务 handler 可以直接拿到：

- `InjectLogger`
- `InjectDatabase`
- `InjectClient`
- `InjectTelemetry`

这类参数，而不需要在每个 handler 内手工拼装。

### 4.5 `integrations` 与 `application/protocol`

有些 integration 只依赖内核和容器，例如 `config/logger/cache/orm/mongodb`。

有些 integration 会进一步桥接到应用或协议层，例如：

- `otel`
  - 需要与应用启动、logger 和协议请求链路对接
- `swagger`
  - 需要读取 HTTP 路由声明并挂载 HTTP bridge
- `terminus`
  - 需要对外暴露 HTTP 健康检查端点
- `auth`
  - 需要与协议 binding 和 AOP 链路配合
- `events`
  - 需要把 registry 中的事件声明挂接到事件总线
- `outbox`
  - 需要把 ORM 事务、事件发布和 dispatcher 连接起来

### 4.6 `cmd` 与其他模块

`cmd` 的职责是消费，不是定义。

一个最小样板通常只做以下事情：

1. 创建业务对象
2. 创建 root module
3. 创建 adapter
4. 创建 application
5. 通过 adapter API 写 DSL 声明
6. 调用 `CompileDiagnostics()` / `StartupReport()`
7. `Run()` 或 `Listen()`

## 5. 一条完整主链路是怎么工作的

这一节描述协议无关的总链路。所有协议都会复用这套骨架。

### 5.1 第一步：创建模块树

业务首先用 `module.CreateModule(...)` 或其他 module 构造方式定义根模块。

模块树中会放入：

- `imports`
- `providers`
- `controllers`
- `resolvers`
- `exports`

这一步解决的是“业务对象属于哪个模块、哪些对象允许被别的模块导入”。

### 5.2 第二步：创建 `Application`

应用通常通过：

```go
application.NewWithOptions(
    root,
    application.Options{Registry: application.NewRegistry()},
    adapter,
)
```

在这一阶段，`Application` 会：

1. 校验并接收显式 `Registry`
2. 调用 `ModuleLoader.LoadMultiple(root)` 加载模块树
3. 构建 `runtime.Runtime`
4. 把根容器接入 `Executor`
5. 挂载 adapter 和 protocol plugin

这一步解决的是“把模块树和协议栈装成一个可启动应用”。

### 5.3 第三步：通过 DSL 写声明到 `Registry`

此时还没有真正启动服务。

例如：

- HTTP：`Controller("/users", ctrl).Get("/ping", ctrl.Ping)`
- GraphQL：`Resolver("Query", query).Query("ping", query.Ping)`
- gRPC：`Service("UserService", svc).Method("Ping", svc.Ping)`
- WS：`Gateway("/ws/chat", gateway).On("ping", gateway.Ping)`

这些 DSL 的本质都是：

- 把声明写到 `Registry`
- 暂时不执行
- 等待编译阶段统一读取

### 5.4 第四步：编译

`CompileDiagnostics()`、`StartupReport()`、`Run()`、`Listen()` 都会触发或依赖编译。

编译期主要做下面几件事：

1. 调用各协议 plugin 的 `Register`
   - 补充默认 binding、默认声明或编译前准备
2. 调用 `Scan`
   - 从 registry 扫描本协议声明
   - 推导 owner、模块归属、容器归属
3. 调用 `Compile`
   - 生成 routes / matchers / handler plans / route containers
4. 聚合全局产物
   - `BindingRegistry`
   - `RouteContainers`
   - 全局 AOP
   - fallback inventory
5. 检查冲突
   - 例如跨协议 `routeKey` 冲突

这一步解决的是“把静态声明变成精确可执行的运行期计划”。

### 5.5 第五步：安装到 `Runtime`

编译成功后，`CompiledApp.Install(rt)` 会把产物装入 runtime：

1. 创建新的 `Router`
2. 安装各协议 matcher 和 routes
3. 把 `BindingRegistry` 注入 `Executor`
4. 把 `RouteContainers` 注入 `Executor`
5. 把全局 AOP 同步到 runtime

这一步解决的是“runtime 具体拿什么路由、什么绑定规则、什么容器来执行请求”。

### 5.6 第六步：执行生命周期

应用启动前后，`Application` 会遍历模块和 provider，触发生命周期接口。

这一阶段常用于：

- integration 初始化
- registry/moduleRef 注入
- 事件总线挂接
- bridge 安装

因此很多 integration 的真正联动点不只在 `ForRoot(...)`，还在生命周期回调里。

### 5.7 第七步：对外监听或运行

最后应用通过两种方式启动：

- `Listen(addr)`
  - 常见于 HTTP/GraphQL/WS 共享监听
- `Run()`
  - 常见于 gRPC、MQ、Scheduler 或由 adapter 自己控制监听地址的场景

### 5.8 第八步：请求进入 runtime 统一执行

请求期的统一骨架如下：

```text
client request
  -> adapter transport
  -> runtime.HandlerContext
  -> runtime.Router.Match
  -> runtime.Executor
  -> BindingRegistry / DI
  -> AOP Pipeline
  -> invoke handler
  -> adapter write response
```

这一步是整套框架真正实现“多协议统一执行”的核心。

## 6. 六条协议链路分别怎么工作

### 6.1 HTTP 链路

HTTP 链路的典型流程如下：

1. 业务通过 `httpAdapter.API().Controller(...)` 声明 controller 和 routes
2. 声明写入 `Registry`
3. HTTP plugin 在编译期扫描路由、controller owner、参数计划、AOP 计划
4. 编译得到：
   - `routeKey -> handler`
   - 模板路由 matcher
   - route 对应 module container
5. `Listen(":8080")` 时 HTTP adapter 启动服务
6. `ServeHTTP` 收到请求后：
   - 处理基础中间件
   - 构造 `HandlerContext`
   - 写入 request/response/raw object
   - 进入 runtime
7. runtime 执行 handler，结果再由 HTTP adapter 写回响应

HTTP 的特点：

- 路由匹配最典型
- 参数绑定种类最丰富
- Swagger、Auth、OTel、Terminus 等桥接最常见

### 6.2 GraphQL 链路

GraphQL 链路的典型流程如下：

1. 业务通过 `gqlAdapter.API().Resolver(...)` 声明 Query/Mutation/Resolver
2. 声明写入 `Registry`
3. GraphQL plugin 在编译期扫描 resolver、field 与 owner
4. 编译阶段构建 schema 与 field handler 映射
5. adapter 启动 GraphQL transport 和 playground
6. 一次 GraphQL 请求进入后：
   - adapter 解析 operation、field、args
   - 写入 GraphQL 相关 runtime 上下文
   - 进入 runtime 执行 field 对应 handler
7. 返回值再由 GraphQL transport 序列化为 GraphQL response

GraphQL 的特点：

- schema 是编译链路中的关键产物
- 请求不是直接按 REST path 匹配，而是按 operation/field 分发
- binding 中会包含 args、parent、selection set、info 等 GraphQL 语义

### 6.3 WebSocket 链路

WebSocket 链路的典型流程如下：

1. 业务通过 `wsAdapter.API().Gateway(...)` 声明 gateway 和事件 handler
2. 声明写入 `Registry`
3. WS plugin 在编译期解析 gateway、event 和 owner
4. adapter 启动 WebSocket 服务
5. 客户端连接建立后，事件消息进入 adapter
6. adapter 根据 event 名组装 `HandlerContext`
7. runtime 继续执行：
   - 路由或事件匹配
   - 参数绑定
   - AOP
   - handler 调用
8. adapter 把结果回写给对应连接

WebSocket 的特点：

- 连接是长生命周期对象
- 一条连接上会反复触发多次事件
- handler 更接近“事件处理”而不是“单次请求处理”

### 6.4 gRPC 链路

gRPC 链路的典型流程如下：

1. 业务通过 `grpcAdapter.API().Service(...)` 声明 service 和 method
2. 选择方法模式：
   - `Method(...)`：unary
   - `ServerStreamMethod(...)`
   - `ClientStreamMethod(...)`
   - `BidiStreamMethod(...)`
3. 声明写入 `Registry`
4. gRPC plugin 在编译期扫描 service、method、owner、参数计划
5. 编译阶段生成 runtime handler 与 `grpc.ServiceDesc`
6. adapter 启动 gRPC server，并动态注册 service
7. 请求进入后：
   - unary 把 request message 作为主请求对象
   - streaming 把 `grpc.ServerStream` 或 wrapper 放到 `Request.Raw`
8. binding 层为 handler 注入：
   - `Req[T]`
   - `ServerStream[T]`
   - `ClientStream[T]`
   - `BidiStream[Req, Resp]`
   - `RawServerStream`
9. runtime 执行 handler，adapter 再把结果桥接回 gRPC 协议语义

gRPC 的特点：

- 四种调用模式都已纳入统一执行链
- 协议流语义主要由 gRPC binding 和 transport 吸收
- 内核 runtime 主模型保持不变

### 6.5 MQ 链路

MQ 链路的典型流程如下：

1. 业务声明消息消费端口和 handler
2. 声明写入 `Registry`
3. MQ plugin 编译出消费 handler 和驱动映射
4. `integrations/kafka` 等桥接模块把真实消息系统接入
5. 消费端收到消息后，adapter/driver 构造 `HandlerContext`
6. runtime 统一执行 handler
7. handler 返回结果后，由驱动决定 ack、重试或后续处理

MQ 的特点：

- 触发源是消息中间件而不是同步请求
- Kafka 同时出现在 `protocol/mq` 和 `integrations/kafka` 两层
- 驱动桥接和业务消费链路绑定更紧

### 6.6 Scheduler 链路

Scheduler 链路的典型流程如下：

1. 业务声明 job 和调度规则
2. 声明写入 `Registry`
3. Scheduler plugin 编译出 job handler 和触发计划
4. adapter/driver 启动调度器
5. 每次时间触发时，构造 `HandlerContext`
6. runtime 执行 job handler
7. 执行结果用于记录状态、错误或后续调度决策

Scheduler 的特点：

- 触发条件是时间计划
- 没有真实网络请求，但仍复用 runtime 执行骨架

## 7. 横切链路如何工作

### 7.1 Binding 与 DI 链路

这是 handler 参数能“自动拿到值”的核心。

执行时，`Executor` 解析 handler 参数的顺序大致是：

1. 先问 `BindingRegistry`
   - 当前协议有没有对应 wrapper/resolver
2. 如果没命中，再回退到 DI 容器
   - `ctx.Container.Get(paramType)`

因此参数来源有两类：

- **协议绑定值**
  - 例如 HTTP query、path param、header、body
  - GraphQL args、parent、info
  - gRPC request、stream
- **容器实例**
  - logger、db、cache、client、service 等 integration/provider

这条链路是协议层和 integration 层发生实际汇合的地方。

### 7.2 AOP 链路

AOP 统一由 pipeline 承载。

语义顺序可以按下面理解：

```text
middleware
  -> guard
  -> input pipe
  -> interceptor
  -> handler
  -> output pipe
  -> filter
```

它的作用是：

- 把横切逻辑从业务 handler 中拆出来
- 让不同协议共享一致的治理语义

典型能力包括：

- 鉴权
- 参数校验
- 统一异常处理
- tracing/logging
- 超时和重试等外围治理

### 7.3 Events 链路

`events` integration 是框架里的事件总线桥。

典型流程：

1. 通过 `events.ForRoot(...)` 注册 `Bus/Emitter/Factory`
2. 通过 `RegisterOn/RegisterOnce/RegisterHandlers` 写入事件声明
3. 启动生命周期阶段调用 `AttachRegisteredHandlers(...)`
4. 把 registry 中的事件声明挂到 `Bus`
5. 业务通过 `Emitter` 发事件
6. 事件总线把消息分发给对应 handler

它把“声明事件处理器”和“真正挂接到运行总线”拆成了两个阶段。

### 7.4 Outbox 链路

`outbox` integration 把数据库事务和事件投递连接起来。

典型流程：

1. 业务在事务中写 outbox 记录
2. outbox service/store 保存事件
3. dispatcher 从 outbox 读取待投递事件
4. 通过 `events` 总线或外部系统投递
5. 成功后更新状态；失败则走重试或死信

它解决的是“事务提交成功但事件没发出去”这类不一致问题。

### 7.5 OTel 链路

`otel` integration 提供 tracing、metrics、propagation 和日志字段桥接。

典型流程：

1. `otel.ForRoot(...)` 创建 telemetry 模块
2. 导出 `Telemetry/TracerProvider/MeterProvider/Propagator`
3. 在应用链路中安装 bridge
4. 协议请求进入时创建或续接 trace context
5. 运行中的日志、指标和上下文字段共享同一条链路信息

它解决的是“跨协议、跨 integration 的可观测信息如何保持一致”。

### 7.6 Auth 链路

`auth` integration 把鉴权和用户上下文接入 handler 执行链。

典型流程：

1. `auth.ForRoot(...)` 创建 auth service
2. 注册 JWT / Session / API Key / RBAC 等能力
3. 协议请求进入时由 guard 或 binding 解析认证信息
4. 把 user、token、role、permission 写入上下文或通过 binding 注入
5. handler 直接获取认证相关参数

它解决的是“认证结果如何以统一方式进入业务处理”。

### 7.7 Resilience 链路

`resilience` integration 提供治理策略服务。

典型落点有两类：

- 作为 AOP 或外围执行策略
- 作为下游调用前的保护层

它负责：

- 超时
- 重试
- 熔断
- 限流
- 幂等

因此它通常不是单独存在的一条协议链，而是叠加到 handler 执行或外部调用链上的横切层。

### 7.8 Swagger 链路

`swagger` integration 主要服务于 HTTP。

典型流程：

1. HTTP DSL 写路由声明
2. 编译或 bridge 阶段读取 HTTP registry
3. 构建 OpenAPI 文档
4. 通过 HTTP bridge 暴露 Swagger UI 或文档 JSON

它解决的是“如何从框架声明直接生成文档”。

### 7.9 Terminus 链路

`terminus` integration 负责健康检查。

典型流程：

1. `terminus.ForRoot(...)` 注册健康检查服务
2. 聚合健康检查项
3. 通过 HTTP bridge 暴露 `/health` 等端点
4. 外部系统据此探活或监控

它解决的是“应用状态如何标准化暴露给平台和运维系统”。

### 7.10 Kafka 双重角色链路

`kafka` 在当前仓库中有双重角色：

1. 作为 integration
   - 提供 Kafka client、reader/writer factory
2. 作为 MQ 桥接
   - 连接 `protocol/mq` 的消费模型

这说明 Kafka 不是单纯的“外部客户端”，而是已经深入到消息协议主链路。

### 7.11 兼容与 fallback 链路

当前仓库仍保留一部分显式 compat/fallback 路径，用于兼容历史使用方式。

主要包括：

- `application.New(...)`
- `application.NewCompat(...)`
- `compiler.CompileCompat(...)`
- 各协议 `NewCompatAPI(...)`
- 若干 integration 的 `ForRootCompat(...)`
- `events.AttachRegisteredHandlersCompat(...)`
- `swagger.BuildFromHTTPRegistryCompat(...)`

当前设计倾向是：

- 普通入口要求显式传入实例级 `Registry`
- 只有显式 `Compat` helper 才继续使用全局 fallback

这条链路的存在意义不是推荐新代码继续使用，而是为了迁移期可控。

## 8. 最值得先理解的几条关键链路

如果你第一次接手这个仓库，建议优先看下面四条：

1. **业务启动链路**
   - `cmd/*-app-demo -> application/v3 -> kernel/v3/module`
2. **协议编译链路**
   - `protocol/*/v3 DSL -> registry -> compiler -> runtime`
3. **请求执行链路**

只要把这四条看清，整个项目的大部分设计都会变得顺畅。

## 10. 一句话总结

`lania-g` 当前项目可以概括为：

- `application` 负责装配和启动
- `kernel` 负责模块、编译、运行时、DI 和 AOP
- `protocol` 负责声明、编译协议产物和对外 transport
- `integrations` 负责把外部能力标准化接入
- `cmd` 负责给出最小样板和能力演示
- 所有协议最终都在运行期汇合到统一的 `runtime` 执行模型

因此，这个仓库的核心不是“每个协议各跑一套”，而是“多协议共享一套编译与执行骨架，再用 integration 把外部能力挂进来”。

## 11. DI、模块容器与实例生命周期细节

这一节补充前面没有展开的实现细节。当前项目的 DI 不是“只有一个全局大容器”，而是：

```text
每个 Module 一个独立容器
  -> Application 持有 root container
  -> 每条 route/job/subscription 对应一个 route container
  -> 每次请求/消息/任务执行时，再从 route/root container 派生 request child container
```

### 11.1 `Container` 的内部模型

`kernel/v3/di.Container` 内部维护三类核心状态：

- `providers`
  - token 到 provider 定义的映射
- `instances`
  - 已缓存实例
- `parent`
  - 父容器引用

当前这套实现里，token 虽然是任意可比较值，但大量场景直接使用 `reflect.Type` 作为 token，因此容器天然支持“按类型取值”。

查找语义不是“只查当前容器”，而是：

1. 先查当前容器是否定义 provider
2. 没命中则沿 `parent` 向上回溯
3. 如果最终找到了 provider，再根据 scope 决定实例缓存落在哪个容器

### 11.2 三种 scope 语义

当前最关键的 scope 语义是：

- `Singleton`
  - 缓存到“定义该 provider 的容器”
- `Request`
  - 缓存到当前请求的 child container
- `Transient`
  - 不缓存，每次重新创建

这意味着：

- provider 可以定义在父容器
- 但 request-scope 实例不会回写到父容器
- 同一个请求期对象只在当前 child container 内复用

这正是当前 DI 能安全支撑 HTTP/gRPC/WS/MQ/Scheduler 等请求期执行的基础。

### 11.3 provider 类型与实例创建方式

当前容器支持四类 provider：

- `class`
- `value`
- `factory`
- `existing`（别名转发）

实例创建的大致优先级是：

1. 若存在构造函数描述，则先走构造函数注入
2. 否则直接 `reflect.New`
3. 若实例实现 `Injectable`，则再执行 `Inject(container)`
4. 最后进入缓存或直接返回

需要注意两个实现细节：

- 当前已经支持构造函数注入
- 当前没有真正启用字段级自动注入，`injectFields()` 仍然是空实现

所以这套 DI 更接近：

- **构造期注入 + 容器取值 + request child 隔离**

而不是重字段注入风格的容器系统。

### 11.4 循环依赖与构造保护

容器内部使用 `resolving map[token]bool` 记录当前正在构造的 token。  
如果一个 token 在构造链里再次进入解析，就会被视为循环依赖并报错。

这套实现的特点是：

- 简单
- 成本低
- 足够覆盖当前框架的 provider 构造链

但它也意味着容器并没有做更复杂的“懒代理”或“分阶段构造”。

### 11.5 模块如何把对象放进容器

`kernel/v3/module.Module.Init()` 里，模块初始化顺序大致是：

1. 先初始化 `imports`
2. 把 import 的 `exports` 从对方容器取出实例
3. 再 `RegisterValue(...)` 到当前模块容器
4. 注册本模块的 `providers`
5. 把 `controllers/resolvers` 也注册成按类型可取的 value
6. 预实例化非 request-scope provider
7. 触发模块级生命周期

这里有一个非常重要的语义：

- `imports/exports` 不是共享容器引用
- 而是把导出实例“转抄”进当前模块容器

也就是说，模块边界是显式的，导出的也是显式的；并不存在“跨模块任意透视对方容器”的设计。

### 11.6 `imports` / `exports` / `Reexport`

`exports` 支持两种使用方式：

- 直接导出指定 token
- `ModuleReexport`

`ModuleReexport` 又分两种：

- `Reexport(module, tokens...)`
  - 只透出指定 token
- `Reexport(module)`
  - 递归展开对方模块全部 exports

这套机制的本质是：

- 让模块对外暴露能力面可控
- 避免业务直接依赖模块内部实现细节

### 11.7 全局模块并不是特殊容器

`IsGlobal` 模块的实现方式不是“特殊全局单例容器”，而是：

- `ModuleLoader` 在加载图时，把全局模块追加到其他模块的 `imports`

也就是说，全局模块仍然遵守普通模块模型，只是 loader 在应用装配阶段替你自动做了一轮导入。

### 11.8 `ModuleRef` 的角色

`ModuleRef` 不是运行时真正执行用的容器，它更像“应用模块树的只读索引视图”。

它主要提供：

- root container
- 模块树访问
- `reflect.Type -> Module` 索引
- 编译期和生命周期阶段的统一入口

但要注意：

- request-scope 解析不应该直接用 `ModuleRef` 的 root container
- 真正请求执行时，应该由 `runtime.Executor` 基于 route/root container 创建 child container

### 11.9 request child container 是怎么创建的

执行期进入 `Executor` 后，会按以下顺序选择容器：

1. 先根据 `routeKey` 查 `routeContainers`
2. 找到则从该 route 对应模块容器 `NewChild()`
3. 否则从 root container `NewChild()`
4. 把这个 child container 挂到 `ctx.Container`

后续所有 DI 解析、request-scope provider 缓存、部分 binding fallback 都发生在这个 child container 上。

这套机制带来三个效果：

- 请求级实例隔离
- 模块边界仍然保留
- route 可以优先使用自己所属模块容器，而不是退回全局 root

### 11.10 参数解析时 Binding 和 DI 的先后顺序

当前执行顺序非常明确：

1. `BindingRegistry.Resolve()` 先尝试按参数类型匹配 binding resolver
2. 如果 resolver 没找到，返回 `ErrBindingNotFound`
3. 只有在这个错误下，`Executor` 才回退到 `ctx.Container.Get(paramType)`
4. 如果 binding 已命中但失败，不会再退回 DI

所以 fallback 语义不是“binding 不行就自动 DI”，而是更严格的：

- **只有完全没有绑定器时，才走 DI**

这能避免协议 binding 错误被 DI 悄悄吞掉。

### 11.11 模块与 DI 这一层的当前取舍

这套实现的风格可以概括为：

- 不追求特别重的容器特性
- 优先把模块边界和请求期隔离做清楚
- 通过 child container 支撑 request scope
- 通过 binding + DI 双层解析支撑 handler 参数注入

它没有走那种“反射自动扫全目录、自动注册全部类型”的激进路线，而是：

- 模块显式声明
- 容器显式注册
- 生命周期显式触发

这也是当前框架可预测性比较强的原因之一。

## 12. 编译期扫描、owner 推导与安装细节

前面已经讲了“声明 -> 编译 -> 安装 -> 执行”的主链路，这里把扫描和 owner 推导的内部结构补齐。

### 12.1 `snapshot` 是什么

编译器不会直接对运行中的模块树做随手读取，而是先构建一个只读视图：`snapshot`。

它主要收集这些信息：

- `Modules`
- `Providers`
- `Controllers`
- `Resolvers`
- `ModuleOwners`
- `ControllerOwners`
- `ResolverOwners`

它的作用是：

- 把“模块树当前有哪些对象”冻结成一份只读输入
- 避免编译期到处直接碰运行时对象结构
- 为后续 owner 解析建立统一输入

### 12.2 为什么还要在 `snapshot` 之上再建 `owner index`

`snapshot` 更像原始材料；真正用于扫描归属解析的是 `SnapshotOwnerIndex`。

它内部至少维护两类索引：

- `OwnerByType map[reflect.Type][]ModuleOwner`
- `OwnerByPointer map[uintptr]ModuleOwner`

设计动机是：

- 同一个类型可能出现在多个模块
- 只按类型匹配会出现歧义
- 需要先按类型缩小候选，再按实例指针消歧

### 12.3 owner 解析的大致规则

owner 解析的大致顺序是：

1. 先看某个实例/receiver 的类型 token
2. 在 `OwnerByType` 里查候选模块 owner
3. 没有候选则判定为 `Missing`
4. 只有一个候选则直接 `Resolved`
5. 多个候选时，再用实例指针去 `OwnerByPointer` 精确消歧
6. 仍无法唯一确定则标记为 `Ambiguous`

这套模型的重要意义是：

- 支持同类型实例在多个模块中共存
- 支持 controller / resolver / provider 的真实实例归属解析
- 避免仅靠类型名做粗暴匹配

### 12.4 六协议扫描前的统一流程

编译期主流程大致如下：

1. 先对 protocol plugins 做稳定排序
2. 对每个 plugin 执行 `Register(reg)`
   - 用于补默认 binding 或协议默认声明
3. 冻结 `BindingRegistry`
4. 汇总全局 AOP、声明数量、binding 数量等诊断输入
5. 对每个 plugin 依次执行：
   - `Scan`
   - `Compile`
6. 汇总成 `CompiledApp`
7. 检查跨协议 `routeKey` 冲突
8. 生成 diagnostics 与 fallback inventory

这意味着：

- binding 注册发生在扫描编译之前
- 编译顺序是稳定的
- 每个协议不是各自独立编译完就直接运行，而是先统一收敛到 `CompiledApp`

### 12.5 各协议在扫描 owner 时的差异

虽然六协议共用一套 compiler 外壳，但 owner 扫描来源并不完全相同：

- HTTP
  - 只认 controller owner
- GraphQL
  - 认 controller 和 resolver
- WS
  - 认 controller 和 resolver
- gRPC
  - 认 controller、resolver、provider
- MQ
  - 认 controller、resolver、provider
- Scheduler
  - 认 controller、resolver、provider

这个差异直接影响：

- 扫描规则
- 歧义诊断
- route 到 module/container 的归属结果

也是为什么当前文档里一直强调 owner 规则是框架认知成本较高的一块。

### 12.6 单协议编译后会得到什么

每个协议编译后都会得到一个 `CompiledProtocol`，其核心产物包括：

- `Protocol`
- `Routes`
- `RouteContainers`
- `Install`

其中最关键的是：

- `Routes`
  - `routeKey -> handler`
- `RouteContainers`
  - `routeKey -> module container`

对单个 handler 而言，编译后会把这些信息固化进元数据：

- `RouteKey`
- `Protocol`
- `ModuleKey`
- `ParamPlans`
- `CompiledAOP`
- 以及协议专属元数据

例如 HTTP 还会补：

- status code
- header
- render/redirect

### 12.7 `routeContainers` 到底有什么用

`routeContainers` 的本质是：

- **路由级模块容器选择表**

它的作用链路如下：

1. plugin 编译单条声明时，记录 owner.container
2. 编译器汇总为 `routeKey -> container`
3. `CompiledApp.Install()` 把这份映射注入 runtime
4. `Executor` 执行请求时优先按 `routeKey` 取对应模块容器
5. 再从这个容器派生 child container

如果没有它，runtime 只能总是退回 root container，模块边界会被冲淡很多。

### 12.8 `CompiledApp.Install()` 安装时做了什么

安装步骤大致是：

1. 创建新的 `Router`
2. 按协议顺序安装 matcher / routes
3. 把 `BindingRegistry` 注入 `Executor`
4. 把 `RouteContainers` 注入 `Executor`
5. 把全局 AOP 同步到 runtime

这里要注意两个点：

- 路由和 matcher 是编译期产物，不是运行时临时解释
- runtime 安装用的是“新 Router”，不是边跑边原地拼接

### 12.9 fallback inventory 是什么

编译器和应用层会显式维护 fallback inventory，用来记录当前还有哪些兼容路径没有完全移除。

当前已明确建账的 runtime fallback 包括：

- `runtime_global_aop`
- `binding_to_di`
- `route_to_root_container`

已明确建账的 registry/read fallback 包括：

- `application_global_compat`
- `compile_registry_global_compat`
- `graphql_schema_global_read`
- `events_attach_global_read`
- `swagger_http_registry_global_read`

这套 inventory 的价值不只是“列个清单”，而是：

- 让 compat 行为显式可见
- 让 `StartupReport` 和 `CompileDiagnostics` 能输出具体来源
- 让后续继续收敛时有明确治理对象

### 12.10 编译器这一层当前的设计取舍

当前 compiler 的风格是：

- 用统一外壳收敛协议差异
- 把 owner、binding、route container、AOP 计划尽量前置到编译期
- 让 runtime 只消费产物，不重复推导

但它仍然保留少量 fallback，以兼容历史路径和低频场景。

## 13. 六协议实现细节对照

前面已经讲过六协议各自的链路，这里再从“声明粒度、扫描、transport、binding、返回写回”五个维度做一次对照，方便放到一个表里统一看。

| 协议 | 声明粒度 | 扫描/编译特征 | transport/server | binding 重点 | 返回写回 |
| --- | --- | --- | --- | --- | --- |
| HTTP | `Controller + Route(method/path)` | owner 只看 controller；编译期额外构建 method/path 树 | `net/http` 入口，解析 body/form/files/middleware，再进 runtime | body/query/param/header/form/cookie/file/auth/session/auto struct | 统一 HTTP 响应写回，支持状态码、header、redirect、render、json/string/bytes |
| GraphQL | `Resolver + Field(Query/Mutation/Object)` | 按 resolver 找 owner，再拍平成 field；routeKey 不是 path | transport 解析 GraphQL request，逐字段执行时再进入 runtime | args/parent/variables/selection-set/info | 固定写回 GraphQL `data/errors/extensions` |
| gRPC | `Service + Method`，声明期确定 RPCMode | owner 可来自 controller/resolver/provider；编译前会做签名校验 | `grpc.Server` 动态注册 `ServiceDesc`；unary/stream 分两条桥接链 | proto message、metadata、RawServerStream、ServerStream、ClientStream、BidiStream | unary 直接 return；stream 主要通过 wrapper 发消息；错误回给 gRPC 栈 |
| WS | `Gateway(namespace) + On(event)` | 按 gateway owner 解析；routeKey = event + namespace | socket 回调里组装 `HandlerContext` | message/header/socket/context/room/event | 成功 emit response event，失败 emit error event |
| MQ | `Consumer + On(topic)` | owner 可来自 controller/resolver/provider；simple protocol 编译 | driver 轮询消息，投影为 `HandlerContext` | message/header/topic/key/retry/ack/nack | 没有传统响应体；成功 ack，失败 nack |
| Scheduler | `Job(name) + Trigger` | owner 可来自 controller/resolver/provider；simple protocol 编译 | cron/ticker/timer 触发后构造 `HandlerContext` | job metadata、run id、scheduled at、context | 无外部回包；结果影响 retry、history、metrics |

### 13.1 HTTP 细节

HTTP 是当前最“全量”的协议实现，原因有三点：

1. 路由形态最复杂
2. binding 类型最多
3. 生态桥接最多

它的实现特点包括：

- 编译期额外构建模板路由 matcher tree，而不是只走 simple protocol 壳
- 请求期读取 body、query、param、form、cookie、file 等多来源输入
- 响应期有独立 `writeHTTPResponse` 逻辑，负责状态码、header、redirect、render、已写回判断
- Swagger、Auth、OTel、Terminus 等 integration 最容易挂接在这条链路上

### 13.2 GraphQL 细节

GraphQL 的关键不是 URL 路径，而是：

- schema
- resolver
- field

因此它的实现特点包括：

- 扫描时按 resolver 找 owner，再拍平成 field ownership
- transport 只负责 GraphQL request/operation 入口
- 真正的业务执行按 field 多次进入 runtime
- binding 重点不在 body，而在 args、parent、selection set、resolver info

它比 HTTP 更像“按字段执行计划驱动”的协议。

### 13.3 gRPC 细节

gRPC 最大的特殊点是同时支持四种调用模式：

- unary
- server streaming
- client streaming
- bidirectional streaming

它的实现特点包括：

- 声明期就固定 `RPCMode`
- 编译前会做签名校验
- unary 和 stream 请求走不同桥接链
- streaming 模式把原生 `grpc.ServerStream` 或 wrapper 放入 `Request.Raw`
- binding 负责把 metadata、request、stream 包装成 handler 可直接使用的强类型参数

gRPC 这一层已经尽量把流式协议差异吸收到 binding 和 transport 里，避免把 runtime 主模型搞乱。

### 13.4 WebSocket 细节

WS 更像“长连接上的事件协议”。

它的实现特点包括：

- routeKey 更接近 `namespace + event`
- 每次消息事件都重新组装一个 `HandlerContext`
- 连接对象、房间、事件名等信息会进入上下文或 binding
- 返回值不是 HTTP body，而是二次 emit 的事件消息

所以它和 HTTP 共用 runtime，但 transport 心智完全不同。

### 13.5 MQ 细节

MQ 这条链路不是请求响应模型，而是消费模型。

它的实现特点包括：

- 没有常规 server，而是 driver/session 轮询消息
- 把消息头、topic、key、重试次数、ack/nack 能力直接投影进 binding
- 业务 handler 更像“消息处理器”
- 执行成功与失败的后果主要体现为 ack/nack，而不是返回值

### 13.6 Scheduler 细节

Scheduler 最接近“时间驱动任务执行器”。

它的实现特点包括：

- routeKey 更像 `triggerKind + jobName`
- transport 不是网络适配器，而是调度器触发器
- binding 很克制，主要暴露 job metadata
- 返回值不写回外部协议，而是进入 retry、history、metrics 等后处理

## 14. 当前已经做过的优化与仍然存在的成本

用户前面专门问到了“DI 系统、反射扫描优化这些是怎么做的”，这一节单独回答。

### 14.1 已见优化点

当前代码里已经比较明确的优化包括：

#### 1. 编译顺序稳定化

protocol plugins 会先做稳定排序，再进入编译。  
好处是：

- 输出可预测
- 避免不同协议安装顺序导致行为不稳定

#### 2. `BindingRegistry` 编译期冻结

binding 注册完成后，编译期会冻结 `BindingRegistry`，运行时只消费，不再重复推导。

好处是：

- binding 规则稳定
- 运行期少做动态组装

#### 3. `BindingRegistry.Find()` 有正/负缓存

binding 匹配不是每次都全量反射扫描。  
当前实现会缓存：

- 正缓存：某类型命中了哪个 resolver
- 负缓存：某类型没有可用 resolver

好处是：

- 热路径上反射匹配成本下降
- 对大量参数解析场景更友好

#### 4. AOP 计划前置编译

全局 AOP 和局部 AOP 会在编译期收敛成 `CompiledAOP`，运行时优先直接命中，不再现拼。

好处是：

- 减少运行期拼装链路的成本
- 协议间执行模型更一致

#### 5. HTTP 路由树提前编译

HTTP 不是运行时反复解释模板路径，而是先编译成 method/path matcher tree，再安装到 runtime。

好处是：

- 请求期路由匹配更直接
- 少做模板解释

#### 6. owner 解析采用“类型命中 + 指针消歧”

owner index 并不是粗暴按类型唯一匹配，而是：

- 先按类型缩小候选
- 再按实例指针消歧

好处是：

- 允许同类型对象在多个模块共存
- 避免大量误判

#### 7. `routeContainers` 让请求直接落到模块容器

编译期提前产出 `routeKey -> container` 映射，运行时直接使用。

好处是：

- 减少 root container 污染
- request child container 可以从正确模块边界派生

#### 8. request-scope provider 启动期跳过实例化

模块初始化阶段不会预实例化 request-scope provider，也不会提前跑它们的生命周期。

好处是：

- 避免启动期开销
- 避免请求期对象被提前创建

#### 9. compat/fallback 显式建账

compat 行为不再完全隐形，而是显式进入 inventory 和 startup report。

好处是：

- 后续治理有抓手
- 用户能看见自己是否仍在走 fallback

### 14.2 当前仍然存在的反射与复杂度成本

虽然已经做了不少前置优化，但仍然有几类成本存在。

#### 1. binding 层仍然大量依赖反射

尤其是：

- HTTP 绑定 struct
- GraphQL args 到 DTO 的转换
- gRPC stream wrapper 的泛型/类型检查
- 各协议 wrapper 匹配

这部分仍然是 runtime 热路径上比较真实的反射来源。

#### 2. owner 规则还没有完全统一

当前虽然 owner 错误表达已经收敛，但 owner 来源本身仍按协议分裂：

- 有的协议只认 controller
- 有的还认 resolver/provider

这会增加理解成本，也意味着扫描规则暂时还做不到完全统一。

#### 3. `imports/exports` 是实例转抄，不是容器共享

这让边界更清楚，但也意味着：

- 初始化时要做一次实例提取与重新注册
- 模块层级多时，理解成本会提高

#### 4. 仍保留一部分 fallback

当前主路径已经比较纯，但仍保留：

- `binding_to_di`
- `route_to_root_container`
- 若干显式 compat helper

这些路径是为了兼容，但也意味着执行模型还没有完全收口到“纯编译产物 + 无 fallback”。

### 14.3 这套优化思路的本质

当前项目的优化思路不是“把反射彻底消灭”，而是：

1. 让高层行为尽量在编译期固化
2. 让运行期更多消费结构化产物
3. 把仍然存在的 fallback 和动态路径显式化
4. 在不推翻 runtime 主模型的前提下局部收缩复杂度

这也是为什么现在你会看到很多设计都是：

- 先 `Scan`
- 再 `Compile`
- 再 `Install`
- 最后运行期尽量只做匹配、绑定、执行

## 16. 四层 AOP 的详细组装链路与工作链路

### 16.1 AOP 的四层模型

框架的 AOP 系统按执行顺序从外到内分为四层五个组件。每层解决不同的问题，对应不同的执行时机和干预能力：

```text
第一层 Middleware（中间件）：洋葱模型最外层，包裹整个执行过程
  → 问题：需要在 handler 执行前后都做操作
  → 能力：可以决定是否继续调用 next()，可以在 next() 前后执行逻辑
  → 典型场景：请求日志记录请求/响应、CORS 跨域处理、请求头改写

第二层 Guard（守卫）：决定性能入检查
  → 问题：这个请求有没有权限继续？
  → 能力：一票否决——任意 guard 返回 false 即中断执行
  → 典型场景：JWT 鉴权、RBAC 权限判断、IP 白名单、接口开关

第三层 Interceptor（拦截器）+ Pipe（管道）：handler 执行的核心包裹层
  → Interceptor 问题：需要在 handler 调用前后获取返回值/错误
  → Interceptor 能力：可以拿到 handler 的 (result, error)，可以改写或重试
  → Interceptor 典型场景：Tracing 链路追踪、Metrics 指标采集、缓存命中、超时重试
  → Pipe 问题：参数从哪里来？怎么转换？返回值怎么格式化？
  → Pipe 能力：在参数进入 handler 前做 Transform，在返回值返回前做 Transform
  → Pipe 典型场景：字符串转 int、参数校验、DTO 还原、返回值脱敏

第四层 ExceptionFilter（异常过滤器）：错误发生后的统一处理
  → 问题：handler 返回了 error，怎么响应给客户端？
  → 能力：可以"消费"错误（吞掉），也可以转换后继续传播
  → 典型场景：统一错误响应格式、错误日志记录、panic 恢复
```

#### 三层使用形态

每一层都提供了三种使用方式，业务可以根据复杂度选择：

**形态一：接口实现**——适合复杂业务逻辑
业务定义一个结构体，实现对应接口（如 `Guard` 的 `CanActivate` 方法）。框架在编译期或运行期通过类型断言识别。

**形态二：函数式**——适合简单逻辑
直接传一个闭包函数（如 `GuardFunc`），框架通过函数类型适配接口。轻量，不需要定义结构体。

**形态三：延迟构造**——适合需要从 DI 容器解析的场景
传一个构造函数，框架在每次请求执行时调用构造函数产生新的实例。适合需要请求级上下文的场景。

这三种形态的统一方式是：框架内部通过 `WrapGuard`、`WrapInterceptor`、`WrapPipe` 等辅助函数，将接口形态统一转换为函数切片。这样一来，运行期的 Pipeline 只处理函数切片，不处理接口——减少了接口调用的类型断言开销，也让执行路径更可预测。

### 16.2 ExecutionContext：AOP 的统一上下文

AOP 各层不能直接依赖 `runtime.HandlerContext`（否则会造成循环依赖——AOP 在 runtime 之下），因此框架定义了一个"投影"结构 `ExecutionContext`。

这个结构把 runtime 层的信息（协议、路由、请求、响应、容器等）投影到 AOP 层可见的视图中。各层 AOP 组件只通过 `ExecutionContext` 读取上下文，不关心底层是 HTTP 还是 gRPC 还是 MQ。

创建时机在 `Pipeline.Run()` 执行前：用 `HandlerContext` 中的信息填充 `ExecutionContext`，然后传递给所有 AOP 组件。

### 16.3 AOP 的编译期组装

AOP 的所有组装工作在编译期完成，运行期只做执行。完整组装分四个阶段：

**阶段一：DSL 声明**——业务在 Builder 上声明 AOP

业务通过链式调用声明 AOP，分为两级：
- **Controller/Service 级**：作用于该 controller 下所有路由，作为"基座"
- **Route/Method 级**：仅作用于当前路由，在 Controller 级基础上"追加"

为什么要分两级？因为一个 controller 内的路由通常共享大部分治理逻辑（都需要鉴权、都需要日志），但可能有少数路由需要额外的处理（某个接口需要额外的参数校验）。两级设计避免了在每个路由上重复声明公共 AOP。

**阶段二：Build() 写入 Registry**

当业务调用 `Build()` 时，Builder 将"Controller 级 AOP + Route 级 AOP"合并且写入 `Registry`。合并规则很简单：Controller 级的 AOP 列表在前，Route 级的追加在后。ParamPipes 需要按参数索引分别合并。

**阶段三：Plugin 编译——三级 AOP 合并**

这是最关键的一步。编译期 `Plugin.Compile()` 阶段会做三级合并：

```text
全局 AOP（来自 registry.GlobalAOPRegistration）
  + Controller/Service 级 AOP（来自 RouteDefinition 的基座）
  + Route/Method 级 AOP（来自 RouteDefinition 的追加项）
  = CompiledAOP（写入 handler.Meta.CompiledAOP）
```

全局 AOP 是 application 层面注册的、对所有协议所有路由生效的 AOP；Controller 级只对该 controller 下的路由生效；Route 级只对该路由生效。

**一旦合并完成，CompiledAOP 就成为"最终权威结果"**，运行期不再做任何合并。这保证了执行顺序的可预测性，也消除了运行期合并带来的性能开销。

**阶段四：安装到 Runtime**

`CompiledApp.Install(rt)` 将编译期产出的 AOP 计划、BindingRegistry、RouteContainers 等一次性安装到 Runtime 中。至此运行期准备就绪。

### 16.4 AOP 的运行期执行链

运行期执行入口在 `Pipeline.Run()`，它按固定顺序执行各层：

```text
Pipeline.Run(ctx, handler, args)
  │
  ├─ Step 0: Panic 恢复 defer——任何 panic 都被捕获为 error，不影响进程
  │
  ├─ Step 1: 选择 AOP 来源
  │   → 优先使用 handler.Meta.CompiledAOP（编译期产物）
  │   → fallback：从全局列表 + handler 局部列表实时合并
  │
  ├─ Step 2: 构建 ExecutionContext
  │   → 将 HandlerContext 信息投影到 AOP 统一上下文
  │
  ├─ Step 3: Middleware 链
  │   → 从右向左构建嵌套调用链（洋葱模型）
  │   → 执行时从左到右：mw[0] → mw[1] → ... → next()
  │   → next() 之后执行后置逻辑
  │   → 任意 middleware 可以不调用 next() 来中断链路
  │
  ├─ Step 4: Guards 逐个执行
  │   → guard[0].CanActivate() → guard[1].CanActivate() → ...
  │   → 任一返回 false → ErrGuardRejected（一票否决）
  │   → 任一返回 error → 中断执行
  │
  ├─ Step 5: Interceptor 链（嵌套执行）
  │   → interceptor[0].Intercept() → interceptor[1].Intercept() → ... → handler()
  │   → 与 Middleware 的区别：Interceptor 可以获取返回值 (result, error)
  │   → 适合做缓存命中（直接返回缓存结果跳过 handler）、重试等
  │
  ├─ Step 6: Pipes(input)——参数到达 handler 前
  │   → 对每个入参依次执行所有 pipe.Transform()
  │   → 例如 ParseIntPipe 把 "42" 变为 42
  │   → 转换后的值替换原始参数
  │
  ├─ Step 7: Handler.Invoke——实际调用业务方法
  │   → Instance 模式：直接 method.Call(args)
  │   → Token 模式：从容器取 receiver → method.Call(args)
  │   → 约定：最后一个返回值如果是 error，视为错误
  │
  ├─ Step 8: Pipes(output)——返回值返回后
  │   → 对第一个返回值执行 pipe.Transform()
  │
  ├─ Step 9: ExceptionFilters（有 error 时执行）
  │   → 逐个执行 filter.Catch(exception, execCtx)
  │   → filter 返回 nil：已消费错误（不再传播）
  │   → filter 返回 error：继续传播（或被后续 filter 处理）
  │
  └─ 返回 (result, error)
```

#### 洋葱模型的执行顺序

Middleware 是"洋葱模型"，即执行顺序是"进入 → 进入 → handler → 返回 → 返回"：

```text
middleware[0].Use()
  → 进入前逻辑（打印日志、开启计时）
  → middleware[1].Use()
    → 进入前逻辑
    → handler()
    → 返回后逻辑
  → 返回后逻辑（计算耗时、写日志）
```

这允许 middleware 在 handler 前后都做操作，比如日志中间件可以同时记录请求和响应。

#### Interceptor 与 Middleware 的本质区别

Middleware 只接收 `next() error`，不知道 handler 返回了什么值。Interceptor 通过 `CallHandler` 接口可以获得 `(result, error)`，因此可以：
- 读取 handler 的返回值做后处理
- 在 cache 命中时直接返回缓存结果，跳过 handler
- 在发生错误时决定是否重试

### 16.5 ExceptionFilter 的错误消费机制

ExceptionFilter 的设计有一个关键语义：**返回 nil 表示"已消费该错误"**。

```text
handler 返回 error → filter[0].Catch(err)
  → filter[0] 识别为 HttpException(400, "参数错误")
  → 写入 Response 对象，返回 nil（已消费）
  → Pipeline 收到 nil → 不再传播错误
  → 上层 adapter 读取 Response 写回客户端
```

如果 filter 返回非 nil，则错误继续传播。多个 filter 可以形成链——前一个没消费的，后一个接着处理。

框架内置了 `HttpException` 类型，携带 HTTP 状态码和错误消息，专门供 HTTP adapter 读取并映射到响应。

### 16.6 AOP 的 fallback 路径

当 `handler.Meta.CompiledAOP == nil`（没有编译期产物时），Pipeline 会从全局列表和 handler 局部列表中实时收集 AOP 项并合并。这条路径记录在 `runtime_global_aop` fallback inventory 中，供启动报告和诊断输出。

## 17. 底层反射优化详解

### 17.1 优化策略的三层模型

框架没有追求"彻底消灭反射"（这在 Go 的动态分发中几乎不可能），而是采用三层递进策略：

**第一层：能前置到编译期的，绝不留到运行期**
- AOP 计划在编译期合并为 `CompiledAOP`，运行期直接读取，不做任何合并
- HTTP 路由在编译期构建为 Radix Tree（前缀树），运行期直接树匹配
- 参数的 BindingName（比如 path 中的 `:id`）在编译期钉死到 ParamPlans，运行期直接覆盖
- BindingRegistry 在编译期冻结，运行期不再增删 resolver

**第二层：必须在运行期做的反射，加缓存**
- BindingRegistry 的 Find() 有正缓存和负缓存：正缓存记住"这个类型对应哪个 resolver"，负缓存记住"这个类型没有任何 resolver 匹配"
- Handler 使用 MethodIndex（int 索引）代替 MethodByName（字符串查找）
- WrapperDescriptor（参数描述信息）缓存，同一参数类型不重复匹配

**第三层：通过类型约定减少反射不确定性**
- 泛型 wrapper（`Body[T]`、`Param[T]`）的匹配路径是固定的：包路径 + 泛型名裁剪
- 精确类型匹配（`*swagger.Builder`、`*kafka.Client`）不走模糊匹配，直接用 `==` 比较
- 后注册优先的覆盖策略减少"猜"的成本——越具体的 resolver 越后注册，优先命中

### 17.2 BindingRegistry 的正缓存和负缓存

这是 Binding 系统中最关键的优化。BindingRegistry 维护一个 `map[reflect.Type]bindingCacheEntry` 缓存，存储每个参数类型的匹配结果。

**正缓存**：某参数类型命中了某个 resolver，缓存 resolver + descriptor。后续同一参数类型直接返回，不需要再次遍历 resolver 列表。

**负缓存**：某参数类型没有任何 resolver 匹配，缓存 `ok=false`。后续同一参数类型也不需要再次遍历——直接返回"没有匹配"，走 DI fallback。

为什么负缓存很重要？因为大量 handler 参数是业务 struct（如 `*UserService`），它们没有对应的 binding resolver。如果没有负缓存，每次请求每个业务 struct 参数都要遍历全部 resolver 列表来确定"没有匹配"——这在有 30+ 个 resolver 时成本可观。

**缓存的清空时机**：当 `Register()` 被调用时（新注册了一个 resolver），缓存被清空。因为新 resolver 可能覆盖旧的匹配结果，以前缓存的"类型 A 匹配 resolver B"可能不再正确。

**性能收益对比**：

```text
假设 5 个参数、30 个 resolver：
  无缓存：每次请求 5 × 30 = 150 次 Match
  首请求：5 次 miss + 缓存回填 ≈ 150 次 Match
  后续请求：5 次 map 查找 ≈ O(1)
```

### 17.3 Handler 的两种模式：Instance vs Token

`runtime.Handler` 支持两种 receiver 解析模式，这是理解编译期产物和运行期注册的关键分水岭。

**Instance 模式**（运行期注册）：
- 编译期直接持有 receiver 的实例和方法的 `reflect.Value`
- 调用时直接 `method.Call(args)`，没有额外查找
- 缺点：编译期无法做 AOP 优化，实例是全局单例，不支持模块隔离

**Token 模式**（编译期产物）：
- 编译期只保存 receiver 的 type token（`reflect.Type`）和方法索引（`MethodIndex`）
- 编译期通过 `typ.MethodByName` 查找方法——**只做一次**，找到后记住 `m.Index`
- 运行期调用时：先从 `ctx.Container.Get(token)` 解析 receiver 实例，再用 `rv.Method(MethodIndex)` 索引方法——**只用 int 索引，不用字符串查找**
- 优点：运行期不需要做 `MethodByName`，支持模块容器隔离（每次请求从容器解析 receiver），支持热更新

这就是 MethodIndex 优化的本质——把 O(n) 的方法名查找变成 O(1) 的 int 索引。

### 17.4 编译期 AOP 计划和 Radix Tree

**AOP 计划前置**：全局 AOP + Controller 级 AOP + Route 级 AOP 在编译期合并为 `CompiledAOP`，写入 `handler.Meta.CompiledAOP`。运行期 `Pipeline.Run()` 直接读取这个预编译结果，不再做任何合并操作。

对比 fallback 路径：没有编译期 AOP 时，运行期每次请求都要做 6 次切片合并（middleware + guard + interceptor + pipe + filter + paramPipe），外加 6 次内存分配。

**HTTP 路由树前置**：HTTP 协议在编译期将所有路由构建为 Radix Tree（前缀树）。树节点分三种：
- **Static 节点**：精确字符串匹配（如 `/users`）
- **Param 节点**：路径参数匹配（如 `/:id`）
- **Wildcard 节点**：通配符匹配（如 `/*path`）

运行期匹配时，按路径段逐层走树节点，复杂度为 O(path_segments)。远优于 O(routes_count) 的逐条正则匹配。

### 17.5 Owner 解析的指针消歧

编译期 Scan 阶段需要确定"这个 controller 属于哪个模块"。但同一个类型（如 `*UserController`）可能在多个模块中出现，仅靠类型匹配会产生歧义。

解决方案是两级索引：
- **OwnerByType**：类型 → 候选 owner 列表（可能有多个）
- **OwnerByPointer**：实例指针 → 精确 owner（唯一）

解析流程：先按类型缩小候选范围，如果只有一个候选就直接确定；如果有多个候选，再用实例指针做精确消歧。如果类型有多个候选但指针不在索引中，标记为 Ambiguous。

### 17.6 编译期 ParamPlans 固化 BindingName

编译期已经知道"这个 handler 的第一个参数 `Param[string]` 对应 path 中的 `:id`"。这个信息被钉死在 `handler.Meta.ParamPlans[0].BindingName = "id"`。

运行期 binding 解析时，编译期的 BindingName 会覆盖 resolver 默认的 BindingName。这意味着运行期**不需要**重新解析路径模板来推断参数名。

### 17.7 仍然存在的反射成本

优化不能消除所有反射。以下场景仍然存在反射：
1. **HTTP `Bind[T]` 的 struct tag 解析**：遍历 struct 字段，读取 json/form 等 tag 来确定数据来源
2. **`Handler.Invoke()` 的 `method.Call(args)`**：这是 Go 反射调用的固有成本，无论如何都绕不开
3. **gRPC stream wrapper 的类型检查**：需要反射检查泛型参数是否合法的 stream 类型

框架的优化哲学是：**不在热路径上做不可缓存的重复反射，但不能消除的反射不强行消除**。前两个优化点把高频低成本的反射消除了（缓存命中后 BindingRegistry.Find 是 O(1) map 查找），剩下的反射要么是低频的（BindInto 只在用了 `Bind[T]` 时触发），要么是不可避免的（Call 本身）。

## 18. 三级 Scope 的 DI 系统组装与工作链路

### 18.1 容器的树状结构

DI 容器不是平面的单例，而是一棵树。这棵树从根节点（Root Container）开始，经过路由级节点（Route Container），到请求级节点（Request Child Container）结束。每一层都有不同的职责和生命周期。

**Root Container**：应用启动时由 ModuleLoader 构建，持有所有模块注册的 provider 定义。Singleton 作用域的实例缓存在这里，进程级别复用。

**Route Container**：每个模块拥有自己的容器。路由级独有 provider 注册在这里。编译期 `CompiledApp` 中 `routeContainers` 映射了 `routeKey → container`。

**Request Child Container**：每次请求进入时，从 route container（或 root）派生一个 child 容器。Request 作用域的实例缓存在这里，请求结束后被 GC 回收。

```text
Root Container（进程级，持有所有 Singleton 缓存）
  ├── Route Container A（模块 A 的 provider）
  │     └── Request Child（请求 A1，持有 Request-scope 缓存）
  │     └── Request Child（请求 A2）
  └── Route Container B（模块 B 的 provider）
        └── Request Child（请求 B1）
```

**查找语义**：Child 容器查找 token 时，如果自身没有 provider 定义，会沿 parent 链向上回溯到父容器、再到根容器。这意味着 Child 只需要注册自己特有的 provider（通常是 Request-scope 的），其他依赖从父链继承。

### 18.2 三级 Scope 的定义和缓存规则

三个作用域的核心区别在于实例缓存在哪个容器上：

**Singleton**：缓存在定义该 provider 的容器上。所有请求共享同一个实例。适用于无状态服务（如 Logger、Config）、线程安全的客户端（如 DB 连接池）。

**Request**：缓存在请求级 child container 上。同一请求内多次 Get 返回同一实例，不同请求之间完全隔离。适用于请求上下文（如当前用户、请求 ID）、非线程安全的对象。

**Transient**：不缓存，每次 Get 都重新创建。适用于需要每次全新实例的场景（如轻量 VO、DTO）。

缓存定位规则：框架根据 scope 和 requester 参数决定缓存位置。Singleton 存到 provider 定义所在的容器（即 Root 或 Route 容器），Request 存到 requester 参数指定的 child 容器（如果 requester 为空则退化到当前容器），Transient 不缓存。

完整的 Get 流程是：先查找 provider 定义（含 parent 回溯），再尝试从缓存读取（命中则直接返回），然后做循环依赖检测，最后创建实例并根据 scope 决定是否写入缓存。

### 18.3 Provider 的四种类型

框架支持四种 provider 创建方式，覆盖不同的使用场景：

**Value provider**：直接返回一个常量值。最简单，用于注册已创建好的实例（如 `*kafka.Client`、`*swagger.Builder`）。

**Factory provider**：通过工厂函数创建实例。可以配合 Scope 做缓存（Singleton 的 Factory 只在首次调用，Transient 的 Factory 每次调用）。

**Class provider**：通过反射构造 struct。支持两条路径：如果设置了构造函数查找器（ConstructorFinder），则走构造函数注入（构造函数的参数自动从容器解析）；否则走默认的 reflect.New + Injectable.Inject。

**Existing provider**：别名转发。解析 token A 时实际解析 token B 的实例。用于类型兼容场景。

### 18.4 构造函数注入

构造函数注入是框架最常用的注入方式。当模块设置了 ConstructorFinder 后，框架会优先使用构造函数来创建实例，而不是默认的 reflect.New。

流程如下：框架收到创建 `*UserService` 的请求 → 检查 ConstructorFinder 是否命中 UserService 类型 → 找到构造函数 NewUserService(db, cache, logger) → 对构造函数的每个参数递归调用 Container.Get() 解析依赖 → 用解析到的参数调用构造函数 → 返回实例。

这意味着你不需要在构造后手动设置依赖，框架会自动从容器中解析构造函数的每个参数。

### 18.5 模块初始化时容器的装配顺序

Module.Init() 中容器的装配顺序非常关键，它决定了模块间的依赖关系何时可用：

**Step 1 - 递归初始化 imports**：先初始化被导入的模块。只有被导入模块就绪了，才能从中提取 exports。

**Step 2 - 提取 exports 并注册**：从每个 import 模块的 exports 中取出实例（通过对方容器的 Get），然后 RegisterValue 到当前模块容器。这是实例转抄——不是共享容器引用，而是把值复制一份注册到自己的容器。

**Step 3 - 注册本模块 providers**：将模块元信息中声明的 provider 注册到容器。

**Step 4 - 注册 controllers/resolvers**：将 controller 和 resolver 实例也作为 value 注册，这样 handler 可以从容器按类型获取 receiver。

**Step 5 - 预实例化非 Request-scope**：Singleton 和 Transient provider 在启动时预构造（提前发现依赖缺失问题），Request-scope 的跳过（请求时才创建）。

**Step 6 - 触发生命周期**：如果模块实现了生命周期接口，调用相应的回调。

### 18.6 请求期的容器选择

请求进入 Executor.Execute() 时，容器选择按以下优先级进行：

1. 如果 ctx.Container 已被外部设置（比如测试中 mock 了容器），直接使用
2. 否则查 routeContainers[handler.Meta.RouteKey]，如果存在，从此容器派生 child
3. 否则从 rootContainer 派生 child

这个优先级的意义在于：模块专属的路由从模块容器派生 child，这样模块的 provider 对当前请求可见；没有专属模块容器的路由从 root 派生，只能访问全局 provider。这保证了模块边界的隔离性。

### 18.7 Binding 和 DI 的协作关系

Binding 和 DI 的关系可以概括为一句话：Binding 优先，DI 兜底。

Executor 对每个参数：先用 BindingRegistry.Find(paramType) 查找是否有 binding resolver——有则从请求中取值；没有则返回 ErrBindingNotFound，进入 DI fallback 步骤：ctx.Container.Get(paramType)。

关键语义：binding 一旦命中，无论成功失败，都不会回退到 DI。这能避免错误的 binding 配置被 DI 悄悄掩盖问题。

### 18.8 模块间容器隔离

模块通过 imports/exports 机制控制哪些对象可以被其他模块访问。

模块 A 的 exports 列表声明了"我愿意让其他人用我的哪些类型"。模块 B imports 模块 A 时，只能获取 A 的 exports 中的类型。这些类型通过实例转抄的方式注册到 B 的容器中——不是共享容器引用，而是把值复制一份。

ModuleReexport 支持递归展开：Reexport(mod) 展开对方模块的全部 exports，Reexport(mod, tokenA, tokenB) 只透出指定 token。

这种设计保证了模块边界是显式的，不存在"跨模块任意透视对方容器"的能力。

### 18.9 循环依赖检测

容器使用 resolving map 记录当前正在构造的 token。当在同一个解析链中再次遇到同一个 token 时，判定为循环依赖并报错。

检测成本很低——当前框架的 provider 构造链通常不深（一般不超过 3 层），简单的 map 检查足够覆盖。

## 19. 六协议三段式详细总览

### 19.1 三段式模型

每个协议的完整链路固定为三个阶段，由 ProtocolPlugin 接口驱动：

```text
第一段：DSL 声明（业务代码编写时）
  adapter.API().Controller(...).Get(...).Build()
  → 写入 Registry.RegisterDecl(pluginID, kind, items...)

第二段：编译期（应用启动前/触发编译时）
  compiler.Compile(moduleRef, reg, plugins...)
    ├── [Plugin.Register] 补齐默认 binding
    ├── [BindingRegistry 冻结]
    ├── [Plugin.Scan] 扫描声明，解析 owner
    ├── [Plugin.Compile] → CompiledProtocol
    └── [CompiledApp.Install → Runtime]

第三段：运行期（请求进入时）
  Transport → HandlerContext → Runtime.Execute → Response
```

### 19.2 HTTP 协议三段式

HTTP 协议是当前最"全量"的协议实现——路由形态最复杂、binding 类型最多、生态桥接最多。

**第一段 DSL 声明**：通过 `adapter.API().Controller("/users", ctrl)` 创建 ControllerBuilder，链式调用 UseGuards() 等配置 controller 级 AOP，然后通过 Get/Post/Put 等方法声明具体路由并配置路由级 AOP。最终 Build() 将收集的 RouteDefinition 写入 Registry。

DSL 层的关键设计是"两级的 AOP 继承"：Controller 级 AOP 作为基座被每个路由自动继承，Route 级 AOP 追加在其后。ParamPipes 按参数索引合并。

**第二段编译期（Plugin 三阶段）**：
- Register 阶段：注册约 30 种 HTTP binding resolver（Body[T]、Query[T]、Param[T]、Header[T]、Form、BodyBytes、IP、Host、AuthUser 等），全部限定只对 HTTP 协议生效
- Scan 阶段：使用 `ScanResolvedRegistryItems` 从 registry 读取 routes 声明，通过 controller 实例解析 owner 归属。HTTP 只认 controller owner 槽位
- Compile 阶段：将每条路由编译为 runtime.Handler（Token 模式），做三级 AOP 合并，构建 Radix Tree（CompiledHTTPTree），生成 routeKey → handler 和 routeKey → container 映射

**第三段运行期**：
请求进入 Adapter.ServeHTTP → CORS/Helmet 处理 → 解析 body/query/form/file → 构造 HandlerContext（包括 Protocol/Method/Path/Headers/Query/Body/Raw）+ HttpContext → Runtime.Execute → Router.Match（Radix Tree 匹配）→ 容器选择 → resolveArguments（BindingRegistry → DI fallback）→ Pipeline.Run（AOP 所有层）→ adapter.writeHTTPResponse（状态码/header/redirect/render）

#### 第三段：运行期（请求执行完整流程）

```text
HTTP 请求进入 :8080
  |
  +-- Adapter.ServeHTTP(w, r)
  |     |
  |     +-- CORS 处理（如果有配置）
  |     +-- Helmet 安全头（如果有配置）
  |     +-- 读取请求体到 []byte（受 maxBodyBytes 限制）
  |     +-- 解析 Form/MultipartForm
  |     +-- 构造 runtime.HandlerContext
  |     |     Protocol: "http"
  |     |     Request: {
  |     |       Method: "GET",
  |     |       Path: "/users/42",
  |     |       Headers: {"Content-Type": "application/json"},
  |     |       Query: {},
  |     |       Params: {},       // 路由匹配后会回填
  |     |       Body: nil,
  |     |       BodyBytes: []byte(...),
  |     |       Raw: &http.Request{...}  // 原始请求
  |     |     },
  |     |     Response: { Status: 200, Headers: {} }
  |     |
  |     +-- 构造 HttpContext（放入 ctx.Metadata["http.context"]）
  |     +-- 提取 auth/session（如果有）
  |     |
  |     +-- Runtime.Execute(ctx)
  |           |
  |           +-- Router.Match(ctx)
  |           |     → 按 Protocol("http") 获取 matcher
  |           |     → Radix Tree 匹配 "GET" + "/users/42"
  |           |     → 返回 Handler + Params: {"id": "42"}
  |           |     → ctx.RouteKey = "GET /users/:id"
  |           |     → ctx.Request.Params["id"] = "42"
  |           |
  |           +-- 容器选择
  |           |     → routeContainers["GET /users/:id"] 存在吗？
  |           |     → 存在 → container.NewChild()
  |           |     → ctx.Container = child
  |           |
  |           +-- resolveArguments(ctx, handler)
  |           |     → 参数[0]: Param[string]
  |           |       → BindingRegistry.Find(Param[string]) 命中
  |           |       → desc.BindingName 被 ParamPlans[0] 覆盖为 "id"
  |           |       → resolver.Resolve: ctx.Request.Params["id"] = "42"
  |           |       → 返回 Param[string]{Value: "42"}
  |           |     → 参数[1]: *UserService
  |           |       → BindingRegistry.Find 未命中（ErrBindingNotFound）
  |           |       → DI fallback: ctx.Container.Get(*UserService)
  |           |       → 返回 UserService 实例
  |           |
  |           +-- Pipeline.Run(ctx, handler, args)
  |           |     → CompiledAOP 存在，直接使用
  |           |     → Middleware Chain → Guard Chain → Interceptor Chain
  |           |     → Pipes(input) → Handler.Invoke → Pipes(output)
  |           |     → 返回 (*User, nil)
  |           |
  |           +-- 返回 (result, nil)
  |
  +-- Adapter 写回响应
        → 没有错误
        → StatusCode = handler.Meta.StatusCode (默认200)
        → Headers = handler.Meta.Headers
        → body = json.Marshal(user)
        → w.WriteHeader(200)
        → w.Write(jsonBody)
```

### 19.3 gRPC 协议三段式

gRPC 的特殊之处在于它同时支持四种调用模式（Unary、ServerStream、ClientStream、BidiStream），其声明结构也围绕 RPCMode 设计。

**第一段 DSL 声明**：通过 `adapter.API().Service("UserService", svc)` 创建 ServiceBuilder，然后调用 `Method("GetUser", handler)`（unary）、`ServerStreamMethod(...)`、`ClientStreamMethod(...)`、`BidiStreamMethod(...)` 声明具体方法，声明期就固定了 RPCMode。

**第二段编译期**：
- Register 阶段注册 gRPC binding 类型（Req[T]、ServerStream[T]、ClientStream[T]、BidiStream[Req, Resp]）
- Scan 阶段扫描 methods，解析 receiver 归属——gRPC 比 HTTP 更宽松，允许 receiver 来自 controller/resolver/provider 三个槽位
- Compile 阶段做签名校验（参数数量、stream wrapper 合法性），生成 handler 和 `grpc.ServiceDesc` 注册数据。gRPC 可以使用 `CompileSimpleProtocol` 简化编译流程

**第三段运行期**：gRPC Server 收到请求后根据 RPCMode 分发到不同处理链：
- Unary：解码 proto message → HandlerContext → Runtime.Execute → 序列化返回
- ServerStream：HandlerContext 中包含 stream wrapper，handler 通过 Send() 发送多条消息
- ClientStream：HandlerContext 中包含 stream wrapper，handler 通过 Recv() 读取多条消息
- BidiStream：双向通信，Recv()/Send() 自由组合

所有模式最终都汇入 Runtime.Execute 统一执行，差异被约束在 transport 和 binding 层。

### 19.4 GraphQL 协议三段式

GraphQL 与 HTTP/gRPC 的关键区别是：请求不是按 URL 路由分发的，而是按 operation 和 field 分发的。

**第一段 DSL 声明**：通过 `Resolver("Query", &resolver{})` 声明 Resolver，用 `Query("user", handler)` 和 `Mutation("createUser", handler)` 声明具体字段。

**第二段编译期**：Register 阶段注册 GraphQL 特有 binding（args、parent、selection-set、info）。Scan 阶段按 resolver 找 owner，然后将 resolver 的字段拍平为 field 级别的 ownership。Compile 阶段构建 GraphQL Schema，每个 field 编译为一个 runtime.Handler，routeKey 为 field 名（如 `Query.user`）。

**第三段运行期**：transport 解析 GraphQL 请求 → 提取 operation 和 field → 对每个 field 逐个进入 Runtime.Execute（binding 注入 args、parent、selection-set、info）→ 统一写回 `data/errors/extensions` 格式。

### 19.5 WebSocket 协议三段式

WebSocket 是长连接上的事件协议——与 HTTP 的单次请求-响应模型完全不同。

**第一段 DSL 声明**：通过 `Gateway("/ws/chat", gateway)` 声明 gateway，用 `On("message", handler)` 声明事件处理器。routeKey 为 event 名（如 `message`）。

**第二段编译期**：按 gateway owner 解析，生成 event → handler 映射。

**第三段运行期**：连接建立后进入事件循环，收到消息事件时构造 HandlerContext（event 名、消息体、连接对象），执行 Runtime.Execute。成功时 emit response event，失败时 emit error event。连接对象、房间信息通过 binding 注入。

### 19.6 MQ 协议三段式

MQ 不是请求-响应模型，而是消费模型。典型的驱动是 Kafka（通过 integrations/kafka 桥接）。

**第一段 DSL 声明**：通过 `Consumer("order_events")` 声明消费端口，用 `On("order.created", handler)` 声明具体 topic 处理器。

**第二段编译期**：owner 可来自 controller/resolver/provider。使用 CompileSimpleProtocol 编译，生成 topic → handler 映射。

**第三段运行期**：由 driver（如 kafka consumer）轮询消费消息，收到消息后构造 HandlerContext（message body、header、topic、key、retry count），执行 Runtime.Execute。binding 提供 Ack/Nack 函数（通过 Metadata 传递），handler 返回 nil → ack，返回 error → nack/重试。

### 19.7 Scheduler 协议三段式

Scheduler 是时间驱动的任务执行器，没有网络请求。

**第一段 DSL 声明**：通过 `Job("cleanup", handler).Trigger("@every 5m")` 声明 job 和调度规则。

**第二段编译期**：owner 可来自 controller/resolver/provider。生成 trigger → job handler 映射。

**第三段运行期**：cron/ticker 定时触发，构造 HandlerContext（job metadata、run id），执行 Runtime.Execute。结果影响 retry/history/metrics，没有外部回包。

### 19.8 六协议三段式一览表

| 协议 | DSL 入口 | Register（binding） | Scan（owner 来源） | Compile 产物 | 运行期触发 | 响应方式 |
| --- | --- | --- | --- | --- | --- | --- |
| HTTP | Controller.Get/Post/... | ~30 种 wrapper | controller | Radix Tree | 网络请求 | HTTP Response |
| gRPC | Service.Method/StreamMethod | Req/Stream wrapper | controller/resolver/provider | ServiceDesc | gRPC Request | return / stream msg |
| GraphQL | Resolver.Query/Mutation | GraphQL wrapper | controller/resolver | Schema + field map | GraphQL Request | data/errors |
| WS | Gateway.On | WS wrapper | controller/resolver | event map | Socket 事件 | emit event |
| MQ | Consumer.On | ack/nack wrapper | controller/resolver/provider | topic map | 消息到达 | ack/nack |
| Scheduler | Job.Trigger | metadata wrapper | controller/resolver/provider | trigger map | 时间事件 | metrics/retry |

## 20. Binding 系统详解与自动绑定类型实现

### 20.1 Binding 系统的设计动机

先理解为什么需要 Binding 系统。

在传统的 Go web 框架中，handler 需要手动从 request 中提取参数，每次都要重复写提取逻辑，且 handler 签名没有语义——看不出参数从哪来。

Binding 系统通过"类型即语义"的思路解决这个问题：通过 handler 参数的类型声明，框架自动推断值从哪里取。例如 `id Param[string]` 表示从 path param 取，`body Body[CreateUserReq]` 表示从请求体反序列化，`svc *UserService` 表示从 DI 容器注入。

### 20.2 Binding 系统的三层架构

Binding 系统由三层组件协作完成，每层都有明确的职责：

```text
┌─────────────────────────────────────────────────────────────────────┐
│ 第一层：BindingRegistry（参数绑定注册表）                            │
│ 位置：kernel/v3/runtime/binding.go                                  │
│ 职责：管理所有 BindingResolver 的注册、查找、缓存                    │
│ 关键设计：后注册优先、正/负缓存                                      │
├─────────────────────────────────────────────────────────────────────┤
│ 第二层：BindingResolver（参数绑定解析器接口）                        │
│ 职责：定义"如何匹配一个参数类型 + 如何为它取值"的契约                │
│ 四个方法：Name、AllowedProtocols、Match、Resolve                     │
├─────────────────────────────────────────────────────────────────────┤
│ 第三层：具体实现                                                    │
│ 协议侧实现：HTTP 的 Body[T]/Query[T]/Param[T] 等 30+ 种             │
│ Integration 侧实现：containerBindingResolver（从 DI 容器取值）       │
│ 自定义实现：用户通过 BindingRegistration 注册自己的 resolver         │
└─────────────────────────────────────────────────────────────────────┘
```

### 20.3 第一层：BindingRegistry 的工作机制

BindingRegistry 是 Binding 系统的"大脑"，它解决一个核心问题：**给定一个参数类型，找到对应的 resolver**。

#### 注册与查找规则

```text
注册：
  reg.Register(resolverA)  → 列表: [A]
  reg.Register(resolverB)  → 列表: [A, B]
  reg.Register(resolverC)  → 列表: [A, B, C]

查找（后注册优先）：
  Find(Param[string])  → 从尾到头遍历 C → B → A
                        → 谁先匹配就返回谁
```

为什么"后注册优先"？因为后面注册的 resolver 通常更具体。比如：

```text
基础注册（框架内置）：
  matchGenericWrapper("Param")  → 匹配所有 Param[T]

后面注册（业务自定义）：
  matchCustomParam()  → 只匹配 Param[UserId]
  
查找 Param[UserId] 时：
  → 先检查 matchCustomParam → 命中 → 返回
  → 不会走到 matchGenericWrapper
```

这样就可以用更具体的 resolver 覆盖默认行为。

#### 正缓存和负缓存

这里要理解缓存为什么重要。假设一个 handler 有 5 个参数，系统中有 30 个 resolver：

- **无缓存**：每次请求 5 × 30 = 150 次 Match 调用
- **首请求**：5 次 Miss + 缓存回填
- **后续请求**：5 次 map 查找（O(1)），命中率 100%

负缓存更重要——对于没有 binding 的类型（比如业务 struct），如果不缓存，每次请求都要遍历全部 30 个 resolver 来确定"没有匹配"。有了负缓存，这个遍历也只做一次。

#### 什么时候清空缓存？

当 `Register()` 被调用时缓存会被清空。原因：新注册的 resolver 可能覆盖旧的匹配结果，以前缓存的"这个类型匹配 resolver X"可能不再正确。

### 20.4 第二层：BindingResolver 的四个方法

每个 resolver 需要实现四个方法：

**Name**：返回名称用于诊断，让人知道谁处理了这个参数（如 "Body"、"Query"）。

**AllowedProtocols**：协议白名单。HTTP 的 `Body[T]` 只应给 HTTP 协议用，gRPC 的 `Req[T]` 只应给 gRPC 用，而 Integration 的服务如 `*swagger.Builder` 对所有协议可用。这解决了"跨协议参数冲突"问题——如果不加限制，gRPC 请求的 Param[string] 可能被 HTTP 的 resolver 错误拦截。

**Match**：给定参数类型，判断是否归这个 resolver 管。返回 WrapperDescriptor 说明匹配细节。

**Resolve**：运行期取值。从 HandlerContext 中提取实际值返回。

`AllowedProtocols` 的设计有什么深意？它解决了"跨协议参数冲突"的问题。例如：

```text
HTTP 协议有 Param[string]（从 path 取）
gRPC 协议也有 Param[string]（从 metadata 取）

如果没有协议限制：
  gRPC 请求进来，参数 Param[string] 被 HTTP 的 resolver 拦截
  → HTTP resolver 从 ctx.Request.Params 取值
  → 但 gRPC 的 path params 是空的
  → 返回空字符串，悄无声息地错了

有协议限制：
  gRPC 请求进来：
    → HTTP 的 Param resolver: AllowedProtocols = {http: true}
    → 当前协议是 "grpc"，不在白名单
    → 返回 ErrBindingNotSupported
    → 框架继续尝试下一个 resolver
```

### 20.5 第三层：两种匹配模式

#### 模式一：泛型 Wrapper 匹配（协议侧）

这种模式用于 `Body[T]`、`Query[T]`、`Param[T]` 这类泛型包装类型。

匹配的核心思路是"剥洋葱"：

```text
步骤 1：检查参数类型是不是 struct
步骤 2：检查这个 struct 是不是在 HTTP binding 包下
步骤 3：去掉泛型后缀 [T]（Go 的泛型在反射中名为 "Body[string]"）
步骤 4：与基础名比较（"Body"）
步骤 5：取第一个字段（Value）的类型作为 InnerType

例子：Param[string]
  → 类型名 "Param[string]"
  → 去掉泛型后缀 → "Param"
  → 匹配 baseName "Param" → 命中
  → 第一个字段 Value 的类型是 string
  → 返回 {Kind: "Param", WrapperType: Param[string], InnerType: string}
```

为什么取第一个字段？因为所有 HTTP wrapper 的约定是 `Value` 字段在第一位，`Body[T]` 和 `Param[T]` 都是如此。

#### 模式二：精确类型匹配（Integration 侧）

这种模式用于 `*swagger.Builder`、`kafka.Client` 这类集成服务。

匹配规则极其简单：**参数类型完全相等才命中**。

```text
handler 参数: client *kafka.Client
  → reflect.TypeOf(*kafka.Client)
  → 遍历 resolvers
  → containerBindingResolver.target 也是 *kafka.Client
  → t == r.target → 命中
  → 从 ctx.Container.Get(*kafka.Client) 取值
```

这里的关键设计是"精确匹配"而不是"接口匹配"。为什么不匹配接口？因为如果两个不同的集成都注入了 `interface{}`，系统就无法区分谁是谁了。精确类型匹配牺牲了一点灵活性，但换来了确定性。

### 20.6 整个参数解析的执行流程（resolveArgument）

现在把上面的所有组件串起来，看一次完整的参数解析过程：

```text
Executor.resolveArgument(ctx, handler, paramType, paramIndex)

  阶段 1：找 resolver
    → BindingRegistry.Find(paramType)
       → 查缓存
          → 有正缓存：直接返回缓存的 resolver + descriptor
          → 有负缓存：直接返回 ErrBindingNotFound → 走 DI fallback
       → 无缓存：遍历 resolvers（后注册优先）
          → 找到：回填正缓存，继续
          → 未找到：回填负缓存，返回 ErrBindingNotFound → 走 DI fallback

  阶段 2：协议校验
    → resolver.AllowedProtocols 不为空吗？
       → 是 ctx.Protocol 不在白名单中吗？
          → 返回 ErrBindingNotSupported
       → 是 ctx.Protocol 在白名单中吗？
          → 继续

  阶段 3：BindingName 覆盖
    → 编译期 ParamPlans[paramIndex].BindingName 不为空吗？
       → 用编译期的名字覆盖 resolver 默认的名字
    → 这有什么用？
       编译期已经知道 "path 中的 :id 对应 handler 的第一个参数"
       所以运行期不需要再解析路由模板

  阶段 4：取值
    → resolver.Resolve(ctx, desc)
      → 协议解析器：从 ctx.Request.Params["id"] 取值
      → Integration 解析器：从 ctx.Container.Get(*Service) 取值

  阶段 5：类型校验
    → 取到的值能赋值给参数类型吗？
       → 能：继续
       → 不能但能转换：自动转换
       → 都不能：返回类型不匹配错误

  阶段 6：参数级 Pipe
    → handler 对这个参数有注册 Pipe 吗？
       → 有：逐个执行 pipe.Transform()
       → 例如 ParseIntPipe 把 "42" 变成 42

  阶段 7：返回
    → 返回 resolved reflect.Value
```

### 20.7 Binding 系统和 DI 系统的协作关系

这是整个框架中容易混淆的地方。两者的关系可以概括为一句话：

**Binding 优先，DI 兜底。**

```text
Executor 的参数解析顺序：
  1. BindingRegistry.Resolve(paramType)
     → 有 binding：用 binding 的值
     → 没有 binding：走下一步
  
  2. ctx.Container.Get(paramType)
     → 容器中有 provider：返回实例
     → 没有 provider：报错
```

这条规则有什么实际意义？

**场景一：HTTP handler 的参数是 `Param[string]`**
```text
→ BindingRegistry 找到 Param 的 resolver
→ 从请求的 path params 取值
→ DI 不参与
→ 正确：值从请求来
```

**场景二：HTTP handler 的参数是 `*UserService`**
```text
→ BindingRegistry 遍历所有 resolver
→ 没有 resolver 匹配 *UserService
→ ErrBindingNotFound
→ DI fallback: ctx.Container.Get(*UserService)
→ 从容器中取出注册的实例
→ 正确：服务从 DI 来
```

**场景三：有人错误地注册了 `*UserService` 的 binding**
```text
→ BindingRegistry 找到 *UserService 的 resolver
→ resolver.Resolve() 从请求中取值
→ 但请求中没有 *UserService
→ 返回空值或错误
→ DI 不会参与（因为 binding 命中了）
```

这就是"先 binding 再 DI"的意义：**binding 一旦命中，不管成功失败，都不会回退到 DI**。这能避免因错误的 binding 配置而被 DI 悄悄掩盖问题。

### 20.8 两种绑定的本质差异

| 维度 | 协议绑定 | Integration 绑定 |
| --- | --- | --- |
| **匹配哲学** | 泛型类型推导（"你说 Body[T] 我就从 body 取"） | 精确类型匹配（"你说 *Client 我就从容器拿"） |
| **值从哪里来** | 从当前请求数据中提取 | 从 DI 容器中获取 |
| **有没有协议限制** | 通常有（只服务自己的协议） | 通常没有（所有协议都可注入） |
| **注册时机** | 编译期 Plugin.Register() | 模块初始化 Init() |
| **依赖什么** | 不依赖模块（框架内置） | 依赖 ForRoot() 先创建 provider |
| **典型例子** | HTTP 的 `Param[string]` | Swagger 的 `*swagger.Builder` |
| **能否自定义** | 可以，注册新的 BindingRegistration | 可以，RegisterContainerBindings |

## 21. Integration 自动绑定类型详解（Swagger + Kafka）

### 21.1 Integration 自动绑定的通用机制

所有 integration 的自动绑定通过 `kernel/v3/integration/binding.go` 中的 `RegisterContainerBindings` 完成。这个函数接收一组 `BindingEntry`（每个 entry 包含一个名字和一个 reflect.Type token），为每个 entry 创建一个 `containerBindingResolver`。

`containerBindingResolver` 的工作逻辑极其简单：

- **Match**：参数类型与 target 完全相等（`==` 比较）才命中。不做任何泛型推导或包路径检查。
- **Resolve**：从 `ctx.Container.Get(token)` 取值——直接从请求级 DI 容器获取之前由 ForRoot 注册的实例。

这种"精确类型匹配"的设计哲学和协议 binding 的"泛型 wrapper 推导"截然不同。原因很简单：Integration 侧没有"从请求中提取数据"的需求，只有"从容器中查找服务"的需求。精确匹配最安全——不会误拦截其他类型的参数。

### 21.2 Swagger 的自动绑定注入链路

Swagger 的自动绑定完整链路可以分为四步：

**第一步：ForRoot 创建实例**。用户在 `swagger.ForRoot(cfg)` 时，框架创建 `*Builder`、`Config`、`*UIConfig`、`Factory` 五个实例，并包装为 `di.Provider`（token = reflect.Type）注册到模块的 providers 和 exports。

**第二步：Init 注册 binding**。`Module.Init()` 调用 `RegisterContainerBindings`，向 registry 注册 5 个 `containerBindingResolver`。每个 resolver 知道"当 handler 参数类型是 X 时，从容器取 X 的实例"。

**第三步：编译期聚合**。compiler 从 registry 读取所有 binding resolver，组装到 BindingRegistry。

**第四步：运行期注入**。handler 参数中有 `*swagger.Builder` → BindingRegistry.Find 命中 → containerBindingResolver.Resolve 从 ctx.Container.Get(*swagger.Builder) → 返回 ForRoot 时注册的实例。

关键理解：**ForRoot 创建实例并放入容器，RegisterContainerBindings 告诉 binding 系统"这个类型可以从容器取"，两者缺一不可**。

### 21.3 Kafka 的两种绑定（精确匹配 + 命名引用）

Kafka 比 Swagger 多了一种绑定能力——命名引用绑定。它解决的是"多个同类型实例如何区分"的问题。

**精确类型绑定**：和 Swagger 一样，注册 `*kafka.Client`、`ReaderFactory`、`WriterFactory`、`Config`、`*Config`、`Factory` 等 6 个 containerBindingResolver。当 handler 参数类型精确匹配时，从容器取对应的单例。

**命名引用绑定**：当应用中有多个 Kafka 客户端（如一个处理订单消息、一个处理通知消息）时，通过 `Ref[T, Marker]` 模式区分。`Marker` 是一个标记类型（如 `OrderTopic`、`NotificationTopic`），运行时通过 Marker 的类型名推导出命名空间的名称，从容器中按名称查找对应的实例。

这和协议 binding 的泛型 wrapper 有本质区别：协议 wrapper 的泛型参数 T 是值的类型（如 `Param[string]` 中的 string），而 Ref 的泛型参数 T 是服务类型、Marker 是区分标记。

### 21.4 协议绑定 vs Integration 绑定的本质差异总结

| 特性 | 协议绑定 | Integration 绑定 |
| --- | --- | --- |
| 匹配条件 | 包路径 + 泛型名 / 命名类型完全匹配 | 类型完全相等（`t == r.target`） |
| 值来源 | 请求数据（`HandlerContext.Request` 的字段） | DI 容器（`ctx.Container.Get()`） |
| 有无协议限制 | 通常有（只对特定协议生效） | 通常无（所有协议都可注入） |
| 是否依赖请求数据 | 是 | 否 |
| 是否依赖模块注册 | 否（由 plugin Register 注入） | 是（依赖 ForRoot 创建 provider） |

## 22. 链式调用的实现

### 22.1 链式调用的设计模式

框架的 DSL 使用 **Builder 模式**实现链式调用。每个方法返回 `*Builder` 自身（或相关的子 Builder），让调用可以持续串联。

核心模式是每个`配置方法`返回自身（`*Builder`），每个`路由声明方法`返回子 Builder（`*RouteBuilder`），每个`终结方法`返回终结 Builder（`*RouteTerminalBuilder`）。

### 22.2 三种 Builder 状态切换

链式调用有清晰的状态切换：

- **ControllerBuilder**（配置阶段）：`UseGuards()` / `UseMiddlewares()` / `UsePipes()` → 返回自身，继续配置
- **ControllerBuilder → RouteBuilder**（路由声明）：`Get()` / `Post()` / `Put()` → 返回 RouteBuilder，开始配置具体路由
- **RouteBuilder**（路由配置）：`UseGuards()` / `UsePipes()` / `Summary()` / `Description()` → 返回自身
- **RouteBuilder → RouteTerminalBuilder**（终结）：`StatusCode()` / `Redirect()` / `Render()` → 返回终结 Builder，当前路由封装修路（sealed=true）
- **RouteTerminalBuilder**：只能回到 ControllerBuilder 继续声明下一条路由或调用 Build()

为什么需要 sealed 机制？因为一旦设置了 StatusCode(201)，再追加 AOP 配置的顺序语义就会混乱。sealed 标志位阻止了这种误用。

### 22.3 继承与合并

RouteBuilder 从 ControllerBuilder 继承 AOP 配置。合并发生在 `build()` 方法中：Controller 级的 Guards/Interceptors/Middlewares/Pipes/Filters 作为"基座"，Route 级的追加在其后。ParamPipes 需要按 paramIndex 分别合并——Controller 级的先，Route 级的后。

### 22.4 gRPC 的链式调用

gRPC 的链式调用模式与 HTTP 类似，只是 ServiceBuilder ↔ MethodBuilder 代替了 ControllerBuilder ↔ RouteBuilder。Service 级 AOP 作为基座，Method 级 AOP 追加。

### 22.5 链式调用的本质

链式调用的本质是**声明收集器**，它不执行业务逻辑，只负责在 Build() 时一次性写入 Registry。这也解释了为什么所有 DSL 方法都不做类型检查——它们只是把 `any` 参数收集起来，真正的类型解析和校验发生在编译期。

## 23. 从请求进来到响应出去的完整链路（含全部细节）

### 23.1 完整链路总图

以一个 HTTP 请求为例，完整走通从"声明"到"响应"的所有阶段：

```text
【阶段一：模块与启动装配】
Application.NewWithOptions(rootModule, opts, httpAdapter)
  -> ModuleLoader.LoadMultiple(rootModule)：加载模块树
  -> Module.Init()：初始化各模块，注册 provider 到容器
  -> adapter.Mount(host)：挂载 HTTP adapter
  -> adapter.Plugins()：注册 HTTP Plugin 到 compiler
  
【阶段二：DSL 声明】
adapter.API().Controller("/users", ctrl).
    UseGuards(AuthGuard{}).
    Get("/:id", ctrl.GetByID).UsePipes(ParseIntPipe{}).
    Post("/", ctrl.Create).StatusCode(201).
    Build()
  -> 创建 ControllerBuilder -> RouteBuilder
  -> BuildE() 写入 registry.RegisterDecl("http", "routes", defs...)

【阶段三：编译】
app.CompileDiagnostics() / app.Run() / app.Listen()
  -> compiler.Compile(moduleRef, reg, plugins...)
    -> [Plugin.Register] HTTP Plugin 注册 Body[T]/Query[T]/... 等 binding
    -> [BindingRegistry 冻结] 所有 resolver 编译期固化
    -> [Plugin.Scan] 扫描 registry 中的 routes 声明，解析 controller owner
    -> [Plugin.Compile]
      -> 合并 AOP（全局 + Controller + Route -> CompiledAOP）
      -> 构建 CompiledHTTPTree（Radix Tree）
      -> 编译 ParamPlans（记录每个参数的 BindingName）
      -> 生成 routeKey -> handler 映射
      -> 生成 routeContainers（routeKey -> module container）
    -> [跨协议冲突检测]
    -> [CompiledApp]
  -> CompiledApp.Install(rt)
    -> 创建新 Router
    -> 安装 matcher（HTTP 的 Radix Tree matcher）
    -> 注入 BindingRegistry -> Executor
    -> 注入 RouteContainers -> Executor
    -> 同步全局 AOP -> Pipeline

【阶段四：服务启动】
app.Listen(":8080")
  -> adapter.Start()
  -> http.Server 启动
  -> 进入 ServeHTTP 循环

【阶段五：请求处理】
HTTP Request -> ServeHTTP(w, r)
  |
  +-- adapter 层处理
  |   -> CORS/Helmet/中间件
  |   -> 解析 body/query/form/file
  |   -> 构造 HandlerContext
  |     {
  |       Protocol: "http",
  |       Request: { Method, Path, Headers, Query, Params, Body, Raw },
  |       Response: { Status: 200, Headers: {} }
  |     }
  |   -> 构造 HttpContext（放入 Metadata）
  |   -> 从 Request.Raw 提取 auth user/session 等（如果有）
  |
  +-- Runtime.Execute(ctx)
  |     |
  |     +-- Router.Match(ctx)
  |     |     -> Radix Tree 按 method + path 匹配
  |     |     -> 返回 Handler + path params
  |     |     -> ctx.RouteKey = handler.Meta.RouteKey
  |     |     -> ctx.Request.Params 回填 path params
  |     |
  |     +-- 选择容器（Executor）
  |     |     -> routeContainers[routeKey] ? NewChild() : rootContainer.NewChild()
  |     |     -> ctx.Container = child container
  |     |
  |     +-- resolveArguments(ctx, handler)
  |     |     -> 遍历 handler.Meta.ParamTypes
  |     |     -> 对每个参数：
  |     |       -> BindingRegistry.Find(paramType) [正/负缓存]
  |     |       -> 命中 -> AllowedProtocols 校验 -> resolver.Resolve()
  |     |       -> 未命中 -> ctx.Container.Get(paramType) [DI fallback]
  |     |       -> 类型校验（AssignableTo / ConvertibleTo）
  |     |       -> ParamPipes[paramIndex] 执行 Transform
  |     |
  |     +-- Pipeline.Run(ctx, handler, args)
  |     |     -> 选择 AOP 来源（编译期 CompiledAOP 优先）
  |     |     -> 构建 ExecutionContext
  |     |     -> [Middleware Chain]
  |     |       -> middleware[0].Use() -> ... -> middleware[n].Use() -> next()
  |     |     -> [Guard Chain]
  |     |       -> guard[0].CanActivate() -> ... -> guard[n].CanActivate()
  |     |       -> 任一 false -> ErrGuardRejected
  |     |     -> [Interceptor Chain]
  |     |       -> interceptor[0].Intercept() -> ... -> interceptor[n].Intercept()
  |     |     -> [Pipe(input)]
  |     |       -> 对每个入参执行 pipe.Transform()
  |     |     -> [Handler.Invoke]
  |     |       -> Instance 模式：Instance.Method.Call(args)
  |     |       -> Token 模式：Container.Get(token) -> Method.Call(args)
  |     |     -> [Pipe(output)]
  |     |       -> 对返回值执行 pipe.Transform()
  |     |     -> [ExceptionFilter]
  |     |       -> 若有 error，filter 逐个处理
  |     |     -> 返回 (result, error)
  |     |
  |     +-- normalizeError（若有 error）
  |           -> 补全 protocol/routeKey/moduleKey/paramIndex/meta
  |
  +-- adapter 写回响应
        -> 若有 error -> 映射为 HTTP 状态码 + 错误体
        -> 若无 error -> 按 StatusCode/Headers/Redirect/Render 写回
        -> 支持 json/string/bytes/redirect/render
```

### 23.2 六种协议在统一执行链中的差异点

上述链路中，阶段五的 `Runtime.Execute` 完全一致，差异只出现在：

1. **Router.Match 的 matcher 不同**
   - HTTP：Radix Tree（method + path）
   - gRPC：service/method 字符串匹配
   - GraphQL：field name 匹配
   - WS：event name 匹配
   - MQ：topic 匹配
   - Scheduler：trigger kind 匹配

2. **HandlerContext 的构建方式不同**
   - 数据来源不同：HTTP 的 body/query/param，gRPC 的 proto message/stream，MQ 的 message 等
   - 但最终都投影为统一 `HandlerContext.Request` 和 `HandlerContext.Response`

3. **响应写回方式不同**
   - HTTP：`writeHTTPResponse`（状态码 + header + body）
   - gRPC unary：直接 return
   - gRPC stream：通过 stream wrapper 发送
   - GraphQL：写回 `data/errors/extensions`
   - WS：emit response/error event
   - MQ：ack/nack
   - Scheduler：记录状态/metrics

## 24. 如何扩展

### 24.1 封装一个新的协议

要新增一个协议（比如 AMQP），需要实现四个组件：

**1. DSL 声明层**：定义 Builder 模式的结构体（如 ConsumerBuilder、HandlerBuilder），提供链式调用的 DSL API。核心是 `Build()` 方法将声明写入 Registry。

**2. ProtocolPlugin**：实现 `Register/Scan/Compile` 三个方法：
- Register：向 registry 注册该协议的默认 binding resolver
- Scan：从 registry 读取声明，使用 `ScanResolvedRegistryItems` 辅助函数解析 owner 归属
- Compile：将扫描结果编译为 `CompiledProtocol`，可复用 `CompileSimpleProtocol` 简化

**3. Adapter**：实现 adapter.Adapter 接口（ID/API/Plugins/Mount/Start），对接宿主应用的生命周期。

**4. 注册到 Application**：将 Adapter 传入 `application.NewWithOptions()`，框架自动加载其 Plugin。

### 24.2 封装一个新的 Integration

需要两步：

**ForRoot**：创建服务的实例（如 `*Client`），包装为 di.Provider（token = reflect.Type），放入模块的 Providers 和 Exports。这样实例就会在模块初始化时注册到 DI 容器。

**Init 注册 binding**：在 Module.Init() 中调用 `RegisterContainerBindings`，为每个需要自动注入的类型注册 containerBindingResolver。

之后，handler 只需在参数中声明该类型（如 `client *redis.Client`），框架就会自动从容器注入。

### 24.3 注册一个新的自动绑定类型

有三种方式，适用不同场景：

**方式一：协议侧（编译期）**。在 Plugin.Register() 中调用 `reg.RegisterBindings()`，传入实现了完整匹配逻辑的 BindingResolver。适合需要从请求数据中提取值的新参数类型。

**方式二：Integration 侧（模块初始化）**。在 Module.Init() 中调用 RegisterContainerBindings。适合让 handler 从 DI 容器注入服务实例。

**方式三：运行期注册**。直接通过 Runtime.RegisterBindingFunc() 注册。适合测试覆盖和临时扩展。

### 24.4 自动绑定类型的注册时机总结

| 注册方式 | 时机 | 作用域 | 适用场景 |
| --- | --- | --- | --- |
| `Plugin.Register()` | 编译期 | 全局（registry） | 协议侧内置绑定类型 |
| `Module.Init()` 中 `RegisterContainerBindings` | 模块初始化 | 全局（registry） | Integration 的服务/配置注入 |
| `Executor.RegisterBindingFunc()` | 运行期 | 运行时实例 | 单测覆盖、临时扩展 |
