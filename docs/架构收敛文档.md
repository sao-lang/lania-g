# v3 架构收敛文档

## 1. 目标

本文档用于沉淀当前多 module 版本的架构收敛判断，回答两个问题：

- 当前 v3 是“没有架构导致混乱”，还是“主架构已成型但边界未完全收口”
- 哪些问题需要优先治理，哪些属于可接受的框架复杂度

当前判断：

- v3 主架构已经成型，主链路清晰，核心设计不是失控状态
- 当前的“混乱感”主要来自边界未完全收口，而不是目录本身太多
- 最需要治理的是全局状态、边界不一致、协议归属规则不统一、兼容路径过厚

---

## 2. 总体结论

v3 的核心主线已经比较明确：

```text
声明 -> 编译 -> 安装 -> 执行
```

对应关系大致如下：

- `application`：应用装配与生命周期
- `adapter/*`：协议 DSL、协议插件、transport
- `binding/*`：参数绑定与默认解析器
- `core/module`、`core/di`：模块模型与容器
- `core/compiler`：编译期收敛
- `core/runtime`：统一执行内核
- `integrations/*`：基础设施集成

因此，v3 的问题不是“没有设计”，而是“设计方向已经对了，但过渡态痕迹仍然比较重”。

补充说明：

- 第二至第四阶段的阶段性结论已统一归档在本文第 `2.1` 节

---

## 2.1 阶段归档

### 第二阶段：把边界过渡态显式化

第二阶段的核心成果是让“看不清”的问题先可见、可诊断：

- `mq / scheduler` 已补齐 owner 诊断统一化
- `CompileDiagnostics` / `StartupReport` 已补充 route、module 与 fallback inventory
- 高频读路径开始显式 compat 命名，例如 `application.NewCompat(...)`、`compiler.CompileCompat(...)`
- 六协议 `Plugin.Scan(..., nil)` 的全局读取回退已进入 inventory

这一阶段的价值不在于立即删掉所有兼容层，而在于先把推荐路径、兼容路径和 internal-only 兜底区分清楚。

### 第三阶段：把默认写回退从文档推荐收紧到行为约束

第三阶段开始真正压缩默认写全局的能力面：

- `application.NewWithOptions(...)` 与 `compiler.Compile(...)` 要求显式传入实例级 registry
- 六协议 `NewAPI(nil)` 已统一补充为显式 `NewCompatAPI(...)`
- `events.Register*`、`binding/*/RegisterDefaults*`、多数 `integrations/* RegisterBindings*` 已进入统一 compat 命名体系
- integration module 的 `Module.InitDefaultFallback` 已整体收紧，普通 `ForRoot(...).Init()` 不再默认写全局

这一阶段完成后，问题重点从“默认写回退太多”转向“剩余 read fallback 和 compat 曝光还需要继续压低”。

### 第四阶段：继续压低 compat 曝光与高频 read fallback

第四阶段的重点不再是大规模清理默认写，而是继续弱化 compat 的默认存在感：

- `events.RegisterOnCompat/RegisterOnceCompat/RegisterHandlersCompat` 已可在 `StartupReport` 中单独识别
- 主文档示例已统一回到 mounted adapter 的实例 API
- 六协议 `Plugin.Scan(..., nil)` 已收紧为必须显式传入 registry
- `integrations/events.AttachRegisteredHandlers(...)` 与 `integrations/swagger.BuildFromHTTPRegistry(...)` 的普通 API nil 回退已移除，仅保留显式 compat helper

当前态结论是：主路径已经进一步稳定到“实例级 registry + 实例 API”，剩余问题主要集中在显式 compat 层的长期保留边界。

当前效果：

- owner 缺失、歧义、target 为空的错误表达在主协议间已经明显收敛

### 3.5 高级 Demo 的定位已弱化误导性

已完成项：

- `http-demo`、`graphql-demo`、`ws-demo`、`grpc-demo` 文件头已明确标注为 capability demo

当前效果：

- 高级 demo 仍可用于理解框架机制
- 但其复杂 wiring 不再容易被误读为业务默认模板

## 4. 高优先级混乱点

### 3.1 全局 Registry 与实例 Registry 并存

这是当前最核心的混乱来源。

现象：

- 文档与标准模板推荐新代码使用实例级 registry；当前对外创建入口已统一为 `application.NewRegistry()`
- 但很多 DSL 和内部流程仍会默认回退到 `registry.Global()`
- 使用者很容易不自觉地把声明写进全局单例，而应用实例编译时又读取另一份 registry

风险：

- 声明来源不稳定，排查成本高
- demo、测试、热重载、多应用并存场景容易出现串数据
- “声明到底注册到哪里”成为隐性规则，而不是显性规则

建议：

- 将实例级 registry 作为唯一推荐入口
- 包级 DSL 保留时，至少在文档和命名上明确标记为兼容入口
- 分阶段减少 `registry.Global()` 的默认回退路径
- 对新模板、新 demo、对外文档统一只展示实例级 registry 用法

### 3.2 公共 API 边界与官方示例不一致

现象：

- 文档声明业务代码应优先依赖 `application`、`adapter/*`、`binding/*`、`integrations/*`
- `core/compiler`、`core/runtime`、`core/registry`、`core/errors` 等属于内部基础设施层
- 但多个 demo 仍直接 import 内部包

风险：

- 使用者会以 demo 为准，而不是以边界文档为准
- 业务代码一旦直接依赖内部包，后续内部演进会放大升级成本
- “哪些能力算公共 API”会长期模糊

建议：

- 统一清理 demo，使其只展示推荐使用面
- 将 demo 分为“业务接入示例”和“框架扩展示例”
- 业务接入示例禁止直接 import 内部基础设施包
- 若某些内部能力业务确实需要，则应提升到公共包，而不是继续靠示例绕过边界

### 3.3 协议 Owner 规则不统一

现象：

- HTTP 插件主要按 `controller` 做 owner 推导
- GraphQL 插件允许 `controller + resolver`
- WS 插件也允许多种 owner 来源
- 不同协议对“handler 归属于哪个模块容器”的认知不一致

风险：

- 接入者需要按协议分别记忆规则
- 多协议组合时，模块归属问题更难排查
- runtime 中的 `RouteContainers` 机制虽然合理，但前置 owner 规则不统一会放大理解成本

建议：

- 给出统一的 owner 模型定义，例如：
  - HTTP 使用 `controller`
  - GraphQL 使用 `resolver`
  - WS 使用 `gateway`
  - 这些概念在模块层统一归类为“协议入口组件”
- 在编译期诊断中明确打印 owner 推导规则与失败原因
- 在标准模板中明确每类协议入口组件应注册在模块的哪个位置

### 3.4 编译期主模型与运行期 Fallback 双轨并存

现象：

- v3 的主设计已经是编译期收敛
- 但全局 AOP 仍保留 runtime fallback 入口以兼容未完全走编译计划的路径

风险：

- 使用者难以判断某项行为到底属于编译期规则还是运行期补救逻辑
- 维护者后续修改执行链时容易产生“改了一边，另一边还在兜底”的问题
- 编译期模型的纯度被削弱

建议：

- 明确列出仍依赖 runtime fallback 的场景清单
- 为这些场景建立迁移计划
- 中长期目标是默认行为全部走编译期计划，runtime fallback 仅保留应急兼容用途

## 5. 中优先级混乱点

### 4.1 Application 层仍存在协议特例

现象：

- `application` 理论上应是协议无关的装配层
- 但仍存在类似 `SetGlobalPrefix()` 这样偏 HTTP 特化的接口

影响：

- 不一定造成直接 bug
- 但会持续削弱“application 只负责装配”的边界纯度

建议：

- 协议特定配置优先下沉到 adapter API
- `application` 只保留通用生命周期和装配语义

### 4.2 兼容 v2 的 Sugar 仍然偏厚

现象：

- `application` 中保留了多组全局 AOP sugar
- HTTP adapter 中保留了 `Listen`、`WithAddr`、`AsStandalone`、`SetGlobalPrefix` 等兼容命名

影响：

- 迁移成本更低
- 但会让新人分不清“推荐姿势”和“历史兼容姿势”

建议：

- 在文档中区分“推荐 API”和“兼容 API”
- 新示例只展示推荐 API
- 对兼容 API 做更明确的 deprecated 收敛计划

### 4.3 包级 DSL 入口过于显眼

现象：

- 例如 HTTP 的 `Controller(...)` 入口默认可以直接写入全局 registry
- 这种写法很顺手，但与实例挂载后再注册声明的推荐方式并存

影响：

- 造成“看起来两种写法都对，但底层并不完全等价”
- 在复杂应用里容易混用

建议：

- 标准文档只保留实例 API 的推荐路径
- 包级 DSL 明确标注为简写/兼容/测试辅助入口
- 若继续保留包级 DSL，最好增加显式的实例绑定版本

### 4.4 模块容器与路由归属机制对使用者不够直观

现象：

- 编译结果不仅有 routes，还有 `RouteContainers`
- 请求执行时会根据 `routeKey` 选择对应模块容器

影响：

- 这套设计本身是合理的
- 但如果缺少统一的 owner 规则与诊断输出，使用者很难建立完整心智模型

建议：

- 在 `StartupReport` 或编译诊断中增加“route -> module -> container”可视化信息
- 把“容器归属”作为核心文档的一部分，而不是隐藏在内部实现里

## 6. 可接受复杂度

以下内容虽然会让 v3 看起来复杂，但整体属于框架目标带来的正常复杂度，不应简单视为混乱。

### 5.1 目录层次较多

原因：

- v3 目标不是单一 HTTP 框架，而是统一承接多协议执行链路
- 因此 `application / adapter / binding / compiler / runtime / integrations` 分层是合理的

结论：

- 目录多不等于混乱
- 关键是边界是否稳定、推荐路径是否统一

### 5.2 多协议共享统一 Runtime

原因：

- 请求统一走 matcher、binding、pipeline、DI、invoke 链路
- 这天然比单协议框架更抽象、更厚一些

结论：

- 这是设计目标决定的复杂度
- 只要路由归属、AOP、绑定、诊断机制足够清楚，就属于可接受复杂度

### 5.3 协议插件存在各自特化逻辑

原因：

- HTTP 需要 matcher tree
- GraphQL 需要 field 级路由
- WS 需要 event/namespace 语义

结论：

- 各协议保留必要特化是正常的
- 真正的问题不在“差异存在”，而在“共性边界是否统一”

### 5.4 内部基础设施层较丰富

原因：

- `compiler`、`runtime`、`registry`、`graph` 等内部层是多协议内核的自然产物

结论：

- 内部层丰富本身不是问题
- 问题在于这些内部层是否被业务侧意外依赖、是否被示例错误暴露

---

## 7. 收敛优先顺序

建议按以下顺序治理：

### 第一阶段：先统一心智模型

- 统一推荐写法，只保留实例级 registry 作为主路径
- 修正文档与 demo，使二者完全一致
- 为不同协议定义统一的 owner 语义

### 第二阶段：再压缩兼容层

- 将兼容 API 与推荐 API 明确分流
- 减少 `application` 层的协议特例
- 收敛包级 DSL 对全局 registry 的隐式依赖

### 第三阶段：最后提升内核纯度

- 逐步减少 runtime fallback 路径
- 让编译期产物成为默认且唯一的执行来源
- 增强编译诊断和启动报告，降低内核复杂度的感知成本

---

## 8. 一句话结论

v3 当前不是“无架构的混乱”，而是“主架构成熟，但过渡态边界尚未彻底收拢”。

真正需要优先治理的只有四类问题：

- 全局状态
- 公共边界与示例不一致
- 协议 owner 规则不统一
- 编译期与运行期 fallback 双轨并存

除此之外，大量“看起来复杂”的地方，其实属于多协议统一 runtime 的正常复杂度，应当通过文档、示例、诊断能力来降低理解成本，而不是简单地推翻现有设计。

---

## 9. 行动项清单

以下行动项按照落地周期拆分为短期、中期、长期，目标是先统一外部心智模型，再逐步收缩内部过渡层。

### 8.1 短期行动项

目标：低风险收敛认知分裂，优先修正“对外表达”和“实际推荐路径”不一致的问题。

- [已完成] 统一所有对外文档，以实例级 registry 作为唯一推荐写法；当前对外创建入口已统一为 `application.NewRegistry()`
- [已完成] 统一 `cmd/*-demo` 示例定位，并新增业务接入样板层
- [已完成] 在 `adapter/*` 的包级 DSL 文档注释中明确标记“兼容入口”与“推荐入口”
- [已完成] 在 `API.md` 中增加“业务接入示例必须遵守的导入边界”小节
- [已完成] 在 `标准接入模板.md` 中补一段“禁止混用全局 registry 与实例 registry”的显式说明
- [已完成] 在 `README.md` 中增加“推荐接入路径”摘要，减少新人直接跟着 demo 走偏

短期完成标准：

- 新人只看 `README + 标准模板 + demo`，不会再形成两套接入心智
- 业务接入示例不再直接暴露内部基础设施包
- 文档与代码样例的推荐路径完全一致

### 8.2 中期行动项

目标：收敛接口与协议规则，让框架边界更纯。

- [进行中] 为 HTTP / GraphQL / WS / gRPC 定义统一的“协议入口组件”模型
- [进行中] 统一 owner 推导术语，例如 controller / resolver / gateway / service 都归入协议入口组件
- [已完成一部分] 在编译诊断与启动报告中输出 per-protocol 的 module owner 摘要
- [待完成] 在报告中进一步输出更细粒度的 `route -> owner -> module -> container` 视图
- [待完成] 减少 `application` 层的协议特定方法，把配置下沉到 adapter API
- [待完成] 对兼容 API 建立分级策略：保留、弱化、废弃、移除
- [待完成] 为包级 DSL 增加更显式的实例绑定用法，降低对全局 registry 的依赖

中期完成标准：

- 不同协议的模块归属规则可以用一页文档讲清楚
- 应用层 API 更接近协议无关装配层
- 兼容路径仍可用，但不会再干扰主路径认知

### 8.3 长期行动项

目标：提升内核纯度，减少过渡态逻辑。

- [待完成] 明确列出 runtime fallback 仍在服务的场景，并逐项迁移到编译期模型
- [待完成] 将全局 AOP 的默认行为完全前移到编译期产物
- [待完成] 进一步减少 `registry.Global()` 在框架内部的默认回退使用点
- [待完成] 若内部能力被业务频繁直接依赖，评估是否上升为稳定公共包
- [进行中] 为编译期诊断建立更强的可观测能力，例如声明来源、owner 推导链、route 冲突视图

长期完成标准：

- 默认执行链只有一套主模型，即编译期产物安装到 runtime 后执行
- 兼容逻辑从“默认共存”变成“局部兜底”
- 外部使用面与内部实现面边界长期稳定

## 10. 代码整改建议

本节将核心混乱点映射到具体目录、入口和建议改动位置，便于后续逐项落地。

### 9.1 全局 Registry 与实例 Registry 并存

涉及位置：

- `application/application.go`
- `core/registry/registry.go`
- `adapter/http/dsl.go`
- 其他 `adapter/*/dsl.go`
- `binding/*/register.go`

现状判断：

- `application.NewWithOptions(...)` 已收紧为必须显式传入实例级 registry
- 包级 DSL 入口默认将声明写入全局 registry
- `application.New(...)` / `application.NewCompat(...)` 仍保留全局 registry 兼容语义
- `compiler.Compile(...)` 已收紧为必须显式传入 registry，`compiler.CompileCompat(...)` 保留兼容读取语义
- 当前已补充 `RegistrySource` 与 warning，可显式识别是否命中了全局默认回退或全局声明残留
- 当前已建立 fallback source inventory，能够区分：
  - `write fallback`：真正把声明 / binding / integration 注册写入全局 registry 的兼容入口
  - `read fallback`：默认从全局 registry 读取声明的 helper 入口
  - `compat`：框架仍保留、但已显式命名的兼容入口

整改建议：

- 保留 `registry.Global()` 作为兼容机制，但不再作为对外主路径强调
- 审视所有 `NewCompatAPI(...)`、包级 DSL 和 `nil -> registry.Global()` 的剩余入口，逐步减少默认回退
- 为每个协议提供显式的实例级 DSL 使用样例，并把它作为唯一推荐示例
- 若短期不能移除全局回退，则至少在编译诊断中标识当前应用是否命中了全局 registry
- 对仍保留的 read fallback 单独建账，避免与 write fallback 混在一起讨论

当前 fallback inventory（2026-04）：

- `write fallback` 已显式记录的高频入口：
  - `adapter/*` 包级 DSL 与 `NewCompatAPI(...)`
  - `binding/*/RegisterDefaultsCompat()`
  - `core/integration.RegisterContainerBindingsCompat(...)`
  - `integrations/events.RegisterOnCompat/OnceCompat/HandlersCompat`
  - 多数 `integrations/*` 的 `RegisterBindingsCompat()` / `RegisterNamedBindingsCompat()`
  - 多数 `integrations/*` 已补充 `ForRootCompat(...)` / `ForRootsCompat(...)` / `ForRootMultiCompat(...)`
  - `integrations/* Module.InitDefaultFallback` 这类未注入实例级 registry 的默认回退已完成收紧，统一要求显式 `SetRegistry(...)` 或显式 `ForRootCompat(...)`
- `read fallback` 仍保留的代表入口：
  - `integrations/swagger.BuildFromHTTPRegistryCompat(...)`
  - `adapter/graphql.buildCompiledSchemaCompat(...)`
  - `integrations/events.AttachRegisteredHandlersCompat(...)`
- `compat` 仍保留的代表入口：
  - `application.New(...)`
  - `application.NewCompat(...)`
  - `compiler.CompileCompat(...)`
  - 各协议 `NewCompatAPI(...)`
  - 多数 integrations 的 `ForRootCompat(...)` 系列构造

当前建议分类：

- `recommended`
  - `application.NewWithOptions(..., Options{Registry: application.NewRegistry()})`
  - `compiler.Compile(moduleRef, reg, ...)`
  - mounted adapter 暴露的实例 API
- `compat`
  - `application.NewCompat(...)`
  - `compiler.CompileCompat(...)`
  - 各协议包级 DSL、`NewCompatAPI(...)`、各类 `ForRootCompat(...)` / `*Compat(...)` helper
- `internal-only`
  - adapter builder 内部防御式 `reg == nil` 兜底
  - integration/module/binding 初始化阶段的 `GlobalWithUsage(...)` 写入兜底

当前态补充（2026-04 第四阶段推进后）：

- 六协议 `Plugin.Scan(..., nil)` 已收紧为必须显式传入 registry，不再保留隐式全局读取分支
- `integrations/events.AttachRegisteredHandlers(...)` 与 `integrations/swagger.BuildFromHTTPRegistry(...)` 已收紧为必须显式传入 registry
- 剩余 read fallback 已基本只保留显式 compat helper，而不再通过普通 API 的 `nil` 参数隐式触发

下一阶段建议：

- 继续削减剩余低频 `write fallback`
- 为 `read fallback` 建立更显式的 compat 命名或实例级替代入口
- 已开始把高频 helper 改为显式 compat 命名，例如 `buildCompiledSchemaCompat(...)`、`AttachRegisteredHandlersCompat(...)`
- [已完成] 将高频 `nil -> Global()` 兼容入口补充为显式 `Compat` API，例如 `application.NewCompat(...)`、`compiler.CompileCompat(...)`、各协议 `NewCompatAPI(...)`、多数 integrations 的 `ForRootCompat(...)`
- [已完成] 六协议 `Plugin.Scan(..., nil)` 与部分高频 helper 的普通 API nil 回退已收紧，只保留显式 compat helper 的全局读取语义
- 后续重点转向 `events.RegisterOnCompat/RegisterOnceCompat/RegisterHandlersCompat` 这类显式 compat 写入口，以及剩余低频 fallback 的继续收缩

优先级：

- 高

### 9.3 协议 Owner 规则不统一

涉及位置：

- `adapter/http/plugin.go`

- `adapter/ws/plugin.go`
- `adapter/grpc/plugin.go`

- 但允许的 owner 类型不完全一致，导致模块归属规则按协议分裂

- 将 owner 推导失败的诊断统一成同一套报错结构，避免协议间语义漂移
- 在文档中补一张“协议入口组件与模块注册位置”的对照表

优先级：

- 高

## 11. 当前建议的下一步

结合当前已落地改造，下一阶段建议优先处理以下事项：

4. 开始梳理 runtime fallback 场景，为后续内核纯化做准备

## 12. 推荐实施顺序

为了避免“一上来改内核，结果对外心智还没统一”，建议按以下顺序推进：

1. 先改文档与 demo，统一推荐路径
2. 再统一 owner 规则与编译诊断输出
3. 然后收缩 `application` 特例与兼容 API 暴露面
4. 最后处理 runtime fallback 和全局状态的深层收敛

这样做的好处是：

- 成本最低的改动先产生认知收益
- 使用者最先感受到“框架变清楚了”
- 内核收敛可以在不打乱外部接入面的前提下逐步推进
