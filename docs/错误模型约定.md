# lania-g v3 错误模型约定

## 1. 目标

本文档用于约定当前多 module 版本的错误模型，目标如下：

- 优先让可预期失败通过 `error` 返回，而不是隐式 panic
- 保留少量显式 `Must...` 兼容入口，但不作为新代码默认推荐
- 让 builder、factory、binding、lifecycle 的错误边界更清晰
- 为后续 API 收敛提供统一判断标准

## 2. 总体原则

- 显式 `Must...` API 可以 panic
- 非 `Must...` API 应优先返回 `error`
- 编译期、启动期、运行期的错误应尽量带阶段信息
- 同一类失败应尽量使用一致的错误文案和元信息
- 新增 helper / builder 时，默认先设计 `error` 路径，再决定是否需要兼容 `Must...`

## 3. 分层约定

### 3.1 Module / DI

- `module.Get(...)`、`module.GetByType(...)`、`di.Get(...)`、`di.GetByType(...)`
  - 应返回 `error`
- `module.MustGet(...)`、`module.MustGetByType(...)`、`di.MustGet(...)`、`di.MustGetByType(...)`
  - 属于显式兼容 panic 入口
- 容器查找失败、类型不匹配、依赖构建失败
  - 应作为普通错误返回

### 3.2 Application / Compiler

- `application.New(...)`、`application.NewCompat(...)`、`application.NewWithOptions(...)`
  - 初始化失败直接返回 `error`
- `compiler.Compile(...)`、`compiler.CompileCompat(...)`
  - 编译失败直接返回 `error`
- `CompileDiagnostics()`、`StartupReport()`
  - 返回诊断或报告，同时保留错误信息
- 若将 `CompileDiagnostics` / `StartupReport` 作为 JSON 输出面
  - 现阶段视作稳定诊断合同，键名固定使用 `lowerCamelCase`
  - compat 聚合摘要优先读取 `compatFallbackCategories` / `compatFallbackSources`
- 编译冲突、owner 归属失败、协议声明非法
  - 应作为编译错误返回，而不是 panic

### 3.3 Adapter / Binding

- binding resolver 在参数缺失、类型不匹配、上下文不完整时
  - 应返回 `error`
- `MustBind`、`MustBodyAs`、`MustBodyBytes` 等显式 Must 包装器
  - 允许维持“失败即错误”的强语义，但不应通过隐藏 panic 传播
- adapter DSL 的 `Build()` 若当前 API 已为兼容入口保留无返回值
  - 新增能力优先通过诊断和运行前检查暴露问题

### 3.4 Integrations / Factory

- `ForRoot(...)`、`Factory.GetOrCreate(...)`、`Loader` / `Client` 初始化
  - 应返回 `error`
- `MustSection(...)`、`cache.Must[...]` 等显式 Must helper
  - 作为便捷语法保留，但文档中需明确推荐替代项

## 4. 推荐用法

- 应用和模块装配优先使用返回 `error` 的入口
- adapter DSL 优先使用 `BuildE()` 这类显式错误入口
- 业务代码优先使用 `Get...` / `Read...` / `Load...` / `Section...` 这类非 Must API
- 测试、启动脚本、一次性原型可谨慎使用 `Must...`
- 基础设施代码应避免把 panic 当作正常控制流

## 5. 兼容保留项

当前以下类型的 panic 入口可继续保留：

- 明确命名为 `Must...` 的 helper
- 测试代码中的快速失败
- 极少数仅用于暴露编程错误的内部断言

但这些接口不应作为新示例中的首选写法。

## 6. 迁移判断标准

新增或改造 API 时，优先按以下问题判断：

1. 这个失败是否可能由外部输入、配置、环境或声明错误触发？
2. 调用方是否有合理的恢复、降级或日志处理需求？
3. 这个能力是否位于框架基础设施层，而不是测试辅助层？

如果答案多数为“是”，则应优先返回 `error`。

## 7. 当前推荐替代关系

- `module.MustGetByType[T](...)` -> `module.GetByType[T](...)`
- `di.MustGetByType[T](...)` -> `di.GetByType[T](...)`
- `config.MustSection[T](...)` -> `config.ReadSection[T](...)`
- `config.MustLoad(...)` -> `config.Load(...)`
- `cache.Must[T](...)` -> `cache.Get[T](...)`
- `runtime.HandlerContext.MustGet(...)` -> `runtime.HandlerContext.Require(...)`
- `binding/http.MustBindInto(...)` -> `binding/http.BindInto(...)`
- `adapter/*` 的 `Build()` -> `BuildE()`

## 8. 一句话约定

当前多 module 版本遵循同一原则：“显式 Must 才允许 panic，默认 API 一律优先返回 error”。
