# v3 代码精简与收敛方案

## 1. 目标

本文档回答三个问题：

- `v3` 当前代码量是否有继续压缩空间
- 哪些目录和模式最适合优先精简
- 如何在不破坏边界清晰度和可维护性的前提下收敛代码

本文档关注的是“有效精简”：

- 不是为了减少文件数而机械合并
- 不是为了追求更短而牺牲可读性
- 而是优先消除模板化重复、边界漂移和兼容层堆积

结论先行：

- `v3` 当前非测试 Go 代码量已经不小，确实存在继续收敛空间
- 最值得处理的不是大逻辑文件，而是多处重复出现的“骨架代码”
- 推荐采用“抽公共骨架，保协议差异”的方式推进，而不是简单删目录或把所有逻辑塞进一个公共包
- 原《第一批试点重构方案》的试点范围、公共 helper 设计和阶段结果已并入本文，不再单独维护

---

## 2. 当前判断

基于当前 `v3` 目录结构和非测试 Go 文件统计，当前代码量可以大致分成三类：

### 2.1 必要复杂度

这部分代码虽然行数多，但主要承载真实框架复杂度，不应为了减行数而强行抽象：

- `core/runtime/*`
- `core/compiler/*`
- `core/module/*`
- `adapter/graphql/schema_*`
- `adapter/http/http.go`
- `adapter/ws/ws.go`
- `application/*`

这些目录承担的是运行时执行、编译期收敛、模块加载、协议特化等核心能力。它们的“厚”不一定是重复，而更多是能力本身的复杂度。

### 2.2 模板化重复

这部分代码是当前最适合压缩的重点区域：

- `binding/*/register.go`
- `integrations/*/refs.go`
- `adapter/*/plugin.go`
- `adapter/*/dsl.go`

这些文件之间普遍存在明显的结构重复：

- 相同的注册入口
- 相同的 resolver 包装结构
- 相同的 scan / compile 骨架
- 相同的“写入 registry -> 编译 -> 安装”模板

### 2.3 低收益小头

这部分代码可以保留，不值得作为精简重点：

- `doc.go`
- `protocol/*/protocol.go`
- 少量常量文件和极短桥接文件

它们虽然也算“额外文件”，但整体行数不高，且保留后对读码体验更好。

## 3. 当前可见的精简机会

以下数据用于帮助判断优先级，而不是单纯用于做“删行 KPI”。

### 3.1 可疑重复区块

当前已识别出几类高重复区块：

- `binding/*/register.go`：6 个文件，约 `1599` 行
- `integrations/*/refs.go`：10 个文件，约 `1933` 行
- `adapter/*/plugin.go`：6 个文件，约 `1215` 行
- `adapter/*/dsl.go`：6 个文件，约 `2462` 行
- `cmd/*/main.go`：8 个文件，约 `2419` 行

其中优先级最高的是：

1. `integrations/*/refs.go`
2. `binding/*/register.go`
3. `adapter/*/plugin.go`

原因：

- 重复度高
- 结构模式稳定
- 对外行为边界相对清楚
- 收敛后对主链路理解更友好

### 3.2 典型重复模式

`integrations/*/refs.go` 里反复出现的模式：

- 定义一个 resolver 结构体
- 实现 `Name()`、`AllowedProtocols()`、`Match()`、`Resolve()`
- 实现 `matchWrapper(...)`
- 实现“按名称取默认实例 / 命名实例”
- 实现“把实例 wrap 回泛型 wrapper”

`binding/*/register.go` 里反复出现的模式：

- `RegisterDefaults(...)`
- `RegisterDefaultsToRegistry(...)`
- `RegisterDefaultsCompat(...)`
- `DefaultResolvers()`
- `registration(...)`
- `runtimeBindingRegistration` 结构体

`adapter/*/plugin.go` 里反复出现的模式：

- `Plugin` 类型
- `ID()` / `Protocol()` / `Register()`
- 基于 snapshot + owner index 的 `Scan()`
- 把 scan result 转成 compiled routes 的 `Compile()`

这些模式说明，很多代码并不是协议真的不同，而是“相同骨架被每个协议各写一份”。

## 4. 哪些地方不建议为减行数而改

为了避免误判，以下区域不建议作为第一批精简目标。

### 4.1 `doc.go`

虽然 `doc.go` 文件数量不少，但总体行数很低，而且对包职责说明有明显帮助。删除这些文件并不会真正降低维护成本。

建议：

- 保留
- 仅在职责明显过时或表述重复时做轻量更新

### 4.2 `protocol/*`

协议常量包虽然很薄，但它们提供了清晰的协议边界：

- 协议标识集中
- import 方向清楚
- 不会引入额外理解成本

建议：

- 继续保留按协议拆分
- 不为了统一而做“协议常量大一统”

### 4.3 核心大文件

例如：

- `core/compiler/compile.go`
- `core/runtime/pipeline.go`
- `core/runtime/executor.go`
- `adapter/graphql/schema_build.go`

这类文件是否需要拆分，应该以职责和可读性为依据，而不是“文件太长所以要压缩”。如果抽象不当，往往会把复杂度转移到更多间接层里。

## 5. 推荐的精简方向

### 5.1 方向 A：收敛 integration 引用绑定骨架

目标：

- 把 `integrations/*/refs.go` 中的通用模式抽到公共 helper
- 让每个 integration 只保留“自身差异”

适用对象：

- `integrations/cache/refs.go`
- `integrations/http/refs.go`
- `integrations/grpc/refs.go`
- `integrations/es/refs.go`
- `integrations/kafka/refs.go`
- `integrations/logger/refs.go`
- `integrations/minio/refs.go`
- `integrations/config/refs.go`
- `integrations/otel/refs.go`
- `integrations/orm/refs.go`

可抽出的公共能力：

- 通用 resolver 实现
- 通用 `matchWrapper(pkgPath, baseName)`
- 通用 marker type 命名解析
- 通用 wrapper 回填逻辑
- 通用“先按 token 取，失败后按类型兜底”的解析流程

每个 integration 保留的差异：

- token 生成规则
- 默认实例名
- marker interface 名称
- 目标实例类型
- 个别 integration 的特殊命名解析或注入语义

预期收益：

- 降低重复实现和重复注释
- 让新 integration 的接入模板更短
- 使跨 integration 的行为更一致

风险：

- 如果 helper 设计过泛，会把类型约束和错误语义藏得太深
- 若不同 integration 的“按名取实例”规则不完全一致，抽象层需要允许轻量定制

建议策略：

- 先选 `cache/http/logger/minio/es` 这类模式接近的 integration 试点
- 不要第一步就把全部 integration 强行统一

### 5.2 方向 B：收敛 binding 注册骨架

目标：

- 把 `binding/*/register.go` 收敛成“描述表 + 通用注册器”

适用对象：

- `binding/http/register.go`
- `binding/graphql/register.go`
- `binding/grpc/register.go`
- `binding/ws/register.go`
- `binding/mq/register.go`
- `binding/scheduler/register.go`

可抽出的公共能力：

- 通用 `BindingRegistration` 结构
- 通用 `RegisterDefaultsToRegistry(...)`
- 通用 `RegisterDefaultsCompat(...)`
- 通用 `ResolverSpec -> runtime.BindingResolver` 转换

每个协议保留的差异：

- 协议 id
- resolver 列表
- 协议特有 wrapper 匹配规则
- 协议特有 resolve 行为

预期收益：

- 大幅减少样板方法
- 统一协议 binding 注册手法
- 降低新增协议或新增 binding 时的模板负担

风险：

- 如果公共注册器同时承担过多兼容逻辑，会让协议代码变短但公共层变晦涩

建议策略：

- 先抽最稳定的注册壳子
- 暂时不抽 resolver 内部逻辑

### 5.3 方向 C：收敛 adapter plugin 骨架

目标：

- 把各协议 `plugin.go` 中重复的扫描与编译骨架抽出来

适用对象：

- `adapter/http/plugin.go`
- `adapter/graphql/plugin.go`
- `adapter/grpc/plugin.go`
- `adapter/ws/plugin.go`
- `adapter/mq/plugin.go`
- `adapter/scheduler/plugin.go`

可抽出的公共能力：

- 通用 `Plugin` 骨架接口
- 通用 owner resolution 流程
- 通用 scan result 收集 helper
- 通用 `CompileRouteSet(...)` 包装器
- 通用错误构造 helper

每个协议保留的差异：

- 声明项类型
- owner 允许来源
- route key 生成方式
- matcher/tree/install 方式

预期收益：

- 协议插件的可读性更强
- owner 规则更容易统一
- 编译期诊断更容易做跨协议收敛

风险：

- 这是三类收敛里风险最高的一类
- 协议差异是真实存在的，抽象过头会把“不同协议的语义差异”错误地隐藏起来

建议策略：

- 优先抽错误构造、owner 解析、route 编译包装等小公共层
- 暂不追求一个巨大的“万能协议插件基类”

### 5.4 方向 D：压缩 DSL 样板

目标：

- 减少 `adapter/*/dsl.go` 中重复的声明写入模板

适用对象：

- 全部协议 `dsl.go`

建议方式：

- 抽声明 builder 或 registry writer helper
- 保留协议对外 DSL 命名
- 把“写 declaration 的样板动作”从 DSL 层抽走

风险：

- DSL 是用户最容易读到的代码之一
- 过度收敛会让 API 看上去整齐，但失去协议语义上的直观性

建议策略：

- 优先压缩内部 helper
- 对外 DSL 形式尽量保持清楚和显式

### 5.5 方向 E：整理 demo 结构

目标：

- 降低 `cmd/*/main.go` 的重复装配代码
- 让 demo 的职责分层更清楚

可考虑方式：

- 抽公共 app bootstrap helper
- 将重复 wiring 提炼到 demo 内部公共包
- 区分“业务接入样板”和“能力展示样板”

注意：

- demo 的目标首先是易读，其次才是减少重复
- 如果抽 helper 反而让示例看不懂，就不值得做

## 6. 推荐推进顺序

建议按“低风险高收益 -> 中风险高收益 -> 高风险高收益”的顺序推进。

### 第一阶段：先收敛机械重复

优先处理：

- `integrations/*/refs.go`
- `binding/*/register.go`

目标：

- 不改变对外 API
- 不改变协议行为
- 只消除模板化重复

验收标准：

- 公共 helper 已抽出
- 原始文件显著缩短
- 行为和现有测试保持一致

### 第二阶段：再收敛编译期骨架

优先处理：

- `adapter/*/plugin.go`

目标：

- 统一 owner 解析和错误表达
- 降低协议插件之间的样板差异

验收标准：

- 至少形成一层可复用的 scan / compile helper
- 主协议插件的错误结构更一致

### 第三阶段：最后处理 DSL 与 demo

优先处理：

- `adapter/*/dsl.go`
- `cmd/*`

目标：

- 在不损伤可读性的前提下压缩样板代码

验收标准：

- 业务接入样板更短
- 高级 demo 定位更清楚
- 不牺牲示例的可读性

## 7. 实施边界

为了避免“为了精简而精简”，建议在实施过程中明确以下边界。

### 7.1 不追求文件数最少

文件多不等于设计差。对于框架代码来说，保持分层明确往往比把多个职责压成一个文件更重要。

### 7.2 不把所有差异都抽到公共层

协议差异、integration 差异是客观存在的。公共层只抽“稳定重复的骨架”，不要抽“仍在演化中的语义”。

### 7.3 不在同一轮同时做重构和行为改造

如果一轮改动同时包含：

- 抽象重构
- 兼容层收紧
- 错误语义调整
- API 迁移

那么排查成本会急剧上升。

建议：

- 先做等价重构
- 再做行为收口

### 7.4 文档和代码同时收敛

公共 helper 一旦落地，应同步更新：

- `docs/技术方案.md`
- `docs/架构收敛文档.md`
- 相关接入文档

否则代码虽然变短，外部心智模型仍然会滞后。

## 8. 预期收益

如果按本文建议推进，预期收益主要不是“看上去少了几千行”，而是：

- 新人更容易识别哪些是协议差异，哪些只是模板代码
- 新增 integration / binding / adapter 时成本更低
- 兼容层和主路径更容易区分
- 协议间行为更一致，诊断也更容易统一
- 后续再做架构收敛时，有更稳定的公共骨架可以依赖

从代码量角度看，最有希望获得可见缩减的是：

- `integrations/*/refs.go`
- `binding/*/register.go`
- `adapter/*/plugin.go`

其中第一批改造更适合追求“低风险减重”，第二批更适合追求“结构统一”。

## 9. 减行预估

以下预估以当前非测试 Go 代码量约 `39459` 行为基线，主要针对重复度较高的区域进行估算：

- `integrations/*/refs.go`
- `binding/*/register.go`
- `adapter/*/plugin.go`
- `adapter/*/dsl.go`
- `cmd/*/main.go`

### 9.1 低档预估

适用前提：

- 只做低风险的等价重构
- 不改对外 API
- 不大幅调整协议插件和 DSL 形态

建议动作：

- 收敛 `integrations/*/refs.go`
- 收敛 `binding/*/register.go`
- 对 `adapter/*/plugin.go` 只抽小型公共 helper
- 对 `dsl.go` 和 demo 只做少量内部辅助抽取

预估减行：

- 约 `1700` 行
- 约占当前非测试 Go 代码的 `4%` 左右

判断：

- 这是最稳妥的一档
- 性价比高，回归风险低
- 适合作为第一阶段真实目标

### 9.2 中档预估

适用前提：

- 在完成低风险收敛后，继续推进协议层与 demo 层的样板压缩
- 允许引入一层稳定的公共骨架

建议动作：

- 完成 `integrations/*/refs.go` 的公共化
- 完成 `binding/*/register.go` 的描述表化
- 对 `adapter/*/plugin.go` 抽取更完整的 scan / compile 骨架
- 对 `adapter/*/dsl.go` 提取 registry writer / builder helper
- 适度整理 `cmd/*/main.go` 的重复启动逻辑

预估减行：

- 约 `2300` 到 `2500` 行
- 中位值约 `2400` 行
- 约占当前非测试 Go 代码的 `6%` 左右

判断：

- 这是最现实的一档
- 可以在不明显伤害可读性的前提下获得可见减重
- 也是本文最推荐的目标区间

### 9.3 高档预估

适用前提：

- 对协议插件和 DSL 做更深入的骨架抽象
- 对 demo 和少量外围文件也一并收敛

建议动作：

- 在中档基础上继续压缩 `adapter/*/plugin.go`
- 更积极地抽取 `adapter/*/dsl.go` 公共写入模板
- 统一更多 demo 的公共启动流程
- 顺手清理少量外围重复注释和小型桥接样板

预估减行：

- 约 `3200` 行
- 约占当前非测试 Go 代码的 `8%` 左右

判断：

- 这档不是做不到，但需要更强的抽象克制
- 如果控制不好，容易出现“代码变短了，但理解成本变高了”的副作用
- 除非前两档推进顺利，否则不建议一开始就以这一档为目标

### 9.4 性价比判断

从收益和风险平衡来看，推荐优先追求的不是“理论最大减行”，而是“最容易稳定拿到的减行”。

建议目标：

1. 第一目标：先拿到 `1200` 到 `1600` 行的稳定下降
2. 第二目标：在结构稳定后推进到 `2300` 到 `2500` 行
3. 第三目标：仅在抽象效果良好时，再考虑冲击 `3000+` 行

原因：

- 第一目标主要来自 `integrations/*/refs.go` 和 `binding/*/register.go`
- 这两块重复度高、风险低、回报直接
- 后续是否继续压缩 `plugin.go` 和 `dsl.go`，应以可读性和行为清晰度为前提

## 10. 当前进展（2026-04-26）

截至当前，这条“先收低风险重复骨架，再收 plugin 外壳”的路线已经验证有效，且没有出现明显的行为回归信号。

### 10.1 已完成的主要收敛

- `binding/*/register.go` 已完成第一轮收敛，统一切到 `BindingRegistration` + `NewBindingResolver(s)` 的转换方式
- `integrations/*/refs.go` 的大部分模板骨架已并入 `core/integration/refbinding.go`
- `integrations/config/refs.go` 已纳入低风险收敛范围
- `integrations/orm/refs.go` 已完成 Phase 1，只删除低风险骨架，保留 repository 构造和匿名字段写入等高风险逻辑
- 运行时硬编码包路径已做一轮全局清理，改为基于本包类型推导 `PkgPath()`
- `adapter/*/plugin.go` 已完成第一阶段公共外壳收敛：
  - `mq`
  - `scheduler`
  - `ws`
  - `grpc`
  - `http` 的 `Scan()`

- `adapter/*/dsl.go` 已完成一轮薄 helper 收敛：
  - 提取了 `FindMethodName(...)`
  - 提取了 `MergeParamPipes(...)`
  - 提取了 `CopyIntStringMap(...)`
  - 各协议 builder 结构与链式语义保持不变

### 10.2 当前累计减行

按当前工作树统计：

- 已跟踪文件累计：`967 insertions(+), 1802 deletions(-)`

### 10.3 对预估区间的修正判断

结合当前真实推进结果，原文第 9 节的三档预估仍然成立，但可以补一条更贴近现状的判断：

- 当前已证明，`binding/*/register.go` + `integrations/*/refs.go` + `adapter/*/plugin.go` 第一阶段合起来，拿到数百行的稳定净减是现实的
- 当前又进一步证明，对 `adapter/*/dsl.go` 只做薄 helper 收敛，也能继续稳定释放重复代码
- 若继续向少量 demo / 兼容壳推进，仍有机会继续接近本文此前给出的低档到中档区间
- 但从性价比看，后续每一轮新增收益都会逐步下降，应更强调“风险/收益比”，而不是单纯追求总删行

### 10.4 当前剩余高性价比方向

截至这一轮，最容易继续推进的低风险区域已经不多，后续更适合：

- 检查 demo / compat 外壳是否有明显的重复装配代码
- 对已有 helper 再做轻量统一，而不是继续做更深的“万能抽象”

## 11. 一句话结论

`v3` 可以精简，但应优先精简“重复骨架”，而不是“真实复杂度”。

推荐顺序是：

1. 先收敛 `integrations/*/refs.go`
2. 再收敛 `binding/*/register.go`
3. 然后处理 `adapter/*/plugin.go`
4. 最后再评估 `dsl.go` 和 demo

这样可以在不伤害架构边界的前提下，逐步把 `v3` 从“代码量偏厚但主线清楚”，推进到“主线清楚且重复更少”。
